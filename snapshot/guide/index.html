Pyronaut

Tools for Python + Micronaut integration

Version: 0.0.7-SNAPSHOT

1 Introduction

Pyronaut is a framework for building Python applications on GraalPy and Micronaut. It gives Python code access to Micronaut’s HTTP server, dependency injection, configuration, validation, serialization, observability, and testing capabilities. Pyronaut processes Python and Java source before the application starts, preparing routes, beans, serializers, and validation metadata.

Use type hints and decorators to build applications for development, direct execution, or deployment as JVM applications, native executables, or containers. You write ordinary Python while Pyronaut connects it to the Micronaut application model.

Recommended path

  1. Start with Installing Pyronaut.

  2. Follow Create a Pyronaut Project to build a project in project mode; complete Step 1 before running pytest. Alternatively, follow The FastAPI Tutorial to try direct-source mode without a project virtual environment.

  3. After the tutorial, read Micronaut Concepts for Python Developers. The remaining chapters assume you understand these concepts. Then use Configure a Pyronaut Project as you add dependencies and application settings.

  4. Use Testing and Packaging and Deployment when you are ready to verify and distribute the application.

If an existing Maven or Gradle build manages the project, or if Python code needs Java libraries, see Using Maven and Gradle Projects and Using Python Packages and Java Libraries.

A minimal application

Create app.py:

from micronaut.http.annotation import Get


@Get("/")
def index() -> dict[str, str]:
    return {"Hello": "World"}

Run:

pyronaut dev app.py

Pyronaut processes the source, starts a server on port 8080, and reloads it when the file changes. The route returns JSON, Pyronaut generates an OpenAPI description, and it serves Swagger UI at /swagger-ui/index.html. This direct-source application does not need pyproject.toml, a GraalPy virtual environment, or a separate application server.

Why choose Pyronaut

A typical production Python service combines a web framework, an application server, validation, serialization, testing, observability, packaging, and deployment tooling. Pyronaut connects these concerns through one application model on top of Micronaut.

Compared with Flask and FastAPI:

  • Decorators map to Micronaut annotations. @Get, @Singleton, @Value, and the other decorators in this guide correspond to Micronaut annotations. Type hints on parameters and return values tell Micronaut how to bind requests, validate input, and serialize output.

  • Processing happens before startup. pyronaut process reads your decorators and type hints and generates route and bean metadata, serializers, and validation metadata before the application starts. Source and generated-metadata errors can therefore appear during processing instead of on the first request.

  • Java libraries are available from Python. Declare a Java library in pyproject.toml, resolve it with pyronaut install, and import its classes from Python. See Using Python Packages and Java Libraries for supported integration patterns.

  • Threads and asyncio both work. Plain def routes run on a thread pool, async def routes run on the Netty event loop, and Python coroutines can await Java asynchronous results directly. See Threading, Blocking Work and asyncio.

The application model also provides:

Observability and operations

Pyronaut exposes Micronaut’s management endpoints (health, info, environment, loggers, routes, and thread dumps) as part of the runtime. Add the Micronaut modules for Micrometer metrics with registries for Prometheus, Datadog, CloudWatch, and others, OpenTelemetry distributed tracing, and Kubernetes service discovery, configuration, and health probes through [tool.pyronaut.dependencies]. For JVM deployments, Java tooling such as Java Flight Recorder, heap and thread analysis, and JMX also applies to the Python service.

Test Resources for local infrastructure

With MicronautTest, pyronaut test can run pytest against the application context and an embedded server. When the configured dependencies identify a supported service, Micronaut Test Resources can start the service, often in a Docker container through Testcontainers, and supply its connection settings. This can remove the need to hard-code local service URLs and credentials. The same mechanism supports pyronaut dev. See Test Resources and Docker.

One CLI for the application lifecycle

pyronaut create, dev, test, validate-config, and build cover the project lifecycle. The build command supports Python wheels, runnable JARs, container images, GraalVM native executables, and reusable Crema runtime images. See Packaging and Deployment.

Multiple deployment targets

JVM packages require a compatible GraalVM JDK. Native executable targets depend on the available launcher bundle and native toolchain for the target platform. Packages for Python applications include the embedded GraalPy runtime, so the deployment target does not need a separate Python installation.

Editor support

pyronaut install generates stubs that Pylance and PyCharm can use for completion and type checking of Micronaut and Java APIs. It also writes JSON schemas that supported editors can use to validate pyproject.toml and application.toml.

Project structure

A typical Pyronaut project directory contains:

  • Python application sources under src

  • Python tests under tests

  • Micronaut configuration such as application.toml under config

  • Python and Java dependencies declared in pyproject.toml

  • Generated state under pyronaut, which is safe to delete

The pyronaut command is the single entry point. It creates projects, resolves Java dependencies, processes sources, runs applications during development or for deployment, runs tests, validates configuration, and builds wheels, JARs, native executables, and container images. It also generates editor stubs that VS Code (Pylance) and PyCharm can use for completion of Micronaut and Java APIs.

3 Installing Pyronaut

Install the Pyronaut CLI, then run pyronaut setup to provision the SDK that runs Pyronaut applications.

Install the Pyronaut CLI

The CLI requires Python 3.10 or later.

Install Pyronaut from PyPI:

python3 -m pip install --upgrade 'pyronaut==0.0.7-SNAPSHOT'
pyronaut --version

The same wheel is also attached to its GitHub release. To install it directly from the release instead of PyPI, point pip at the release assets:

python3 -m pip install --upgrade --no-index \
  --find-links https://github.com/micronaut-projects/pyronaut/releases/expanded_assets/v0.0.7-SNAPSHOT \
  'pyronaut==0.0.7-SNAPSHOT'
pyronaut --version

The Python installation used by pip only installs the CLI. Pyronaut applications run with the embedded GraalPy runtime supplied by the Pyronaut SDK, and pyronaut setup provisions the matching GraalPy interpreter for project virtual environments. pyronaut --version shows the required version on the GraalPy Interpreter line. If your application or tests use Python packages, see Getting Started Step 1 for the project environment setup.

Provision the Pyronaut SDK

Provision the SDK after installing or upgrading the Pyronaut CLI:

pyronaut setup

Setup locates or provisions a compatible GraalVM JDK and the exact GraalPy interpreter the SDK was built with, downloads the native Pyronaut launchers, resolves the SDK dependencies, and stores validated machine-local state under ~/.pyronaut. You do not need to install GraalVM or GraalPy manually for the default setup.

Setup reuses a matching GraalPy that is already installed with pyenv or under ~/.pyronaut/sdks. When none is installed, setup runs pyenv install if pyenv is available, and otherwise downloads GraalPy into ~/.pyronaut/sdks.

Pyronaut records setup state in setup.json under the Pyronaut home directory:

~/.pyronaut/setup/<sdk-version>/<os>-<architecture>/setup.json

The placeholders <sdk-version>, <os>, and <architecture> identify the SDK version and the platform where setup runs.

The setup command is idempotent. Run pyronaut setup --refresh when you need to re-resolve setup dependencies or rewrite setup state. Use pyronaut setup --offline only when the required JDK, native launchers, and Maven artifacts are already cached. If Pyronaut cannot find a recorded artifact, or if the SDK, platform, repository, or native bundle configuration changes, execution commands exit with code 8 and instruct you to run pyronaut setup again. Help and version commands remain available before setup.

To upgrade an installed CLI to the latest release and provision it in one step, run:

pyronaut update

The command also removes the launchers and cached artifacts of older versions. See Pyronaut CLI Reference for its options.

If pyronaut setup or any later command fails, run pyronaut doctor first:

pyronaut doctor

It checks the Python version, the installed wheel and its setup state, the GraalVM JDK, GraalPy and interpreter mismatches, the native launchers, proxy settings, and Docker. Inside a project it also checks pyproject.toml, stale pyronaut install state, the threading configuration, that every declared Python package imports on the project’s GraalPy under the configured context pool, GraalPy’s published compatibility results for those packages, and pytest. Failing rows include a suggested command or action when Pyronaut can identify one, and pyronaut doctor --json produces the same report for tooling. See Pyronaut CLI Reference for the full list of checks.

By default, setup resolves SDK dependencies from Maven Central. When the installed SDK is a snapshot build, setup also checks Sonatype Central’s snapshots repository for pre-release artifacts. Override the setup repositories globally in ~/.pyronaut/settings.toml; an explicit list replaces these defaults:

[maven]
repositories = [
  "mavenCentral",
  "https://central.sonatype.com/repository/maven-snapshots/"
]

Setup installs native executables into ~/.pyronaut/bin:

~/.pyronaut/bin/<version>/<os>-<architecture>/
See Proxy Configuration for proxy setup.

Project installation

After you create a project with pyronaut create or add a pyproject.toml as described in Create a Pyronaut Project, run:

pyronaut install

pyronaut install creates the project .venv with GraalPy and installs the Python dependencies declared in pyproject.toml or requirements.txt into it. It then resolves Java dependencies for the configured build, runtime, development-runtime, test, and test-resources-server scopes.

By default, Pyronaut installs dependency artifacts into Maven local:

~/.m2/repository

If you start the JVM with -Dmaven.repo.local=/path/to/repo, Pyronaut uses that value as the default local repository instead. Override the selected repository for an invocation:

pyronaut install --local-repository .pyronaut-m2

Pyronaut resolves relative paths passed to --local-repository against the project directory. Pyronaut still writes project state and classpath manifests under pyronaut; the option changes only where Pyronaut stores resolved Maven artifacts.

Generated project state

pyronaut install writes files that later commands consume:

  • scoped dependency manifests under pyronaut/resolved-*-dependencies

  • pyproject.toml schema support under pyronaut/schemas

  • optional application.toml schema support

  • Python IDE stubs under pyronaut/ide-stubs

Pyronaut generates the pyronaut directory as state. Treat it as generated state, not application source.

Platform notes

The CLI currently targets macOS and Linux. Docker is only required when using Micronaut Test Resources or Docker package formats.

4.1 Create a Pyronaut Project

Use this guide to create a Pyronaut project, add an HTTP route, configure the application, and run a test. If you prefer direct-source mode, follow the FastAPI tutorial instead.

Step 1: Complete the prerequisites

Pyronaut runs Python application code and Python tests on GraalPy, not on CPython. pyronaut setup provisions the GraalPy version used by Pyronaut, and pyronaut --version shows it:

pyronaut setup
pyronaut --version

If pyenv is installed, setup installs GraalPy with pyenv; otherwise it downloads GraalPy into ~/.pyronaut/sdks.

Change to your project directory and install the project:

cd <project-dir>
pyronaut install

pyronaut install creates a GraalPy virtual environment in .venv and uses pip to install the Python dependencies declared in pyproject.toml or requirements.txt, plus pytest when the project has Python tests. Pyronaut uses this environment for application and test launches. A CPython-created environment cannot provide packages to the embedded GraalPy runtime.

See Using Python Packages and Java Libraries for Python package compatibility and Java library guidance.

Step 2: Create the project

Use pyronaut create demo to generate the project. Add --features data-jdbc,mysql when you need those Micronaut features. The generated project includes the configuration, source, and test layout used by the remaining steps.

The following subsection shows the key generated files for readers who want to understand or customize the project manually.

Manual project configuration

pyproject.toml is the standard Python project file. Pyronaut reads its own settings from the [tool.pyronaut] tables and uses the standard [project] and [build-system] tables for Python packaging.

Create pyproject.toml:

[project] (1)
name = "hello-pyronaut"
version = "0.1.0"
dynamic = ["scripts"]

[build-system]
requires = ["setuptools", "wheel", "tomli"]
build-backend = "setuptools.build_meta"

[tool.pyronaut]
repositories = ["mavenCentral"] (2)

[tool.pyronaut.dependencies] (3)
runtime = []
build = []
test = [
  "io.micronaut.pyronaut:micronaut-pyronaut-pytest",
  "io.micronaut.pyronaut:micronaut-pyronaut-requests"
]
1 The project name and version are also used when packaging the application.
2 The repositories setting tells Pyronaut where to resolve Java libraries. mavenCentral is the default Java-library repository, roughly equivalent to PyPI for Python packages.
3 Declare Java dependencies by scope. Pyronaut makes runtime dependencies available to application code, uses build dependencies while it processes sources, and makes test dependencies available when tests run. This example leaves runtime empty because the Pyronaut launcher already includes Micronaut’s HTTP server, serialization, and validation support. See How Pyronaut Works for details.

For dependency syntax, Python packages, and additional Java dependency options, see Installing Python and Java Dependencies.

Step 3: Add an HTTP route

An HTTP route maps an HTTP method and path to a Python function. Although the example uses controllers.py as its filename, the example does not define a controller class annotated with @Controller; it defines a module-level route function.

Create src/controllers.py:

from micronaut.http.annotation import Get


@Get(value="/", produces="text/plain")
def index() -> str:
    return "Hello from Pyronaut"

The @Get decorator maps GET / to the index function. Group routes in a @Controller class when they share a prefix or need injected services. See Building HTTP APIs for more options.

Step 4: Add application configuration

Create config/application.toml:

[micronaut.application]
name = "hello-pyronaut"

[micronaut.server]
port = 8080

The config/ directory is on the runtime classpath. Use application.toml for Micronaut settings such as the server port, data sources, and application-specific properties. See Configuration Injection to read those settings from Python.

Step 5: Run the application

If you installed or upgraded Pyronaut, provision the SDK before starting the application:

pyronaut setup

Then start the development server:

pyronaut dev

pyronaut dev prepares and starts the application in one command. It:

  • installs the Java dependencies declared in pyproject.toml;

  • processes the Python sources; and

  • enables file watching so that edits reload the application.

Run pyronaut install and pyronaut process separately when you change dependencies or want to inspect processing errors without starting the server:

pyronaut install
pyronaut process

Verify the route:

curl http://localhost:8080/

The response is Hello from Pyronaut.

Step 6: Add and run a test

Create tests/test_controller.py:

import pytest
import requests

from pyronaut.test import MicronautTest, micronaut_test_fixture


@pytest.fixture
def my_context(request):
    fixture = micronaut_test_fixture(request, MicronautTest())  (1)
    yield fixture
    fixture.stop()


@pytest.fixture
def client(my_context):
    return requests.with_context(my_context)  (2)


def test_index(client):
    response = client.get("/")
    assert response.status_code == 200
    assert response.text == "Hello from Pyronaut"
1 micronaut_test_fixture starts the application and an embedded HTTP server on a random port for the fixture’s duration.
2 requests.with_context returns a requests-compatible client whose relative URLs point at the embedded server, so the test does not need to know the port. The micronaut-pyronaut-requests test dependency provides it.

Run the test suite through Pyronaut so that the Micronaut classpath, processed sources, and GraalPy runtime are set up consistently:

pyronaut test

Pyronaut runs pytest inside the application’s JVM and writes an HTML report to pyronaut/reports/tests/index.html. See Testing for JUnit-style Python tests, test selection, and Test Resources.

4.2 The FastAPI Tutorial

This tutorial recreates the FastAPI example using Pyronaut.

It is for readers familiar with FastAPI who want to learn Pyronaut.

You will use standard Python type hints, generate OpenAPI documentation, validate input, reload the application during development, and run an automated test. First install Pyronaut and run pyronaut setup. This direct-source workflow uses the embedded GraalPy runtime and JUnit 5 integration, so it does not require a project virtual environment or pytest.

Create the application

Create an empty project directory, change into it, and create main.py:

from micronaut.http.annotation import Get


@Get("/")
def read_root() -> dict:
    return {"Hello": "World"}


@Get("/items/{item_id}")
def read_item(item_id: int, q: str | None = None) -> dict:
    return {"item_id": item_id, "q": q}

The @Get decorators declare two HTTP GET operations. The item_id: int type hint tells Pyronaut to convert and validate the path value as an integer. Because q defaults to None, it is optional.

Start the development server

Run the development server from the directory containing main.py:

pyronaut dev

When you omit the source argument, pyronaut dev detects main.py in the current directory. Development mode watches the source and reloads the application after changes. The server listens on http://localhost:8080 by default.

Verify the routes

Verify the root route:

curl http://localhost:8080/

The response is:

{"Hello":"World"}

Verify the item route:

curl "http://localhost:8080/items/5?q=somequery"

The response is:

{"item_id":5,"q":"somequery"}

The application now:

  • handles GET requests at / and /items/{item_id}.

  • converts item_id to an int.

  • accepts the optional q query parameter as a str.

  • returns both responses as JSON.

Verify validation with a path value that Pyronaut cannot convert to an integer:

curl -i http://localhost:8080/items/foo

A representative response begins:

HTTP/1.1 400 Bad Request

Explore the API documentation

  • Open Swagger UI to explore and call the API interactively.

  • Open ReDoc for an alternative view of the same API documentation.

Pyronaut generates the OpenAPI description from the routes and Python types while processing main.py.

Add a request body

Replace main.py with the following version to accept an Item request body:

from dataclasses import dataclass
from typing import Annotated

from jakarta.validation import Valid
from jakarta.validation.constraints import NotBlank, Positive
from micronaut.http.annotation import Body, Get, Put
from micronaut.serde.annotation import Serdeable


@Serdeable
@dataclass
class Item:
    name: Annotated[str, NotBlank]
    price: Annotated[float, Positive]
    is_offer: bool | None = None


@Get("/")
def read_root() -> dict:
    return {"Hello": "World"}


@Get("/items/{item_id}")
def read_item(item_id: int, q: str | None = None) -> dict:
    return {"item_id": item_id, "q": q}


@Put("/items/{item_id}")
def update_item(
    item_id: int,
    item: Annotated[Item, Body, Valid],
) -> dict:
    return {"item_name": item.name, "item_id": item_id}

Item is a standard Python dataclass. @Serdeable enables generated JSON serialization, while Valid, NotBlank, and Positive apply Micronaut Validation to the request body. The HTTP operations remain module-level functions. Valid enables validation for the request body, so an explicit @Validated declaration is not needed. This example does not require reflection or a Pydantic model.

The development server reloads the application automatically. Verify the new PUT operation:

curl -X PUT http://localhost:8080/items/5 \
  -H 'Content-Type: application/json' \
  -d '{"name":"Foo","price":42.0,"is_offer":true}'

The response is:

{"item_name":"Foo","item_id":5}

The Swagger UI and ReDoc pages now include the request body and its validation constraints. Verify validation with an invalid body:

curl -i -X PUT http://localhost:8080/items/5 \
  -H 'Content-Type: application/json' \
  -d '{"name":"","price":-1}'

The response begins:

HTTP/1.1 400 Bad Request

Test the application

Create test_main.py next to main.py:

from typing import Annotated

import requests

from jakarta.inject import Inject
from micronaut.context import ApplicationContext
from micronaut.test.extensions.junit5.annotation import MicronautTest
from pyronaut.build import Dependency


Dependency(
    group="io.micronaut.pyronaut",
    module="micronaut-pyronaut-requests",
    scope=Dependency.Scope.TEST,
)


MicronautTest()

context: Annotated[ApplicationContext, Inject]

def client():
    return requests.with_context(context)

def test_root():
    response = client().get("/")
    assert response.json() == {"Hello": "World"}

def test_read_item():
    response = client().get("/items/5", params={"q": "somequery"})
    assert response.json() == {
        "item_id": 5,
        "q": "somequery",
    }

def test_update_item():
    response = client().put(
        "/items/5",
        json={"name": "Foo", "price": 42.0, "is_offer": True},
    )
    assert response.json() == {
        "item_name": "Foo",
        "item_id": 5,
    }

def test_item_validation():
    response = client().put(
        "/items/5",
        json={"name": "", "price": -1},
    )
    assert response.status_code == 400

Run the application and test sources together:

pyronaut test main.py -- test_main.py

MicronautTest() starts and stops an embedded server for the generated JUnit 5 test module. requests.with_context accepts the injected ApplicationContext and provides a requests-compatible client backed by the Micronaut HTTP client. The test covers the root response, path and query binding, a valid request body, and a validation failure. Functions whose names start with test become JUnit 5 test methods automatically. You do not need a top-level test class, an @Test decorator, a self parameter, or a return annotation. Injected values are available through module-level attributes. The development server does not need to run separately.

Run the application

Run the same source file with pyronaut run:

pyronaut run main.py

Pyronaut processes and runs the source directly. This direct-source workflow does not require a separate application server.

Summary

With standard Python type hints and Pyronaut decorators, the application provides:

  • Request definitions that use standard Python type hints and dataclasses.

  • Automatic OpenAPI generation with Swagger UI and ReDoc.

  • Development-time reloads with pyronaut dev.

  • Standalone HTTP integration tests with MicronautTest() and pyronaut test.

Declare the types once and reuse them for HTTP binding, validation, serialization, documentation, and tests.

5 How Pyronaut Works

Pyronaut connects Python code to the Micronaut framework through decorators. This section explains how the decorators map to Micronaut annotations, what the pyronaut command does with your source before it runs, and which runtime features the Pyronaut SDK includes for you.

Use Micronaut annotations as decorators

Micronaut uses annotations such as @Controller, @Get, @Singleton, and @Value. Pyronaut exposes these annotations as Python decorators. Import them from the Java package with the leading io. removed:

from micronaut.http.annotation import Get


@Get(value="/", produces="text/plain")
def index() -> str:
    return "Hello from Pyronaut"

Pyronaut omits the io. prefix because io is a Python standard-library module and a package cannot shadow it. When the Micronaut API reference lists io.micronaut.http.annotation.Get, import it as micronaut.http.annotation.Get. Packages that do not start with io.micronaut keep their original names, such as jakarta.inject.Singleton and jakarta.validation.constraints.NotBlank.

Pass annotation members as keyword arguments, for example @Get(value="/", produces="text/plain"), or pass a single positional argument for the value member, as in @Get("/"). A decorator on a Python class corresponds to a type-level annotation. A decorator on a function or method corresponds to a method-level annotation.

Use typing.Annotated for annotations that Java applies to fields or parameters. It keeps the type hint and annotation together:

from typing import Annotated

from jakarta.validation.constraints import NotBlank, Size
from micronaut.http.annotation import Body


def save(name: Annotated[str, NotBlank, Size(min=1, max=30)], payload: Annotated[Item, Body]) -> Item:
    ...

A bare name inside Annotated, such as NotBlank, applies the annotation with its default values. Call the annotation to pass members.

Names that clash with Python keywords

Some Java members and methods use names that Python reserves as keywords. Append an underscore to the Python name, and Pyronaut maps it back to the Java name:

from micronaut.http.annotation import Error


@Error(global_=True)          # Java member: global
def handle(request, error):
    ...

The same rule applies to packages and methods. For example, use micronaut.core.async_.annotation for io.micronaut.core.async.annotation and Flux.from_(publisher) for Flux.from.

Using Java classes directly

Import any Java class on the classpath with a normal import statement. This works for classes from Micronaut, the JDK, and libraries declared in pyproject.toml:

from java.time import Duration
from org.apache.commons.lang3 import StringUtils

print(StringUtils.capitalize("hello"))
timeout = Duration.ofSeconds(5)

java.type("org.apache.commons.lang3.StringUtils") is an equivalent way to obtain the same class. The Micronaut examples use it for reactive types such as Mono and Publisher. It is also useful when a Java package name would shadow a Python module.

Use Java objects from Python by calling Java-named methods such as response.getHeaders(), indexing Java lists and maps, and iterating over Java collections. Python str, int, float, bool, list, dict, datetime, and uuid.UUID values convert to matching Java types when passed to Java code. See Using Python Packages and Java Libraries to declare dependencies.

What happens during processing

When you run pyronaut dev, pyronaut run, or pyronaut test, the CLI first runs pyronaut process. Processing reads your Python sources and passes decorators, type hints, dataclasses, and abstract classes to the Micronaut compiler. The compiler generates Java classes and metadata for:

  • Bean definitions describing how to construct each @Singleton, @Controller or @Factory and which dependencies to inject.

  • Route metadata for every HTTP method decorator, including how to bind each parameter.

  • Serializers and deserializers for @Serdeable dataclasses.

  • Validation metadata for jakarta.validation constraints.

  • Bridge code that lets Java call your Python functions and lets Python receive Java objects.

  • An OpenAPI description of the routes.

Pyronaut writes processed output to pyronaut/classes. When no processing input has changed, it reuses the complete output. By default, a changed input triggers a clean compilation; optional incremental processing can retain unaffected output and process a smaller source set. Processing can report source and generated-metadata errors before the server starts. The processor must be able to see decorators statically; see Incremental processing for the constructs it can and cannot follow.

To see how processing handles serialization and validation, define a data class:

Writing serializable data classes
from dataclasses import dataclass
from typing import Annotated

from com.fasterxml.jackson.annotation import JsonProperty
from jakarta.validation.constraints import NotBlank, Pattern, Size
from micronaut.serde.annotation import Serdeable


@Serdeable                                                   (1)
@dataclass
class Person:
    name: Annotated[str, NotBlank, Size(min=1, max=30)]      (2)

    telephone: Annotated[str | None, Pattern(regexp=r"\d{10}")] = None

6 Micronaut Concepts for Python Developers

Micronaut has its own vocabulary. Words such as bean, dependency injection, configuration injection and AOP appear throughout the Micronaut documentation and in Pyronaut error messages. None of them are difficult, but they are rarely used in the Python web ecosystem, so this chapter explains each one from the point of view of a developer who already knows Flask or FastAPI.

A quick vocabulary

Micronaut term What it means for a Python developer

Bean

An object whose creation and lifetime Micronaut manages instead of your code. You declare a bean by decorating a class with @Singleton (or another scope) and never call its constructor yourself.

Application context

The container that creates beans, wires them together, reads configuration and starts the HTTP server. pyronaut dev and pyronaut run create one for you. In tests you interact with it through MicronautTest.

Dependency injection (DI)

Micronaut looks at the type hints of a bean’s init parameters (or of Annotated[…​, Inject] attributes) and passes in the matching beans automatically. It replaces module-level globals and FastAPI’s Depends().

Scope

How long a bean lives. @Singleton means one instance per application; @Prototype means a new instance every time it is injected; @RequestScope means one instance per HTTP request.

Qualifier

A label such as @Named("v8") used to pick one bean when several beans implement the same interface.

Configuration property

A value read from application.toml, an environment variable or the command line. Configuration injection delivers these values to your beans as typed Python attributes.

Aspect-oriented programming (AOP)

Behaviour that wraps a method call, such as retrying on failure, validating arguments or running the method on another thread. Pyronaut expresses this behaviour with decorators like @Retryable, @Validated and @ExecuteOn.

Executor

A named thread pool. Pyronaut decides which executor runs each request based on whether your function is def or async def and on decorators such as @ExecuteOn.

Publisher, Mono, Flux, CompletionStage

Java’s asynchronous result types. You can await them from async def Python code; see Threading, blocking work, and asyncio.

Processing happens before startup

The most important difference between Pyronaut and a framework like FastAPI is when Pyronaut interprets decorators.

FastAPI reads your decorators and type hints while the process starts and builds its routing table in memory. Pyronaut reads them during pyronaut process, which runs automatically before pyronaut dev, pyronaut run, and pyronaut test. During processing, Pyronaut generates Micronaut route and bean metadata, dataclass serializers, and validation metadata.

This has two practical consequences:

  • Pyronaut can report source and generated-metadata errors before the application starts, not when the first request arrives. Enable dependency injection validation when you also want pyronaut validate-config to check the bean graph.

  • Declare decorators in a form the processor can see. Applying a decorator dynamically (for example inside a function or from a string name) does not work; see Incremental processing for the constructs the processor understands.

The rest of this chapter walks through each concept in turn.

6.1 Dependency Injection

Dependency injection is how Pyronaut connects the pieces of your application through Micronaut’s application model. If you have used FastAPI’s Depends() or kept a database connection in a Flask module-level global, you have already worked with the problem it solves. The processor generates metadata that resolves dependencies for both Python and Java code.

The problem dependency injection solves

Consider a service that needs a database client:

class BookService:
    def __init__(self):
        self.db = DatabaseClient(url=os.environ["DATABASE_URL"])

The class creates its own dependency. That makes it hard to test (you cannot substitute a fake client), hard to configure (the URL is read from a specific place) and hard to share (every BookService() call creates a new connection).

With dependency injection the class only declares what it needs:

from jakarta.inject import Singleton


@Singleton
class BookService:
    def __init__(self, db: DatabaseClient):
        self.db = db

The application context creates DatabaseClient once, passes it to BookService, and passes BookService to any controller that asks for it. Nothing calls BookService() directly.

Declaring a bean

A bean is any class decorated with a scope. The most common scope is @Singleton from the jakarta.inject package, which means "create exactly one instance for the whole application":

from jakarta.inject import Singleton


@Singleton
class GreetingService:
    def greet(self, name: str) -> str:
        return f"Hello, {name}!"

Beans are ordinary Python classes. You can write methods, keep state, use dataclasses and define properties as usual. The decorator only tells the application context that it should manage the instance.

Controllers, HTTP clients, event listeners, and scheduled jobs are all beans. In most applications, @Singleton is the only scope you need for them.

Receiving dependencies

There are three ways to receive a dependency: constructor injection, attribute injection, and method injection. All of them rely on the type hint to decide what to inject, so the hint must be a class that Micronaut knows about.

Injection mode Use when Trade-off

Constructor injection

Dependencies are required.

Explicit and easy to test.

Attribute injection

A module-level route has no constructor.

Convenient, but less visible.

Method injection

A dependency is optional or supplied after construction.

Flexible, but splits initialisation.

The examples below show each mode.

Constructor injection (recommended)

Pass required dependencies as init parameters:

from jakarta.inject import Singleton
from micronaut.http.annotation import Controller, Get


@Controller("/greet")
class GreetingController:
    def __init__(self, service: GreetingService):
        self.service = service

    @Get("/{name}")
    def greet(self, name: str) -> str:
        return self.service.greet(name)

Attribute injection

Annotate a class attribute with Inject:

from typing import Annotated

from jakarta.inject import Inject
from micronaut.http.annotation import Get

service: Annotated[GreetingService, Inject]


@Get("/greet/{name}")
def greet(name: str) -> str:
    return service.greet(name)

Class attributes work too:

@Singleton
class Vehicle:
    engine: Annotated[Engine, Inject]

    def start(self) -> str:
        return self.engine.start()

Method injection

Use @Inject on a method for post-construction injection:

@Singleton
class Vehicle:
    def __init__(self):
        self.engine = None

    @Inject
    def initialize(self, engine: Engine):
        self.engine = engine

Interfaces and implementations

Python’s abc.ABC plays the role of a Java interface. Declare the abstract class without a scope and put the scope on the implementation. Anything that asks for the abstract type receives the implementation:

from abc import ABC, abstractmethod

from jakarta.inject import Singleton


class Engine(ABC):
    @abstractmethod
    def start(self) -> str:
        ...


@Singleton
class V8Engine(Engine):
    def start(self) -> str:
        return "Starting V8"


@Singleton
class Vehicle:
    def __init__(self, engine: Engine):   # receives the V8Engine bean
        self.engine = engine

This is the main technique for swapping implementations between environments, for example a real payment gateway in production and a fake one in tests.

Choosing between several implementations

If two beans implement the same interface, Micronaut cannot choose between them. Resolving the dependency then fails with a message that lists the candidates. Use a qualifier to choose:

from typing import Annotated

from jakarta.inject import Named, Singleton


@Singleton
@Named("v8")
class V8Engine(Engine):
    ...


@Singleton
@Named("v6")
class V6Engine(Engine):
    ...


@Singleton
class Vehicle:
    def __init__(self, engine: Annotated[Engine, Named("v8")]):
        self.engine = engine

Alternatively mark one implementation with @Primary (from micronaut.context.annotation) so Micronaut chooses it whenever you do not provide a qualifier. You can also inject list[Engine] to receive every implementation.

Optional dependencies

A dependency typed as Engine | None receives None when no bean of that type exists instead of failing:

@Singleton
class Vehicle:
    def __init__(self, engine: Engine | None):
        self.engine = engine if engine is not None else DefaultEngine()

Creating beans from objects you do not own

Sometimes a library supplies the object you want to inject and you cannot decorate it, for example a Java HTTP client, a connection pool or a Python object built from configuration. A factory is a bean whose methods produce other beans:

from jakarta.inject import Singleton
from micronaut.context.annotation import Factory


@Factory
class ClientFactory:
    @Singleton
    def stock_client(self, config: StockConfig) -> StockClient:
        return StockClient(base_url=config.url, timeout=config.timeout)

The return type hint (StockClient) becomes the injectable type. Factory methods can themselves receive dependencies as parameters, exactly like constructors.

Scopes

The scope decorator controls how many instances exist and how long they live:

Scope Behaviour

@Singleton (jakarta.inject)

Micronaut creates one instance per application, lazily the first time an application needs it. Use this for services, repositories, clients and controllers.

@Prototype (micronaut.context.annotation)

Micronaut creates a new instance every time the application injects or looks up the bean.

@Context (micronaut.context.annotation)

Like @Singleton, but Micronaut creates it eagerly when the application starts. Useful for beans that validate configuration at startup.

@RequestScope (micronaut.runtime.http.scope)

One instance per HTTP request; Micronaut destroys it when the response is sent.

Module-level route files that declare no scope receive an automatic pooled scope so that Python code can run on several GraalPy contexts; see The GIL and the Context Pool.

Conditional beans

@Requires from micronaut.context.annotation makes a bean exist only when a condition holds. Common conditions are the presence of a configuration property, of another bean or of a class on the classpath:

from jakarta.inject import Singleton
from micronaut.context.annotation import Requires
from javax.sql import DataSource


@Singleton
@Requires(beans=DataSource)
@Requires(property="datasource.url")
class JdbcBookService(BookService):
    def __init__(self, data_source: DataSource):
        self.data_source = data_source

@Requires(env="test") restricts a bean to an environment; see Configuration Injection for how Micronaut selects environments.

Reference material

Lifecycle hooks

Two decorators from jakarta.annotation let a bean run code after Micronaut constructs it and before Micronaut destroys it. They replace FastAPI’s startup and shutdown events for resources that belong to one bean:

from jakarta.annotation import PostConstruct, PreDestroy
from jakarta.inject import Singleton


@Singleton
class ConnectionPool:
    def __init__(self, config: PoolConfig):
        self.config = config
        self.pool = None

    @PostConstruct
    def open(self):
        self.pool = create_pool(self.config.url)

    @PreDestroy
    def close(self):
        self.pool.close()

@PostConstruct runs after Micronaut supplies every injected dependency. Use it instead of init for work that depends on injected beans.

Replacing beans in tests

@Replaces swaps one bean for another. Combined with @Requires(env="test") it is the idiomatic way to substitute a fake implementation during tests without touching production code:

from jakarta.inject import Singleton
from micronaut.context.annotation import Replaces, Requires


@Singleton
@Requires(env="test")
@Replaces(JdbcBookService)
class InMemoryBookService(BookService):
    books: dict[str, Book] = {}

    def find_book(self, title: str) -> Book | None:
        return self.books.get(title)

Application events

Beans can publish and listen to events. Micronaut publishes StartupEvent and ShutdownEvent itself, which replaces FastAPI’s @app.on_event("startup") and Flask’s before_first_request:

from jakarta.inject import Singleton
from micronaut.context.event import StartupEvent, ShutdownEvent
from micronaut.runtime.event.annotation import EventListener


@Singleton
class Warmup:
    @EventListener
    def on_startup(self, event: StartupEvent) -> None:
        print("application started")

    @EventListener
    def on_shutdown(self, event: ShutdownEvent) -> None:
        print("application stopping")

To publish your own events, define a dataclass for the event and inject ApplicationEventPublisher[YourEvent]:

from dataclasses import dataclass
from typing import Annotated

from jakarta.inject import Inject, Singleton
from micronaut.context.event import ApplicationEventPublisher


@dataclass
class OrderPlaced:
    order_id: int


@Singleton
class OrderService:
    events: Annotated[ApplicationEventPublisher[OrderPlaced], Inject]

    def place(self, order_id: int) -> None:
        self.events.publishEvent(OrderPlaced(order_id))

Add @Async from micronaut.scheduling.annotation to a listener method to run it on a background thread instead of blocking the publisher.

Looking beans up manually

Prefer injection, but you can also ask the application context for a bean. In pytest this is what the MicronautTest fixture wrapper does when you index it:

def test_greeting(my_context):
    service = my_context[GreetingService]
    assert service.greet("Ada") == "Hello, Ada!"

See Using MicronautTest for the fixture and Testing for injecting beans directly into JUnit-style test modules.

6.2 Configuration Injection

Python applications usually read configuration from os.environ, a .env file or a pydantic-settings model. Pyronaut uses Micronaut’s configuration model: it reads configuration from many sources with a defined priority, converts it to the types your code declares, can validate it at startup and injects it into beans.

Where configuration comes from

Pyronaut merges configuration from several sources. Later entries in this list override earlier ones:

  1. config/application.toml (or .yml, .properties, .json) on the classpath.

  2. Environment-specific files such as config/application-dev.toml and config/application-test.toml. Which ones apply depends on the active environments (see below).

  3. Environment variables, using upper-case with underscores: MICRONAUT_SERVER_PORT=9090 sets micronaut.server.port.

  4. Java system properties passed with -D, and --property key=value arguments for direct-source runs.

Every property has a dotted name such as micronaut.server.port. In TOML the dots become tables:

[micronaut.application]
name = "bookstore"

[micronaut.server]
port = 8080

[bookstore.catalog]
url = "https://catalog.example.com"
timeout = "5s"
page-size = 50

The configuration binder normalises key styles, so page-size, pageSize and PAGE_SIZE all refer to the same property. Prefer kebab-case in files and upper snake case in environment variables.

After pyronaut install, config/application.toml carries a JSON schema directive. Editors that understand TOML schemas (VS Code with the Even Better TOML extension, PyCharm) then autocomplete Micronaut property names and flag typos. pyronaut validate-config performs the same check from the command line; see Configuration validation.

Environments

An environment is a named profile such as dev, test or production. Pyronaut activates environments from the MICRONAUT_ENVIRONMENTS environment variable or the micronaut.environments property, and detects some automatically (for example test during pyronaut test). For each active environment, Pyronaut loads application-<env>.toml on top of application.toml.

This replaces the common Python pattern of if os.environ.get("ENV") == "production":. Keep shared settings in application.toml and only the differences in the environment files.

Injecting single values

@Value injects one property into an attribute or a constructor parameter. The ${name:default} syntax provides a fallback:

from typing import Annotated

from jakarta.inject import Singleton
from micronaut.context.annotation import Value


@Singleton
class CatalogClient:
    url: Annotated[str, Value("${bookstore.catalog.url}")]
    page_size: Annotated[int, Value("${bookstore.catalog.page-size:20}")]

The configuration binder converts the raw string to the declared type, so page_size is an int. Durations such as "5s" convert to java.time.Duration, and comma-separated values convert to list[str].

@Property(name="…​") does the same without the placeholder syntax and is slightly clearer when no default is needed:

from micronaut.context.annotation import Property


@Singleton
class CatalogClient:
    url: Annotated[str, Property(name="bookstore.catalog.url")]

Configuration classes

Injecting values one at a time does not scale. @ConfigurationProperties binds an entire prefix to a class, the way a pydantic-settings model binds environment variables. Each attribute maps to a property under the prefix, type hints drive conversion and the configuration binder enforces jakarta.validation constraints when it creates the bean:

from typing import Annotated

from jakarta.validation.constraints import Min, NotBlank
from micronaut.context.annotation import ConfigurationProperties


@ConfigurationProperties("bookstore.catalog")
class CatalogConfig:
    url: Annotated[str, NotBlank]
    timeout: str = "5s"
    page_size: Annotated[int, Min(1)] = 20

Configuration classes are beans, so any other bean can receive one through its constructor:

@Singleton
class CatalogClient:
    def __init__(self, config: CatalogConfig):
        self.config = config

Nested classes map to nested tables:

@ConfigurationProperties("bookstore")
class BookstoreConfig:
    @ConfigurationProperties("catalog")
    class Catalog:
        url: str | None = None

    name: str = "Bookstore"
    catalog: Catalog = Catalog()
[bookstore]
name = "My Bookstore"

[bookstore.catalog]
url = "https://catalog.example.com"

Immutable configuration

A frozen dataclass produces an immutable configuration bean. The configuration binder passes the bound values to the generated constructor:

from dataclasses import dataclass
from typing import Annotated

from jakarta.validation.constraints import NotNull
from micronaut.context.annotation import ConfigurationProperties


@ConfigurationProperties("vat")
@dataclass(frozen=True)
class ValueAddedTaxConfiguration:
    percentage: Annotated[float, NotNull]

Validating at startup

The application context checks constraints on a configuration class when it first creates the bean. Add @Context from micronaut.context.annotation to a configuration class to create it eagerly, so an invalid deployment fails immediately at startup rather than on the first request that touches it.

Repeated configuration

@EachProperty creates one bean per entry under a prefix. It is the Micronaut equivalent of a dictionary of settings, for example several named data sources:

[datasources.primary]
url = "jdbc:postgresql://db1/app"

[datasources.reporting]
url = "jdbc:postgresql://db2/app"
from typing import Annotated

from micronaut.context.annotation import EachProperty, Parameter


@EachProperty("datasources")
class DataSourceConfig:
    url: str | None = None

    def __init__(self, name: Annotated[str, Parameter]):
        self.name = name   # "primary" or "reporting"

Injecting list[DataSourceConfig] returns every entry, and Annotated[DataSourceConfig, Named("reporting")] selects one.

Conditional beans and configuration

@Requires from Dependency Injection reads configuration too. Use it to enable optional features:

@Singleton
@Requires(property="bookstore.cache.enabled", value="true")
class CachingCatalogClient(CatalogClient):
    ...

Configuration in tests

6.3 Aspect-Oriented Programming (AOP)

Aspect-oriented programming (AOP) describes a familiar Python pattern: a decorator wraps a function to add behaviour such as logging, retrying, caching, or timing. Pyronaut exposes many of Micronaut’s decorators and lets you write your own so they work with dependency injection.

AOP compared with Python decorators

A plain Python decorator replaces the function object at import time:

def retry(func):
    def wrapper(*args, **kwargs):
        for attempt in range(3):
            try:
                return func(*args, **kwargs)
            except Exception:
                if attempt == 2:
                    raise
    return wrapper

A Micronaut advice decorator does not change the function. The processor records metadata that Micronaut uses to generate a proxy class during processing. At runtime, the application context creates the proxy bean; the proxy intercepts calls to the decorated method and hands them to an interceptor, an ordinary bean that can receive its own dependencies. The important consequences are:

  • Advice only applies to beans obtained through dependency injection. If you call BookService() yourself, none of the decorators below have any effect.

  • Configure interceptors through application.toml; they can use other beans, which is hard to do with a closure-based decorator.

  • The same decorator works on Python and Java beans.

Common advice

The following decorators are built in and require no code from you:

Decorator Effect

@Validated (micronaut.validation) with jakarta.validation constraints

Validates method arguments before the method runs and raises a ConstraintViolationException (a 400 Bad Request in controllers). Module-level routes enable validation automatically when a constraint is present.

@Retryable and @CircuitBreaker (micronaut.retry.annotation)

Retry a failing call with configurable attempts and delay, optionally opening a circuit after repeated failures.

@Scheduled (micronaut.scheduling.annotation)

Run the method on a fixed rate, fixed delay or cron schedule. Replaces Celery beat or APScheduler for in-process jobs.

@Async (micronaut.scheduling.annotation)

Run the method on a background executor and return immediately. Replaces FastAPI’s BackgroundTasks for fire-and-forget work.

@ExecuteOn (micronaut.scheduling.annotation)

Run the method on a named thread pool. See Running Blocking Code.

@Cacheable, @CachePut, @CacheInvalidate (micronaut.cache.annotation)

Cache the return value keyed by the arguments. Requires a cache implementation such as io.micronaut.cache:micronaut-cache-caffeine in [tool.pyronaut.dependencies].runtime.

@Transactional (jakarta.transaction)

Wrap the method in a database transaction when using Micronaut Data.

@Client (micronaut.http.client.annotation)

Turn an abstract class into an HTTP client. Micronaut implements its declared client methods. See Building HTTP APIs.

For example, a retrying service needs only a decorator:

from jakarta.inject import Singleton
from micronaut.retry.annotation import Retryable


@Singleton
class CatalogClient:
    @Retryable(attempts="5", delay="2s")
    def find_book(self, isbn: str) -> Book:
        ...

Annotation members accept configuration placeholders, so you can tune the retry policy without changing code:

@Retryable(attempts="${catalog.retry.attempts:3}", delay="${catalog.retry.delay:1s}")
def find_book(self, isbn: str) -> Book:
    ...

A scheduled job is a bean with a decorated method:

from jakarta.inject import Singleton
from micronaut.scheduling.annotation import Scheduled


@Singleton
class ReportJob:
    @Scheduled(fixedRate="10m", initialDelay="1m")
    def generate(self) -> None:
        print("generating report")

    @Scheduled(cron="0 15 10 ? * MON")
    def weekly(self) -> None:
        print("it is Monday")
Annotation member names keep their Java spelling (fixedRate, not fixed_rate). Members that clash with Python keywords take a trailing underscore, for example @Error(global_=True).

Writing your own advice

Custom advice has two parts: a decorator that marks the methods to intercept, and an interceptor bean that implements the behaviour.

First define the decorator. It is a plain function that returns its argument unchanged; the @Around decorator tells Micronaut it is an AOP marker and @Executable makes the target methods callable through the proxy:

from micronaut.aop import Around
from micronaut.context.annotation import Executable


@Executable
@Around
def Timed(func):
    return func

Then implement a MethodInterceptor bound to the decorator. context.proceed() calls the original method:

import java
import time

from micronaut.aop import InterceptorBean, MethodInvocationContext

from .Timed import Timed

MethodInterceptor = java.type("io.micronaut.aop.MethodInterceptor")


@InterceptorBean(Timed)
class TimedInterceptor(MethodInterceptor):
    def intercept(self, context: MethodInvocationContext):
        started = time.perf_counter()
        try:
            return context.proceed()
        finally:
            elapsed = time.perf_counter() - started
            print(f"{context.getMethodName()} took {elapsed:.3f}s")

Finally apply the decorator to any bean method:

from jakarta.inject import Singleton

from .Timed import Timed


@Singleton
class BookService:
    @Timed
    def list_books(self) -> list[Book]:
        ...

The interceptor is a bean, so it can receive dependencies through its constructor, for example a metrics registry. MethodInvocationContext exposes the target object, method name, argument values and return type; see the API reference.

Introduction advice

Around advice wraps an existing implementation. Introduction advice supplies the implementation of an abstract method. @Client is the best-known example: you declare an abstract class describing the remote API and the processor generates the code that performs the HTTP calls. Micronaut Data repositories work the same way. Writing your own introduction advice is rarely necessary; the Micronaut guide shows how.

6.4 Building HTTP APIs

Pyronaut applications expose HTTP APIs with the same decorators Micronaut uses in Java, while the Python code looks familiar to FastAPI users: functions with type hints, path variables in braces, and dataclasses for request and response bodies. This section covers the common patterns and their Flask and FastAPI equivalents.

Routes

A route is a function decorated with an HTTP method decorator from micronaut.http.annotation. The decorators are @Get, @Post, @Put, @Patch, @Delete, @Head and @Options. Routes can live at module level, which is the quickest way to start, or inside a @Controller class, which groups related routes under a common prefix and lets them share injected dependencies:

from micronaut.http.annotation import Controller, Get, Post


@Controller("/books")
class BookController:
    def __init__(self, service: BookService):
        self.service = service

    @Get("/")
    def list_books(self) -> list[Book]:
        return self.service.list()

    @Get("/{isbn}")
    def get_book(self, isbn: str) -> Book | None:
        return self.service.find(isbn)

A module with routes but no @Controller receives an implicit controller mounted at /. Call Controller("/prefix") at module level to change the prefix without introducing a class.

Path variables use {name} in the route and a parameter of the same name in the function. The parameter’s type hint drives conversion, so item_id: int rejects non-numeric values with 400 Bad Request.

Binding request data

Micronaut binds function parameters from the request using the parameter name, the type hint and an optional decorator inside typing.Annotated:

Parameter Bound from

item_id: int with {item_id} in the route

The path variable.

q: str | None = None

The query parameter q. Parameters that are not path variables bind from the query string; a default value makes them optional.

Annotated[str, QueryValue("page-size")]

A query parameter whose name differs from the Python name.

Annotated[str, Header("X-Request-Id")]

A request header. Annotated[str, Header] infers the header name from the parameter name.

Annotated[str, CookieValue("session")]

A cookie.

Annotated[Item, Body]

The request body, decoded from JSON into the dataclass. Annotated[str, Body] receives the raw text.

from micronaut.http import HttpRequest, HttpResponse, HttpStatus

class BookNotFound(Exception):

@Controller("/books")

    @Get("/{isbn}")
    def get_book(self, isbn: str) -> Book:
        raise BookNotFound(isbn)

    @Error(status=HttpStatus.NOT_FOUND)
    def on_404(self, request: HttpRequest) -> HttpResponse:
        return HttpResponse.notFound().body(JsonError("Nothing here"))

6.5 Threading, Blocking Work, and asyncio

Python web developers already know two execution models: WSGI frameworks such as Flask run every request on its own thread, while ASGI frameworks such as FastAPI run async def handlers on an event loop and push plain def handlers to a thread pool. Pyronaut combines both models on top of Micronaut’s Netty-based server, and adds a third element that has no equivalent in CPython: the ability to run Python code in several interpreter contexts at once.

This section explains:

  • The Threading Model: which thread runs each kind of Python function and why.

  • Running Blocking Code: how to keep slow operations away from the event loop.

  • Using async/await: which asyncio features work inside a Pyronaut application.

  • Awaiting Reactive and Java Async Types: how Python coroutines interact with Micronaut’s CompletionStage, Publisher, Mono, and Flux types.

  • The GIL and the Context Pool: how GraalPy’s interpreter lock affects throughput and how to configure the pool of Python contexts.

The short version: write def routes for ordinary code, write async def routes when you want to await other services concurrently, and never call blocking code from an async def function without run_in_executor. If you follow those three rules, the defaults Pyronaut applies will serve most applications well.

6.5.1 The Threading Model

Micronaut’s HTTP server is built on Netty. Netty uses a small number of event loop threads, typically two per CPU core, and each thread serves many connections by reacting to I/O events. Blocking one of these threads stalls every connection assigned to it, so the whole design revolves around one question: where does application code run?

The thread and executor model

Pyronaut selects where Python code runs from the function signature and any executor annotation:

Thread, executor, or function Runs on or uses Behavior

Netty event loop

The request’s event loop thread

Reads requests, writes responses, and runs non-blocking code. There are few event loop threads, so they must never block.

def route or bean method

The io executor

Pyronaut routes every synchronous Python method here automatically. The executor uses an unbounded pool of platform threads, creating them on demand and reusing idle ones.

async def route or bean method

The Netty event loop

The coroutine runs on a Micronaut-managed asyncio loop; await suspends it and frees the thread. Await non-blocking operations or move blocking work to run_in_executor (see Running Blocking Code).

Method decorated with @ExecuteOn(TaskExecutors.BLOCKING)

The blocking executor

Runs explicitly selected work on a separate platform-thread pool. Pyronaut uses platform threads because GraalPy cannot run Python code on virtual threads.

Method decorated with @ExecuteOn("my-pool")

The custom executor my-pool

Uses the executor configured under micronaut.executors.

Method returning a Publisher, Mono or CompletionStage

The event loop subscribes; the producer chooses its thread

Micronaut writes the response when the value arrives. The code that produces the value decides which thread does the work.

Pyronaut executor defaults

Pyronaut sets low-priority defaults so that both executors use cached platform threads:

[micronaut.executors.io]
type = "cached"
virtual = false

[micronaut.executors.blocking]
type = "cached"
virtual = false

Anything you put in application.toml overrides these values. For example, to bound the number of concurrent database calls to match a connection pool of 20 connections:

[micronaut.executors.io]
type = "fixed"
n-threads = 20
Never set virtual = true for an executor that runs Python code. GraalPy does not support executing Python on Java virtual threads and the application will fail at runtime.

See the Configuring Server Thread Pools section of the Micronaut guide for executor types and options.

6.5.2 Running Blocking Code

Blocking code is any code that makes the current thread wait: a database query, a synchronous HTTP call, reading a large file, time.sleep() or CPU-heavy computation. The rules for handling it depend on the kind of function you are in.

Situation Choose Why

Blocking work in a def route or bean method

Keep it synchronous

It already runs on the io executor.

Slow work that needs its own pool

@ExecuteOn(TaskExecutors.BLOCKING) or @ExecuteOn("my-pool")

Isolates the work from the shared io executor.

Blocking work in an async def route

await loop.run_in_executor(None, …​)

Moves the call off the event loop and uses Micronaut’s blocking executor.

Work that should start and return immediately

@Async

Submits the method to the scheduled executor.

Manually created threads

Prefer Micronaut executors

They are configured, shut down, and monitored with the application.

In a def route

Synchronous Python routes already run on the io executor, so this is the usual choice for CRUD endpoints:

from micronaut.http.annotation import Controller, Get


@Controller("/books")
class BookController:
    def __init__(self, repository: BookRepository):
        self.repository = repository

    @Get("/{isbn}")
    def find(self, isbn: str) -> Book | None:
        return self.repository.findByIsbn(isbn)   # blocking JDBC call is fine here

Choosing a different pool with @ExecuteOn

Use @ExecuteOn from micronaut.scheduling.annotation to isolate slow work on the blocking executor or a custom pool:

from micronaut.http.annotation import Controller, Get
from micronaut.scheduling import TaskExecutors
from micronaut.scheduling.annotation import ExecuteOn


@Controller("/reports")
@ExecuteOn(TaskExecutors.BLOCKING)
class ReportController:
    @Get("/{year}")
    def yearly(self, year: int) -> Report:
        return build_report(year)   # slow, runs on the blocking executor

Declare custom executors in configuration and reference them by name:

[micronaut.executors.reports]
type = "fixed"
n-threads = 4
@ExecuteOn("reports")
def yearly(self, year: int) -> Report:
    ...

In Python code this is optional for synchronous methods, but useful for separating pools.

In an async def route: use run_in_executor

A coroutine runs on the event loop. Hand blocking calls to Micronaut’s blocking executor with loop.run_in_executor(None, …​) and await the result:

import asyncio

from micronaut.http.annotation import Get


@Get("/report")
async def report() -> Report:
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(None, build_report)

The None executor argument selects Micronaut’s blocking executor. Passing your own concurrent.futures.Executor is not supported and raises NotImplementedError. Pass arguments with functools.partial or a lambda:

from functools import partial

result = await loop.run_in_executor(None, partial(build_report, year=2026))

Background work with @Async

Decorate a bean method with @Async to start work and return immediately:

from jakarta.inject import Singleton
from micronaut.scheduling.annotation import Async


@Singleton
class Mailer:
    @Async
    def send_welcome(self, address: str) -> None:
        deliver(address)   # runs on a background thread

This is similar to FastAPI’s BackgroundTasks. Because the method runs on another bean, the call must go through dependency injection for the decorator to take effect.

Threads and threading

The standard threading module works on GraalPy, and threads created this way execute Python code subject to the interpreter lock described in The GIL and the Context Pool. Prefer Micronaut executors over creating threads by hand: they are sized through configuration, shut down with the application, and are visible to Micronaut’s metrics and management endpoints.

6.5.3 Using async/await

In Pyronaut, async def routes, clients, and bean methods use standard Python asyncio syntax. Pyronaut uses Micronaut’s event loop: each coroutine is bound to the Netty event loop handling the current request, and awaiting a Micronaut client call, a timer, or a supported network operation suspends the coroutine without holding a thread.

There is no asyncio.run() and no uvicorn. The event loop already exists when Pyronaut calls your function.

Writing an async route

Declare the route with async def and await whatever you need. The return type hint describes the awaited result, and Pyronaut exposes the method to Java as a CompletionStage:

import asyncio

from micronaut.http.annotation import Get


@Get("/slow-hello")
async def slow_hello() -> str:
    await asyncio.sleep(0.5)   # does not block the event loop
    return "hello"

The same works for controller methods and for methods of any @Singleton bean.

Async HTTP clients

When you declare a declarative client method as async def, it returns an awaitable. Combining an async route with an async client is the main reason to use coroutines: many outbound calls can be in flight while the event loop keeps serving other requests.

from abc import ABC, abstractmethod
from typing import Annotated

from jakarta.inject import Inject
from micronaut.http.annotation import Get
from micronaut.http.client.annotation import Client


@Client("https://api.example.com")
class BackendClient(ABC):
    @Get("/message")
    @abstractmethod
    async def message(self) -> str:
        ...


backend: Annotated[BackendClient, Inject]


@Get("/proxy-message")
async def proxy_message() -> str:
    return "proxied: " + await backend.message()

You can await the low-level HttpClient too. Inject it with a @Client qualifier and await exchange or retrieve:

import java
from typing import Annotated

from jakarta.inject import Inject
from micronaut.http import HttpRequest
from micronaut.http.annotation import Controller, Get
from micronaut.http.client import HttpClient
from micronaut.http.client.annotation import Client

String = java.type("java.lang.String")


@Controller("/demo")
class DemoController:
    http_client: Annotated[HttpClient, Inject, Client("/")]

    @Get("/exchange")
    async def exchange(self) -> str:
        response = await self.http_client.exchange(HttpRequest.GET("/backend/message"), String)
        return "exchange: " + response.body()

A failed await raises the Java exception itself, exactly as the blocking call does, so you handle it with except on the Java type, for example except HttpClientResponseException as e:. As with a blocking Java call, except Exception does not catch a Java exception; use the Java type, a Java superclass such as java.lang.RuntimeException, or BaseException.

Any CompletionStage (such as a CompletableFuture) or Reactive Streams Publisher returned by a Java call is awaitable. A publisher awaits to its first item, so await Mono.from_(publisher) and await Mono.from_(publisher).toFuture() both work.

Running work concurrently

asyncio.gather and asyncio.TaskGroup schedule several coroutines on the Pyronaut-managed loop and wait for all of them:

import asyncio

from micronaut.http.annotation import Get


@Get("/dashboard")
async def dashboard() -> dict:
    async with asyncio.TaskGroup() as group:
        orders = group.create_task(orders_client.recent())
        stock = group.create_task(stock_client.levels())
    return {"orders": orders.result(), "stock": stock.result()}

Cancellation, except* handling of ExceptionGroup, asyncio.wait_for timeouts and asyncio.shield behave as in CPython.

Supported asyncio APIs

The Pyronaut-managed loop implements the parts of asyncio that make sense inside a server:

  • asyncio.get_running_loop(), loop.create_future() and loop.create_task(…​)

  • loop.call_soon(…​), loop.call_soon_threadsafe(…​), loop.call_later(…​) and loop.call_at(…​)

  • asyncio.sleep(…​), asyncio.gather(…​), asyncio.TaskGroup and task cancellation

  • loop.run_in_executor(None, …​), which uses Pyronaut’s blocking executor

  • Networking: asyncio.open_connection, asyncio.start_server, loop.create_connection, loop.create_server, Unix-domain sockets, datagram endpoints and the sock_* helpers, all backed by Netty channels, with TLS for TCP and Unix-domain connections

The following are not implemented and fail immediately with NotImplementedError rather than silently blocking:

  • loop.run_forever() and loop.run_until_complete(…​) on Pyronaut-managed loops

  • run_in_executor with a custom executor

  • Eager task start (eager_start=True)

  • Python ssl.SSLContext objects. Use ssl=True or the Micronaut TLS mapping described in the Micronaut guide

  • sendfile and start_tls

  • add_reader, remove_reader, add_writer and remove_writer

  • subprocess_exec and subprocess_shell

Third-party async libraries that only rely on the supported primitives (timers, futures, open_connection) generally work. Libraries that need selector registration or their own event loop implementation do not.

Async event listeners and scheduled jobs

Coroutines are not limited to HTTP. Pyronaut exposes an async def method on any bean to Java as a CompletionStage, so Java code and other Micronaut modules can await it. Event listeners, scheduled jobs and message consumers can therefore use coroutines when they need to await other async APIs.

Graceful shutdown

Active coroutine bridges participate in Pyronaut’s graceful shutdown. With micronaut.lifecycle.graceful-shutdown.enabled = true, Pyronaut waits for in-flight Python coroutines up to the configured grace period before stopping the server.

Disabling the bridge

Pyronaut enables the asyncio bridge by default. You can switch it off; in that case async def methods remain valid Python, but Pyronaut executes them to completion on an executor instead of on the event loop:

[micronaut.python.asyncio]
enabled = false

The micronaut-context-python-netty module provides the Netty-backed event loop. The launchers used by pyronaut dev, pyronaut run and pyronaut test, and the artifacts pyronaut build produces, include it, so you do not need to declare a dependency.

Awaiting Java async values

Use the await behavior shown in the table. For example, an async client returning Mono can be awaited directly:

from micronaut.http.annotation import Get


@Get("/first-headline")
async def first_headline() -> str:
    headline = await headline_client.latest()   # client method returns Mono[Headline]
    return headline.title

@Get("/all-headlines")
async def all_headlines() -> list[str]:
    headlines = await headline_client.stream().collectList()
    return [h.title for h in headlines]

Returning reactive types from synchronous code

Return a reactive value from a plain def route to let Micronaut subscribe on the event loop. Because Java generic types are not visible to Python, declare single values with @SingleResult:

import java

from micronaut.core.async_.annotation import SingleResult
from micronaut.http.annotation import Controller, Get

Mono = java.type("reactor.core.publisher.Mono")
Publisher = java.type("org.reactivestreams.Publisher")


@Controller("/reactive")
class ReactiveController:
    @Get("/message")
    @SingleResult
    def message(self) -> Publisher[str]:
        return Mono.just("hello")

This example obtains Mono and Publisher with java.type(…​); from reactor.core.publisher import Mono is equivalent. The trailing underscore in micronaut.core.async_ and Flux.from_ avoids Python keyword collisions.

Streaming responses

Return a Publisher to stream items. Use MediaType.APPLICATION_JSON_STREAM for JSON documents or MediaType.TEXT_EVENT_STREAM for server-sent events:

import java

from micronaut.http import MediaType
from micronaut.http.annotation import Controller, Get
from micronaut.http.sse import Event

Duration = java.type("java.time.Duration")
Flux = java.type("reactor.core.publisher.Flux")
Publisher = java.type("org.reactivestreams.Publisher")


@Controller("/headlines")
class HeadlineController:
    @Get(value="/stream", processes=MediaType.APPLICATION_JSON_STREAM)
    def stream(self) -> Publisher[Headline]:
        return Flux.fromIterable([Headline("one"), Headline("two")]).delayElements(Duration.ofSeconds(1))

    @Get(value="/events", produces=MediaType.TEXT_EVENT_STREAM)
    def events(self) -> Publisher:
        return Flux.fromIterable([Event.of(Headline("one")), Event.of(Headline("two"))])

Reactive operators run on Reactor schedulers or the event loop, not Python threads. For blocking Python producers, wrap the call with Flux.fromCallable(…​) and schedule it on the injected io executor with subscribeOn(…​); see the Reactive HTTP Request Processing section.

Python coroutines seen from Java

The bridge works in both directions. An async def method on a Python bean appears to Java callers as a method returning CompletionStage<T>, so Java code can call .thenApply(…​) on it or a Java controller can return it. This lets a mixed project put its I/O orchestration in Python and its heavy lifting in Java, or the reverse, without either side knowing which language implemented the method.

6.5.5 The GIL and the Context Pool

GraalPy, like CPython, has a global interpreter lock (GIL). Only one thread can execute Python code in a given GraalPy context at a time. GraalPy releases the lock while calling Java or performing I/O, so a Python route that mostly waits on a JDBC query or HTTP call scales well. Two requests that both run Python bytecode in the same context take turns.

Unlike CPython, Pyronaut can create several GraalPy contexts inside one JVM, each with its own lock. Pooling contexts therefore gives true parallelism for Python code, at the cost of memory and of separate module state per context.

What the pool changes

When you enable the pool, Pyronaut instantiates beans with the @ContextPooled scope (the automatic scope of module-level route files that declare no other scope) once per context. A request borrows a context, runs the Python code there, and returns it. Two requests can execute Python bytecode at the same time as long as two contexts are free.

GraalPy shares compiled Python code between contexts where possible, but it does not share module globals. Each context imports your modules separately, so a module-level counter, cache or connection is per context, not per application. Put state that must be shared across requests in a @Singleton bean, which Pyronaut creates once regardless of the pool, or in an external store.

Context pooling, including the @ContextPooled scope, is experimental. Test pooled applications carefully if Python code relies on mutable module or global state.

Configuration

Configure the pool under micronaut.python.pool in application.toml:

[micronaut.python.pool]
enabled = true
size = 8
warn-wait = "2s"
enabled

Defaults to true.

size

The number of additional contexts. 0 selects the default of twice the number of available processors. The runtime creates contexts lazily, and each one costs memory and start-up work.

warn-wait

Log a warning when a request waits longer than this for a free context. Use it as the signal for tuning size.

For CPU-bound Python code, start with a size close to the number of processors and increase it only when the wait warnings show that requests are queuing. For I/O-heavy code a larger pool can raise throughput, but keep it bounded by the concurrency the downstream systems can sustain.

Disable the pool for applications that deliberately keep everything in one context, for example when a Python library holds process-wide state:

[micronaut.python.pool]
enabled = false

Interaction with executors

Contexts and threads are independent. The io executor can have fifty threads while the pool has eight contexts; at most eight of those threads execute Python code at any moment and the rest wait for a context or run Java code. Keep the two settings in proportion when tuning, and remember that the executors must stay on platform threads (virtual = false), because GraalPy cannot run on virtual threads.

The GIL and virtual-thread limitations are properties of the current GraalPy release. Revisit the pool recommendations if a future release changes either limitation. See the Python Threading section of the Micronaut guide for the current guidance and the full list of pool properties.

Create a GraalPy virtual environment

That pip can apply GraalPy-specific package patches and select compatible distributions. See Installing Python and Java Dependencies for the declarations Pyronaut reads.

To add a package without declaring it, use the environment’s pip directly:

.venv/bin/python -m pip install <package>

When a project contains .venv, Pyronaut automatically uses its Python executable and installed packages when launching the application and tests. Create the virtual environment with GraalPy; Pyronaut cannot use packages from a CPython-created virtual environment in its embedded GraalPy runtime.

Python package compatibility

Package compatibility depends on the GraalPy version, native extensions, threading, and deployment mode. Test the exact package versions and deployment mode used by your application.

Support for packages containing native extensions remains experimental. Native wheels that target CPython are not binary-compatible with GraalPy. Use a GraalPy-specific wheel for native extensions or build the extensions with GraalPy. See the GraalPy package compatibility checker and GraalPy reference documentation for current compatibility and native-extension guidance.

Pydantic 2 depends on pydantic-core, which is partially written in Rust and exposed to Python as native code. Because native-extension support remains experimental, test the exact Pydantic, GraalPy, and Pyronaut versions under the threading and deployment model your application uses. A passing compatibility-checker result covers only its tested configuration.

Optimise hot paths in Java

For CPU-bound work such as a tight parsing routine or numeric kernel, a Java implementation can run faster than Python. Add the Java class to the project’s Java source directory (src-java by default; see Pyronaut Toolchain and Project Layout) and make it a bean:

package bookstore;

import jakarta.inject.Singleton;

@Singleton
public class PriceCalculator {
    public double total(double[] prices, double taxRate) {
        double sum = 0;
        for (double price : prices) {
            sum += price;
        }
        return sum * (1 + taxRate);
    }
}

pyronaut process compiles Java and Python sources together, so Python code can inject the bean through its type hint:

from bookstore import PriceCalculator
from micronaut.http.annotation import Controller, Get


@Controller("/orders")
class OrderController:
    def __init__(self, calculator: PriceCalculator):
        self.calculator = calculator

    @Get("/{order_id}/total")
    def total(self, order_id: int) -> float:
        prices = load_prices(order_id)
        return self.calculator.total(prices, 0.2)

Python lists convert to Java arrays and collections automatically, and the Java class participates in the same dependency injection, configuration, and tests as the rest of the application. Java code can also inject Python beans and call async def methods as CompletionStage values (see Awaiting Reactive and Java Async Types). Java tests belong under test-java and run in the same pyronaut test invocation.

Use a Java library from Python

Declare Java dependencies by scope under [tool.pyronaut.dependencies]. For example, add Apache Commons Lang to the runtime classpath:

[tool.pyronaut]
repositories = ["mavenCentral"]

[tool.pyronaut.dependencies]
runtime = [
  "org.apache.commons:commons-lang3:3.20.0"
]

Resolve the dependency and refresh the generated Pyronaut project state:

pyronaut install

The library is now available through a normal Python import. Pyronaut resolves the imported Java type from the configured classpath:

from org.apache.commons.lang3 import StringUtils

message = StringUtils.capitalize("hello from java")

print(message)

Use group:artifact:version coordinates for libraries such as Apache Commons Lang that are not managed by the configured Micronaut BOMs. Micronaut dependencies managed by the Micronaut platform, Micronaut core, or Pyronaut BOMs can use versionless group:artifact coordinates.

For dependency scopes and install options, see Installing Python and Java Dependencies. See also Configuring pyproject.toml, Configuring Maven repositories, and Declaring direct source dependencies.

Extend Java classes and implement Java interfaces

A Python class defined at module level, or nested in another class, can extend a Java class or implement a Java interface from a library. The Pyronaut processor generates a Java class for it, so the class works the same way on the JVM, in the native pyronaut launchers, and in a native image. That includes classes in test sources and the application classes that pytest test modules import:

from com.rabbitmq.client import Channel
from jakarta.inject import Singleton
from micronaut.rabbitmq.connect import ChannelInitializer


@Singleton
class ChannelPoolListener(ChannelInitializer):

    def initialize(self, channel: Channel, name: str) -> None:
        channel.queueDeclare("inventory", True, False, False, None)

A class defined inside a function, such as a pytest test function or a factory function, gets no generated Java class. GraalPy adapts it to the Java type at run time, which only works on the JVM: the native launchers and native images fail with SystemError: Java Class can be extended only in JVM mode when the class statement runs. Define the class at module level, or pass a function or lambda where Java expects a functional interface.

See the Extending Java Classes section of the Micronaut guide for constructor rules and limitations.

9.1 Configuring pyproject.toml

pyproject.toml is the source of truth for Pyronaut’s project configuration and runtime project model. It includes standard Python project metadata plus the [tool.pyronaut] tables consumed by the CLI.

Minimal structure

[project]
name = "hello-pyronaut"
version = "0.1.0"
dynamic = ["scripts"]

[build-system]
requires = ["setuptools", "wheel", "tomli"]
build-backend = "setuptools.build_meta"

[tool.pyronaut]
repositories = ["mavenCentral"]

[tool.pyronaut.dependencies]
runtime = []
build = []
test = []

Managed versions

Pyronaut can resolve versionless Micronaut coordinates from configured BOM versions:

[tool.pyronaut.core]
version = "5.2.3"

[tool.pyronaut.platform]
version = "5.1.0"

If these tables are omitted, Pyronaut uses the managed versions bundled with the current Pyronaut distribution, which pyronaut --version prints. Python support requires Micronaut Core 5.2 or later.

Source layout

Use [tool.pyronaut.sources] to move source and resource directories away from the defaults:

[tool.pyronaut.sources]
python = "app"
python-test = "test/python"
java = "src/main/java"
java-test = "src/test/java"
resources = "app-config"
test-resources = "tests-config"
additional-resources = ["views", "assets"]
additional-test-resources = ["tests-fixtures"]

Packaging, processor, and test modes

Choose what pyronaut build produces when no packaging-shaping command-line option is present:

[tool.pyronaut.packaging]
format = "wheel-jvm"

[tool.pyronaut.processor]
mode = "jvm" # jvm|native
incremental = false
python-incremental-mode = "conservative" # conservative|optimistic
daemon = false

[tool.pyronaut.test]
mode = "jvm" # jvm|native
engine = "both" # junit|pytest|both
verbose = false # stream application and test framework output to the console

format accepts exactly fat-jar, wheel-jvm, wheel-native, wheel-crema, docker-jvm, docker-native, or docker-crema. It defaults to fat-jar when the project has Java sources and to wheel-jvm otherwise. Command-line flags such as --jar, --jvm, --native, and --docker override the configured format for that invocation.

The former tool.pyronaut.build.mode setting is no longer accepted. Migrate mode = "jvm" to format = "wheel-jvm", and mode = "native" to either format = "wheel-native" for a closed-world build or format = "wheel-crema" for a reusable native runtime.

The test engine defaults to both. Use junit for JUnit Jupiter tests, pytest for pytest tests, or both to execute both types.

verbose defaults to false: console output written while a test runs is captured into the test reports rather than shown. Set it to true, or pass --verbose to pyronaut test, to stream it to the terminal instead.

Native image settings and Docker image settings also live under [tool.pyronaut.build]. For a Crema format, set native-base = "default" to use the configured language-specific production runtime for the target platform, or set a filesystem path or HTTP(S) URL to reuse a custom base. Docker builds select Linux; host builds select the current operating system. pyronaut build --native-base=<path> builds a custom base and writes build.native-base together with packaging.format = "wheel-crema"; pyronaut build --docker --native-base=<image> writes build.docker.base-image together with packaging.format = "docker-crema". Bare --native-base selects the default runtime and does not change pyproject.toml. A closed-world wheel-native or docker-native format rejects a configured reusable base. See the CLI reference for the full build option surface. See Incremental processing before enabling incremental processing, the compiler daemon, or the optimistic Python dependency policy.

Control panel

The development/TUI Control Panel is opt-in, and Pyronaut disables it by default. Enable it for pyronaut dev and pyronaut --tui with:

[tool.pyronaut.control-panel]
enabled = true
path = "/control-panel"
production-enabled = false

The command-line option --control-panel enables it for that invocation and overrides this setting. pyronaut dev --control-panel also works for direct-source execution. When you enable development Control Panel support, Pyronaut also adds Micronaut Management and the Control Panel management integration to the development runtime so health and diagnostic panels are available. Pyronaut also adds the optional Control Panel modules that match the application’s dependencies. It adds a module only when the application uses the library that the panel inspects:

Application dependency Control Panel module

io.micronaut.sql:micronaut-jdbc

micronaut-control-panel-datasource

org.hibernate.orm:hibernate-core

micronaut-control-panel-hibernate

io.micronaut.kafka:micronaut-kafka

micronaut-control-panel-kafka

io.micronaut.objectstorage:micronaut-object-storage-core

micronaut-control-panel-object-storage

A Micronaut Cache implementation, such as micronaut-cache-caffeine

micronaut-control-panel-cache

The Caffeine cache that Pyronaut adds to the development runtime by default does not enable the cache panel. Direct-source execution selects the same modules from the dependencies that the sources declare.

Pyronaut writes the implicitly enabled development Control Panel dependencies only to the development-runtime dependency manifest, so pyronaut build does not package them. Applications can declare their own development-only runtime dependencies with development-runtime = […​] under [tool.pyronaut.dependencies].

Set production-enabled = true only when the application has Micronaut Security on the runtime classpath and you want the Control Panel in production runtime artifacts. Production Control Panel inclusion keeps the Micronaut Control Panel security defaults; the anonymous access used by pyronaut --tui is not applied to production builds.

Toolchain

Commands that delegate to Java use a GraalVM JDK. You can let Pyronaut discover a compatible installed JDK, or pin a toolchain:

[tool.pyronaut.toolchain]
type = "jvm" # jvm|native
distribution = "ee"
java-version = 25
version = "25i4"

Development builds can use distribution = "dev" with a release-tag or explicit download-url. Use type = "native" to route supported CLI lifecycle commands through the native pyronaut-dev uber CLI. It selects how CLI tooling executes; it does not select the output of pyronaut build. Use [tool.pyronaut.packaging] for the build default.

AOT cache

With the JVM toolchain on JDK 25 or later, Pyronaut can start its JVMs from a Leyden AOT cache (JEP 483). It is disabled by default:

[tool.pyronaut.toolchain]
type = "jvm"
aot-cache = true

The first launch of each JVM, whether the application or test JVM of pyronaut dev, run and test, or a tool such as the processor, configuration validator, installer or Test Resources client, is a training run. It starts more slowly and prints AOTConfiguration recorded as it exits. The cache is then created in the background under ~/.pyronaut/caches/aot, and later launches start from it. A cache is replaced when the JDK, the JVM options or a class path JAR changes, so a dependency change means one more training run. Each cache takes up to a few hundred megabytes; delete ~/.pyronaut/caches/aot to reclaim the space.

9.2 Installing Python and Micronaut Dependencies

Pyronaut uses normal Python packaging for Python dependencies and Maven coordinates for Java dependencies.

For direct-source applications without pyproject.toml, see Declaring direct source dependencies.

Python dependencies

Declare Python dependencies using standard Python packaging metadata:

[project]
dependencies = [
  "pytest>=8"
]

pyronaut install installs Python dependencies into a GraalPy virtual environment in the project .venv directory. It creates .venv with the GraalPy interpreter provisioned by pyronaut setup and runs pip install for:

  • the requirements in [project].dependencies

  • every group in PEP 735 [dependency-groups], following include-group entries

  • requirements.txt in the project directory

  • pytest, when the project has Python tests and does not declare it

Pyronaut skips pip while these declarations are unchanged. Use pyronaut install --refresh to reinstall them.

Java dependencies

Declare Java dependencies by scope under [tool.pyronaut.dependencies]:

[tool.pyronaut.dependencies]
runtime = [
  "io.micronaut:micronaut-http-server-netty",
  "io.micronaut:micronaut-json-core",
  "io.micronaut.serde:micronaut-serde-jackson",
  "ch.qos.logback:logback-classic"
]
build = [
  "io.micronaut.serde:micronaut-serde-processor"
]
test = [
  "io.micronaut.pyronaut:micronaut-pyronaut-pytest",
  "io.micronaut.test:micronaut-test-junit5",
  "io.micronaut.pyronaut:micronaut-pyronaut-requests"
]

Use group:artifact for dependencies managed by the Micronaut platform, Micronaut core BOM, or Pyronaut BOM. Use group:artifact:version for dependencies that are not managed.

Custom BOMs and exclusions

Apply project BOMs to every dependency scope:

[tool.pyronaut.dependencies]
boms = ["io.netty:netty-bom:4.2.17.Final"]
runtime = ["io.netty:netty-handler"]
exclusions = ["commons:commons-lang"]

[tool.pyronaut.dependencies.artifact-exclusions]
"io.netty:netty-handler" = ["commons:commons-lang"]

boms entries must use group:artifact:version. Explicit dependency versions take precedence over BOM management; Pyronaut applies user BOMs before the bundled Micronaut and Pyronaut BOMs. Global exclusions remove matching transitive modules from all roots, while an explicitly declared dependency remains available. Artifact exclusions apply only below the matching direct group:artifact root.

Install behavior

Run:

pyronaut install

By default, Pyronaut resolves dependency artifacts into Maven local (~/.m2/repository, or -Dmaven.repo.local when set). Pyronaut writes scoped classpath manifests under pyronaut that point at the selected local repository.

To use a project-specific repository instead:

pyronaut install --local-repository .pyronaut-m2

Useful install flags include:

  • --scope <build|runtime|development-runtime|test|test-resources-server|all> to resolve a single scope

  • --dependencies to render dependency tree output

  • --refresh to force re-resolution and manifest rewrite

  • --no-cache to bypass manifest cache reads

  • --offline to resolve without remote repository access

When several scopes are selected, Maven resolution runs in parallel. Interactive terminals show one progress row per scope, advancing from 0% to 100% by resolved artifact count and displaying the current artifact file name. Pyronaut uses ASCII bars by default for compatibility with terminals and log collectors; Unicode block bars can be explicitly enabled with -Dpyronaut.progress.unicode=true on a known UTF-8 terminal. Redirected and CI output remains deterministic and does not contain cursor-control sequences.

Use tool.pyronaut.dependencies.development-runtime for dependencies that should be available only to pyronaut dev and other development runtime launches. Pyronaut writes those artifacts to pyronaut/resolved-development-runtime-dependencies and excludes them from the production runtime manifest used by build/package flows.

9.3 Application Configuration with application.toml

Micronaut application configuration lives in the configured resources directory.

Direct-source applications can declare individual runtime properties with AppConfig; see Declaring Direct Source Dependencies. By default, that directory is config, so the main configuration file is:

config/application.toml

Pyronaut adds Micronaut TOML support to the runtime classpath by default when the Micronaut platform manages dependencies.

Basic configuration

[micronaut.application]
name = "hello-pyronaut"

[micronaut.server]
port = 8080

[endpoints.all]
enabled = true
sensitive = false

Executor defaults

Pyronaut supplies the following low-priority defaults for Micronaut executors. This follows the Micronaut Core Python threading guidance.

Property Default Why Pyronaut changes the default

micronaut.executors.io.type

cached

Uses a cached platform-thread executor for I/O work that may execute Python code.

micronaut.executors.io.virtual

false

GraalPy does not support executing Python code on virtual threads, so the I/O executor must use platform threads.

micronaut.executors.blocking.type

cached

Uses a cached platform-thread executor for blocking work that may execute Python code.

micronaut.executors.blocking.virtual

false

GraalPy does not support executing Python code on virtual threads, so the blocking executor must use platform threads.

Pyronaut applies these defaults only when the application does not provide a value. Normal application configuration, including application.toml or application.properties, can override them, and partial configuration leaves the unspecified defaults in place.

Environment-specific files use the Micronaut naming convention:

config/application-test.toml
config/application-dev.toml

Pyronaut includes the configured resources directory and any additional-resources directories for dev, run, test, and build flows. It includes the configured test-resources directory and any additional-test-resources directories for dev and test flows.

Schema support

When application.toml exists, pyronaut install builds a JSON schema from Micronaut configuration metadata present on the resolved runtime classpath. It writes the schema to:

__pyronaut__/schemas/micronaut-application.schema.json

If application.toml does not already contain a user-managed schema directive, Pyronaut prepends one so TOML-aware editors can validate Micronaut configuration keys.

Validation

Use:

pyronaut validate-config --scenario dev
pyronaut validate-config --scenario test
pyronaut validate-config --scenario production

pyronaut dev, pyronaut run, pyronaut test, and native build flows run scenario-specific validation by default.

9.4 Configuration Validation

pyronaut validate-config validates Micronaut configuration against the resolved application classpath. It is useful after changing application.toml, dependencies, environments, or source layout.

Run validation explicitly with:

pyronaut validate-config --scenario dev
pyronaut validate-config --scenario production

Supported scenarios are:

  • dev

  • run

  • test

  • production

The standalone command defaults to production. pyronaut dev, pyronaut run, pyronaut test, and native build flows call validation with their own scenario defaults unless you pass --no-validate.

What is validated

Validation loads configuration the same way the application does. It reads application.toml (and application.properties, application.yml or application.json) plus environment-specific variants such as application-dev.toml from:

  • the resources directories (config by default, set with resources and additional-resources in [tool.pyronaut.sources])

  • src/main/resources

  • for the test scenario, the test resources directories as well (Maven and Gradle projects also include them for dev)

Each property is checked against the configuration schemas of the application classpath. Validation reports:

  • values of the wrong type, for example port = "eighty-eighty" under [micronaut.server]

  • values that are not in an enum, for example schema-generate = 'CREATE_DRPO' under [datasources.default]

  • unknown keys, for example prot = 8080 under [micronaut.server], with a suggestion when a similar key exists

Each error names the file and line it came from. Unknown keys are errors while fail-on-not-present is true, which is the default.

Validation runs for pyproject.toml projects and for Maven and Gradle projects. Direct-source launches such as pyronaut dev main.py do not run configuration validation.

Reports

By default, Pyronaut writes reports under:

__pyronaut__/reports/config-validation/<scenario>/

The default report files are:

  • configuration-errors.json

  • configuration-errors.html

Pyronaut also writes pyronaut/.config-validation-cache.properties to avoid repeating unchanged validations.

For Maven and Gradle projects Pyronaut writes the reports and cache under target/pyronaut or build/pyronaut instead of pyronaut.

Project configuration

[tool.pyronaut.validation]
enabled = true
fail-on-not-present = true
deduce-environments = false
validate-dependency-injection = false
dependency-injection-validation-strategy = "reachable"
format = "both"
suppressions = []

[tool.pyronaut.validation.test]
environments = ["test"]

[tool.pyronaut.validation.production]
environments = []

Scenario-specific settings can override environments, classpath entries, resources directories, and output directories.

Dependency injection validation

Pyronaut disables dependency injection validation by default. Enable it when you want validation to include bean graph checks:

pyronaut validate-config --validate-dependency-injection

or in pyproject.toml:

[tool.pyronaut.validation]
validate-dependency-injection = true
dependency-injection-validation-strategy = "reachable"

Available strategies are reachable, application-beans, and all-beans.

Suppressions

When validation finds suppressible errors, the CLI prints a TOML snippet that you can copy into pyproject.toml:

[tool.pyronaut.validation]
suppressions = [
  "datasources.default.url"
]

Keep suppressions narrow and revisit them when adding the missing configuration or dependency.

9.5 IDE Setup for VS Code and PyCharm

pyronaut install generates editor support from the resolved runtime and test classpaths. This gives Python editors stubs for Java-backed APIs such as Micronaut annotations and Jakarta injection types.

Generated editor files include:

  • pyronaut/schemas/pyronaut-pyproject.schema.json

  • pyronaut/schemas/micronaut-application.schema.json (the #:schema directive is only added to application.toml when that file exists)

  • pyronaut/ide-stubs

  • pyronaut/resolved-editor-artifacts.json

  • pyronaut/reports/editor-stubs/stub-generation-report.txt

pyronaut install prepends a Taplo schema directive to pyproject.toml and to application.toml when those files do not already have user-managed schema directives.

Configure stub generation

[tool.pyronaut.ide-stubs]
enabled = true
ide = "vscode" # vscode|pycharm
packages = ["io.micronaut", "jakarta"]
exclude-patterns = ["*ModuleInfo"]
destination-dir = "__pyronaut__/ide-stubs"

The default IDE target is vscode. Stub generation is best effort; Pyronaut skips APIs that it cannot render cleanly and reports them in the stub generation report.

Generated stubs are deterministic: the same classpath always produces byte-identical files. Non-interactive builds such as CI or sandboxed packaging that have no use for editor support can skip stub generation without editing pyproject.toml by setting the PYRONAUT_IDE_STUBS_ENABLED=false environment variable (or the pyronaut.ide-stubs.enabled=false system property), which takes precedence over enabled.

VS Code

When ide = "vscode" and the project does not already own Pyright configuration, Pyronaut writes .vscode/settings.json with python.analysis.extraPaths pointing at the generated stub directory. When Pyronaut knows the Python executable or site-packages directory (from the project .venv, the PYRONAUT_PYTHON_EXECUTABLE or PYRONAUT_PYTHON_SITE_PACKAGES environment variables, or the matching pyronaut.python.* system properties), it adds the site-packages directory to extraPaths and sets python.defaultInterpreterPath as well.

If pyrightconfig.json or [tool.pyright] already exists, Pyronaut leaves the configuration user-managed and records that decision in the editor stub report.

For VS Code Test Explorer integration, see VS Code Test Explorer Extension.

PyCharm

When ide = "pycharm", Pyronaut writes a generated .idea/pyronaut-editor-stubs.iml module and registers it in .idea/modules.xml. The generated module marks the stub directory as a source root without rewriting the main PyCharm project module.

Refresh IDE state

Run pyronaut install after changing dependencies, source layout, or IDE stub settings.

Pyronaut caches generated stubs per classpath under ~/.pyronaut/ide-stubs and shares them between projects on the same machine. Deleting pyronaut/ide-stubs makes the next install restore the stubs from that cache; delete the matching cache directory as well (or the whole of ~/.pyronaut/ide-stubs) to force regeneration.

destination-dir must point at a directory that Pyronaut owns. The generator replaces the directory’s contents on every install and refuses to run when the directory contains files it did not generate.

9.6 VS Code Test Explorer Extension

Pyronaut includes a small VS Code extension for projects whose tests must run through pyronaut test. The extension contributes a Pyronaut test controller to VS Code Test Explorer and does not use the Python extension’s pytest runner.

The extension is currently installed manually from this repository. Build the VSIX:

./gradlew :micronaut-pyronaut-vscode:packageVsix

Install the generated package:

code --install-extension pyronaut-vscode/build/vsix/pyronaut-vscode-*.vsix

Open a Pyronaut project in VS Code and use the Testing view. The extension discovers pytest-style functions from the configured Pyronaut Python test source directory and runs selections with pyronaut test.

Configuration

The extension reads the Pyronaut test source directory from:

[tool.pyronaut.sources]
python-test = "tests"

The default test source directory is tests.

The extension settings are:

  • pyronaut.executable: path to the Pyronaut executable. Defaults to pyronaut.

  • pyronaut.test.extraArgs: additional arguments appended to pyronaut test before test selectors.

Python extension pytest support

Do not enable VS Code Python pytest discovery for Micronaut-backed Pyronaut tests that import Java-backed APIs such as micronaut.runtime.server. Those tests need the Pyronaut processed classpath, test resources, and GraalPy runtime bootstrapping provided by pyronaut test.

If you already enabled VS Code Python pytest discovery, disable it in .vscode/settings.json:

{
  "python.testing.pytestEnabled": false
}

Current limitations

  • The extension is not yet published to the VS Code Marketplace.

  • Installation is manual through the generated VSIX.

  • Debug and coverage profiles are not implemented yet.

  • The extension expects pyronaut to be available on PATH unless pyronaut.executable is configured.

  • Parametrized tests are shown as one item; the item fails if any parameter set fails.

9.7 Using Maven and Gradle Projects

Pyronaut can run Java applications whose Maven or Gradle build manages their source layout and dependencies. Run the commands from the build root (the directory containing pom.xml or a Gradle build file):

pyronaut dev
pyronaut run
pyronaut test

Pyronaut resolves the build’s source sets and classpaths, processes the application, and then launches the processed classes. dev, run, and test validate configuration using their respective scenarios. Use --no-validate to skip the lifecycle validation step.

Pyronaut writes generated state such as processed classes, dependency manifests, validation reports and test reports under target/pyronaut (Maven) or build/pyronaut (Gradle) rather than pyronaut.

Development control panel

Pyronaut disables the Micronaut Control Panel by default. For Maven/Gradle projects, pyronaut dev --control-panel enables it for that invocation; pyronaut run never enables it automatically. Python projects can opt in through [tool.pyronaut.control-panel].enabled, and --control-panel always overrides configuration. Pyronaut adds the optional Control Panel modules, such as the datasource or Kafka panel, that match the build’s runtime dependencies. See Configuring pyproject.toml for the full mapping.

Test resources

When the root Gradle project applies io.micronaut.test-resources, or the effective Maven model sets micronaut.test.resources.enabled to true, Pyronaut starts or attaches to Test Resources for dev and test. A plugin applied only in a Gradle subproject is not detected. Pyronaut passes the resulting connection settings to the launched application. run does not automatically start Test Resources.

Versioning

Pyronaut-provided support, including the development Control Panel and Test Resources integration, uses the Micronaut platform version inherited by the installed Pyronaut SDK. It does not use or override the Micronaut platform version configured by the Maven or Gradle build. The build continues to resolve its own application dependencies normally.

Direct Java and Python source execution can declare Maven dependencies, repositories, and Micronaut properties without a pyproject.toml. These declarations apply only when running direct sources without --setup.

Java

9.9 Configuring Maven Repositories

Pyronaut resolves Java dependencies through Apache Maven Resolver.

Direct-source applications can instead use MavenRepository; see Declaring Direct Source Dependencies. Configure remote and local repositories in [tool.pyronaut]:

[tool.pyronaut]
repositories = [
  "mavenCentral",
  "mavenLocal",
  "https://repo.gradle.org/gradle/libs-releases",
  "../build/fixture-repo"
]

Supported entries:

  • mavenCentral: Maven Central

  • mavenLocal: the effective Maven local repository

  • https://…​;: a remote Maven repository URL

  • relative or absolute file paths: local Maven repository directories

If repositories is omitted or empty, Pyronaut uses Maven Central. Pyronaut resolves relative file paths against the project directory.

When the configured Micronaut Core version or the installed Pyronaut SDK is a snapshot, Pyronaut additionally consults the Sonatype Central snapshots repository and the local Maven repository so that snapshot artifacts resolve. [maven]
repositories = ["mavenCentral"]

9.10 Proxy Configuration

pyronaut install and on-demand native-image downloads honor proxy configuration. Pyronaut checks proxy settings in this order:

  1. Environment variables

  2. ~/.pyronaut/settings.toml

  3. ~/.m2/settings.xml

The first configured proxy wins.

Environment variables

Use the standard proxy environment variables:

export HTTPS_PROXY=http://user:password@proxy.example.com:3128
export NO_PROXY=localhost,127.0.0.1,*.internal
pyronaut install

Lowercase variants such as https_proxy and no_proxy are also recognized. If both HTTP and HTTPS proxy variables are set, HTTPS takes precedence.

Pyronaut matches bypass entries as host-name patterns in which is a wildcard. It treats a leading dot (.internal) as .internal and ignores a trailing port; CIDR ranges are not supported.

Pyronaut settings

Use ~/.pyronaut/settings.toml when proxy settings should apply to Pyronaut without changing the shell environment:

[proxy]
url = "https://user:password@proxy.example.com:8443"
nonProxyHosts = "localhost,*.internal"

You can also specify the proxy with individual fields:

[proxy]
protocol = "http"
host = "proxy.example.com"
port = 3128
username = "user"
password = "password"
nonProxyHosts = "localhost|127.*"

nonProxyHosts and noProxyHosts are both accepted. Pyronaut normalizes comma-separated and pipe-separated values before passing them to Maven Resolver.

Maven settings fallback

If neither environment variables nor Pyronaut settings define a proxy, Pyronaut reads the active proxy from ~/.m2/settings.xml:

<settings>
  <proxies>
    <proxy>
      <active>true</active>
      <protocol>https</protocol>
      <host>proxy.example.com</host>
      <port>7443</port>
      <username>user</username>
      <password>password</password>
      <nonProxyHosts>localhost|127.*</nonProxyHosts>
    </proxy>
  </proxies>
</settings>

When dependency resolution fails after Pyronaut selects a proxy, the install error includes the proxy source and host summary.

Native-image downloads use the same precedence and bypass rules. The selected Pyronaut forms the bundle URL from [native-images].base-url and [native-images].version. For GitHub Releases, [native-images].release-tag selects the release used to resolve that versioned asset. These settings are independent of the [proxy] table.

9.11 Incremental Processing

pyronaut process normally performs a clean compilation of all configured Python and Java sources. Incremental processing is opt-in; Pyronaut disables it by default.

Enable it in pyproject.toml:

[tool.pyronaut.processor]
incremental = true
python-incremental-mode = "conservative"
daemon = true

You can override the project setting for one invocation:

pyronaut process --incremental
pyronaut process --no-incremental
pyronaut process --daemon
pyronaut process --no-daemon

--incremental and --no-incremental take precedence over tool.pyronaut.processor.incremental. --daemon and --no-daemon take precedence over tool.pyronaut.processor.daemon. Projects without an explicit setting remain non-incremental, including projects processed through --project-dir.

Compiler daemon

Incremental processing reduces the affected source set, while the optional compiler daemon avoids initializing GraalPy again for every pyronaut process command. The optimizations are independent, but enabling both provides the lowest latency for repeated development compilations.

The daemon works with JVM and native processor toolchains. It re-executes the active processor tool, listens only on the local loopback interface, authenticates requests with a per-daemon token, and handles one compilation at a time. The daemon forwards standard output and standard error separately to the invoking command, so diagnostics and redirected output behave as they do without the daemon. Interactive progress rendering is not available through the daemon; use --progress on to force it.

The daemon keeps a small number of initialized Python processing sessions, one per distinct compiler classpath (up to four, evicted least-recently-used). Python AST transformation, processing, and generated bytecode compilation all reuse the matching session’s GraalPy context. Fresh annotation processors and javac tasks are still created for every request so compiler state cannot leak between compilations. If a compilation fails, the daemon discards its Python session before another request uses it; a changed compiler or annotation processor classpath selects or creates a different session.

The daemon stores endpoint metadata in pyronaut/daemon/daemon.properties. It appends diagnostics that occur outside an active request to pyronaut/daemon/daemon.log. The daemon shuts down after ten minutes without a request (configurable with the pyronaut.processor.daemon.idle-timeout-seconds system property) and removes its endpoint metadata. The next command starts a new daemon. If endpoint health checks or communication fail, the client removes stale metadata and starts a replacement; if daemon startup fails, Pyronaut reports the reason and safely processes in the current command process.

What Pyronaut reuses

Pyronaut first uses its whole-pass fingerprint to skip processing when no input changed. When an input changed, incremental processing retains unaffected classes and resources, adds the existing output directory to the compilation classpath, and recompiles the changed sources and their known transitive dependents.

State for the two processing passes is kept separately:

  • pyronaut/incremental/main

  • pyronaut/incremental/test

Outputs produced from one source are isolating. Changing or deleting that source replaces only its outputs and recompiles sources that depend on it. Outputs produced from a set of sources are aggregating. Changing any contributor reruns the aggregating processing over all contributors and replaces its shared outputs. For example, OpenAPI processing aggregates multiple controllers into one OpenAPI document.

Pyronaut can track Python source files, generated bean metadata, direct VFS sources, and Python bytecode as isolating outputs. Package initializers, bridge modules, VFS indexes, and other shared Python resources are aggregating outputs, so Pyronaut regenerates them whenever the contributing Python set changes.

Full compilation fallbacks

Correctness takes precedence over reusing outputs. Pyronaut performs a clean full compilation when incremental state is absent, corrupt, incompatible, or refers to a missing output. It also performs a full compilation when a compiler-wide input changes, including:

  • source roots, compiler options, application settings, or Python bytecode mode

  • classpath, boot classpath, or annotation processor path contents

  • the selected Python incremental mode

  • an annotation processor that does not declare supported incremental behavior

  • an isolating processor that produces an output without exactly one originating source

  • recovery after a failed compilation

Pyronaut replaces the state only after a successful compilation. If compilation fails, the next invocation performs a repairing full compilation.

--no-cache disables incremental reuse even when you configure incremental processing. It clears the pass outputs and incremental state and performs a full compilation.

Python dependency policy

Pyronaut builds a dependency graph from statically visible local imports, declared types, decorators, annotations, and cross-language type references. Python can also express relationships that static processing cannot prove. Choose how those cases affect recompilation with python-incremental-mode:

conservative

This is the default. When a dynamic or unresolved relationship affects a Python change, Pyronaut reprocesses all Python sources. This avoids stale generated output at the cost of broader compilation.

optimistic

Pyronaut reprocesses only sources selected by the statically discovered graph. This can make dynamic projects faster, but the developer is responsible for ensuring an undiscovered relationship cannot change generated output.

Both modes still reprocess aggregating visitors over all contributors. Deleting a Python source also expands processing so shared Python outputs cannot retain deleted-source data. An unrelated Java-only change does not trigger the conservative all-Python fallback unless it reaches Python through the dependency graph.

Pyronaut treats the following as indicators that Python relationships might be dynamic or unresolved:

  • import(…​) or import_module(…​)

  • getattr(…​), globals(), or locals()

  • star imports such as from example import *

  • @Mixin

  • a relative or local-package import that Pyronaut cannot resolve to a configured Python source

Writing incremental Python code

Prefer explicit, module-level imports:

from petclinic.models import Owner
from petclinic.repositories import OwnerRepository


class OwnerService:
    repository: OwnerRepository

    def find(self, owner_id: int) -> Owner:
        ...

This lets a change to Owner or OwnerRepository propagate to OwnerService without recompiling unrelated modules.

To keep the dependency graph precise:

  • use explicit imports instead of star imports

  • import local modules by their stable configured package name

  • keep type annotations and decorators explicit

  • avoid discovering classes or decorators through strings when they affect generated Micronaut metadata

  • avoid mutating module exports dynamically when processors depend on those exports

  • keep init.py re-exports straightforward; package initializers are shared outputs, so Pyronaut regenerates them when Python changes

Runtime dynamism that cannot affect compiled or generated output does not require conservative processing. If a dynamic relationship does affect generated beans, routes, serialization metadata, or another processor output, keep conservative mode or arrange an explicit static dependency. Use optimistic only when tests cover those relationships well enough to detect stale output.

Writing incremental Java code

The compiler tracks Java dependencies from declarations and references, including inheritance, method and field types, annotations, package-private access, transitive references, and constant owners. Ordinary Java source using explicit types therefore remains incremental:

final class OwnerService {
    private final OwnerRepository repository;

    OwnerService(OwnerRepository repository) {
        this.repository = repository;
    }

    Owner find(long id) {
        return repository.findById(id);
    }
}

Prefer compiler-visible type references over class names encoded only as strings when generated output depends on the relationship. Reflection and service discovery used only at runtime do not require recompilation, but an annotation processor that scans or resolves those relationships must declare and implement the appropriate aggregating behavior.

Writing incremental visitors and annotation processors

A Micronaut TypeElementVisitor that creates output for one source should remain VisitorKind.ISOLATING and associate every generated output with that one originating element. Do not read unrelated source types or the complete application classpath to decide an isolating output.

A visitor whose result combines multiple sources must return VisitorKind.AGGREGATING:

@Override
public VisitorKind getVisitorKind() {
    return VisitorKind.AGGREGATING;
}

This includes registries, indexes, and single documents generated from multiple controllers or models. Aggregating processing is broader, but it ensures removed or changed contributors cannot leave stale data in a shared output.

Custom JSR 269 annotation processors must advertise exactly one of the incremental processor options already used by Gradle:

@SupportedOptions("org.gradle.annotation.processing.isolating")
final class ExampleProcessor extends AbstractProcessor {
    // Each generated output must have exactly one originating element.
}

Use org.gradle.annotation.processing.aggregating instead when outputs combine multiple sources. These are supported-option marker strings; enabling them does not add a Gradle runtime dependency. An unknown processor, a processor declaring both or neither marker, an output outside the compiler target, or an isolating output with zero or multiple originating elements causes Pyronaut to fall back to full compilation.

10 Packaging and Deployment

pyronaut build packages the processed application for distribution. Java applications (Maven and Gradle projects, projects with Java sources, and direct .java sources) default to fat-jar; Python applications default to wheel-jvm. Configure another default with tool.pyronaut.packaging.format. An explicit packaging flag takes precedence over that setting. tool.pyronaut.toolchain.type only controls how Pyronaut’s CLI tooling executes and does not select a build output.

Choosing a package type

Format Equivalent command Best fit and trade-off

fat-jar

pyronaut build --jar

The default for Java applications. One JVM-hosted artifact runnable with java -jar. It includes the selected Java or Python production runtime and is typically larger than a wheel.

wheel-jvm

pyronaut build --jvm

The default for Python applications. It has the shortest build time and is a good choice when a JVM is already available in the deployment environment.

docker-jvm

pyronaut build --jvm --docker

A portable container form of the JVM wheel. JVM deployment generally offers the best peak throughput after warm-up, at the cost of JVM startup time and a larger memory footprint.

wheel-native

pyronaut build --native

Produces a standalone executable with fast startup and low memory use. Each application build performs native-image analysis, which is comparatively slow, and application code must satisfy native-image’s closed-world requirements, including reachability metadata or reflection configuration where needed.

docker-native

pyronaut build --native --docker

Builds the native executable in a Linux container and packages it in a small runtime image. Choose this when the target platform is a container platform.

wheel-crema

pyronaut build --native-base

A wheel using a reusable native production runtime. Pyronaut prefers a configured custom base; otherwise it uses the bundled default.

docker-crema

pyronaut build --native-base --docker

A container with a reusable custom or bundled Crema base and an application layer.

Bare --native-base is shorthand for --native-base=default. To build a custom base instead, name it: --native-base=<path> for a wheel or --native-base=<image> with --docker. See Crema production runtimes and base images.

Runnable fat JARs

Build one executable JAR with:

pyronaut build --jar
java -jar dist/hello-pyronaut-0.1.0.jar argument1 argument2

Pyronaut writes the artifact as dist/<project-name>-<version>.jar and replaces unsafe filename characters with -. Both Java and Python applications require a compatible GraalVM JDK, as they use the same production runtime selected for a JVM wheel. Python FAT JARs therefore include GraalPy and are larger than their Java equivalents. The command supports Pyronaut projects, direct Java or Python sources, and external Maven or Gradle projects.

The outer JAR contains a small launcher plus an indexed PYRONAUT-INF layout. Application classes and resources precede dependencies, followed by dependency roots in resolved-classpath order. Duplicate classes use first-root-wins semantics. Resources, including META-INF/services descriptors, remain enumerable across every root. The packager also merges every root’s Micronaut bean and service markers into META-INF/micronaut/ at the archive root so that Micronaut’s classpath scanning finds them. The launcher preserves multi-release JAR selection and package manifest metadata such as sealing. It reads entries directly from the artifact and does not extract them to disk.

The packager produces reproducible artifacts by using deterministic entry ordering and timestamps and omitting source paths. Repackaging invalidates dependency signature files and stale JAR indexes, so Pyronaut omits them. Sign the completed FAT JAR if you require artifact signing.

Wheels and JVM containers

A JVM build produces a Python wheel in dist/:

pyronaut build --jvm

Install the wheel into the target Python environment in the normal way. The wheel carries the processed application and its runtime launch support; the deployment environment must provide a compatible GraalVM JDK.

Use Docker when the deployment platform expects an OCI image:

pyronaut build --jvm --docker

The default Dockerfile stages the processed classes, application resources, resolved runtime dependencies, and the appropriate production launcher.

Application native images

Native builds create pyronaut/native/application by default:

pyronaut build --native

Native images offer fast startup and low memory consumption, which is useful for short-lived workloads and densely deployed services. The trade-off is build time: every application-native build performs native-image analysis. Native image analysis also uses a closed-world model, so libraries that use reflection, dynamic proxies, resources, or other dynamic behavior may need reachability metadata or explicit native-image configuration. See Reachability metadata repository (native mode) for the metadata repository settings.

Pyronaut derives application packages from processed output and preserves them in fully closed-world native images, keeping user classes available for runtime reflection without widening a reusable production base image.

Use a container-native build to compile for Linux inside the configured native builder image:

pyronaut build --native --docker

Crema production runtimes and base images

Crema is a reusable native production runtime. It contains Pyronaut’s runtime modules but excludes compilers, annotation processors, test libraries, and other development tooling. pyronaut-run is the Java runtime; Python projects use pyronaut-run-python, which additionally contains GraalPy, Truffle, and the Python Logback integration.

Use the downloaded language-specific runtime when no dependency needs to be included in a custom base. The first invocation resolves the configured [native-images] bundle and stores it under ~/.pyronaut/bin:

pyronaut build --native-base

Bare --native-base is equivalent to --native-base=default. Every --native-base form implies native packaging. For default, a host build selects the bundle matching the current operating system and architecture; a Docker build selects the Linux bundle matching the current architecture. Pyronaut chooses pyronaut-run for Java projects and pyronaut-run-python for Python projects. Pyronaut resolves the bundle using [native-images] in ~/.pyronaut/settings.toml, including its configured repository, version, proxy, and authentication settings. Pyronaut reuses a valid bundle already cached under ~/.pyronaut; otherwise it downloads the bundle with progress reporting.

The native launcher projects publish the same complete bundle format used by the CLI downloader. Running ./gradlew :micronaut-pyronaut-dev:assemble, :micronaut-pyronaut-run:assemble, or :micronaut-pyronaut-run-python:assemble creates a versioned .tar.gz under the module’s build/distributions directory. Each archive contains the native executable, generated native classpath manifests, and the native-image resources directory. Python-capable images are built with -H:+CopyLanguageResources, so resources is a runtime input. Keep it beside its executable when you extract an archive, copy it into a wheel, or install it in a container. The bundle also includes adjacent native runtime libraries as part of the same bundle contract.

To make the default runtime the project’s packaging format, configure it in pyproject.toml; a plain pyronaut build then produces a Crema wheel:

[tool.pyronaut.packaging]
format = "wheel-crema"

[tool.pyronaut.build]
native-base = "default"

When the application’s dependencies should be compiled into the runtime, build a custom base by giving it a path, relative to the project directory:

pyronaut build --native-base=build/pyronaut-base/pyronaut-run-python

Pyronaut builds the native base at that path, exports its SBOM, packages the application wheel against it, and records the base in pyproject.toml (an existing value is replaced; the rest of the file is preserved):

[tool.pyronaut.packaging]
format = "wheel-crema"

[tool.pyronaut.build]
native-base = "build/pyronaut-base/pyronaut-run-python"

Later builds reuse the configured native base without rebuilding it. Run pyronaut build --native-base=<path> again after changing the dependencies that the base should contain:

pyronaut build

If Pyronaut cannot update pyproject.toml safely, for example because the [tool.pyronaut] table defines these settings with dotted keys, it leaves the file unchanged and prints the settings to add.

native-base may instead be an HTTP(S) URL to a native executable, either in pyproject.toml or as --native-base=<url>, which packages against the downloaded launcher without building or recording a base. Pyronaut uses the configured proxy settings and displays download progress. URL-based native bases are unavailable with --offline. A raw URL continues to represent a self-contained executable; use a published Pyronaut native bundle when the launcher must transport external language resources with the application.

Crema avoids rebuilding the native runtime for each source change. The native base is the only expensive native-image build; subsequent application builds package processed classes and application dependencies for runtime loading. They retain native startup time without requiring each application to meet the same closed-world reflection configuration requirements as a fully application-native image. Inspect the SBOM exported with the native base to confirm that it contains the shared dependencies.

For Docker, pyronaut build --docker --native-base builds the application image on the bundled Linux runtime. To build a custom base image, name it:

pyronaut build --docker --native-base=acme/pyronaut-runtime:1

Pyronaut builds and tags the native base image, builds the application layer on top of it, and records the image in pyproject.toml:

[tool.pyronaut.packaging]
format = "docker-crema"

[tool.pyronaut.build.docker]
base-image = "acme/pyronaut-runtime:1"

Subsequent builds add only the application layer:

pyronaut build

To reuse a base produced in CI or another project, configure its image name:

[tool.pyronaut.packaging]
format = "docker-crema"

[tool.pyronaut.build.docker]
base-image = "registry.example.com/acme/pyronaut-runtime:1"

The final image then adds only the application configuration, processed classes, and schemas on top of the shared production runtime layer. For a custom layering arrangement, see Custom Dockerfiles with a reusable base.

Profile-guided optimization

A custom native base can be compiled with profile-guided optimization (PGO). Pass one or more .iprof profiles with --pgo when you build the base:

pyronaut build --native-base=build/pyronaut-base/pyronaut-run --pgo=profiles/pyronaut-run.iprof
pyronaut build --docker --native-base=acme/pyronaut-runtime:1 --pgo=profiles/pyronaut-run.iprof

Each value is a local path, relative to the project directory, or an HTTP(S) URL. Separate several profiles with commas or repeat the option; native-image merges them:

pyronaut build --native-base=build/pyronaut-base/pyronaut-run-python \
  --pgo=https://example.com/profiles/pyronaut-run-python.iprof \
  --pgo=profiles/my-workload.iprof

Pyronaut downloads URL profiles under pyronaut/pgo using the configured proxy settings and shows download progress; they are unavailable with --offline. Every profile must exist and be non-empty before the native-image build starts.

--pgo applies only to a custom base build, --native-base=<path> or --docker --native-base=<image>. The bundled default runtime is already optimized, and a closed-world --native build rejects the option. The profiles are not recorded in pyproject.toml: pass them again when you rebuild the base.

PGO requires Oracle GraalVM. For a host build, JAVA_HOME must point to Oracle GraalVM; GraalVM Community Edition cannot build with --pgo. Docker builds use the default Oracle GraalVM builder images unless build.docker.native-builder-image selects another one.

A profile is most effective for the image it was collected from. Choose the profile for the launcher that your project uses, pyronaut-run for Java or pyronaut-run-python for Python, collected on the target operating system and architecture for the same Pyronaut version. A custom base also contains your application’s dependencies. Code that the profile does not cover is still compiled, but without profile information. An older or mismatched profile does not fail the build, but most of the benefit is lost.

Direct-source applications

pyronaut build packages standalone sources through the same JVM, native, Docker, and native-base flows as a regular project:

pyronaut build App.java --native --name hello-java --version 1.0.0
pyronaut build App.py --docker --native-base
pyronaut build App.java --name hello-java --version 1.0.0

Direct .java sources build a FAT JAR by default and .py sources a JVM wheel. Pyronaut compiles sources to disk under pyronaut/direct-source-build and writes the artifacts to dist/ next to the sources, for example dist/hello-java-1.0.0.jar. The build resolves dependencies only; it does not generate the IDE files that pyronaut install App.java creates. Use --setup pyproject.toml for project configuration. Pyronaut resolves inline @Dependency declarations before packaging and includes them in a custom native base’s SBOM. A direct-source build with --native-base=<path|image> builds the custom base but does not record it, because the staged project is regenerated for every build; add the setting to the --setup file to reuse it.

11 Python Logging with Logback

Pyronaut routes Python logging through Logback, the logging backend used by Micronaut, instead of Python’s own handlers. You keep writing logging.getLogger(name).info(…​) and configuring logging with the familiar dictConfig schema; Logback appenders format and write the records alongside the framework’s own log output.

Why use Logback for Python?

When Python runs inside a Micronaut application, two logging systems would otherwise compete: Python’s logging module writing to its own handlers, and Logback writing the framework’s messages. Routing Python records into Logback gives:

  • One log stream. Python and Java messages share the same appenders, format, ordering and files.

  • One configuration. Log levels for Python loggers, Micronaut packages and libraries are set in one place, and Micronaut’s management endpoints can change them at runtime.

  • Less contention. Formatting and writing happen on Logback’s side, outside the GraalPy interpreter lock, so logging from many threads does not serialise Python execution.

  • Logback’s ecosystem. Rolling files, syslog, email, JSON encoders and every other Logback appender are available to Python code.

Basic configuration

Call dictConfig from the logback.config module with a dictionary that follows the Python dictConfig schema:

from logback.config import dictConfig

LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,

    "formatters": {
        "standard": {
            "format": "%(asctime)s [%(levelname)-5s] %(name)s: %(message)s"
        }
    },

    "handlers": {
        "console": {
            "class": "logging.StreamHandler",
            "level": "INFO",
            "formatter": "standard"
        },
        "file": {
            "class": "logging.handlers.RotatingFileHandler",
            "level": "DEBUG",
            "formatter": "standard",
            "filename": "app.log",
            "maxBytes": 10_000_000,
            "backupCount": 5
        }
    },

    "root": {
        "level": "INFO",
        "handlers": ["console", "file"]
    },

    "loggers": {
        "my.module": {
            "level": "DEBUG",
            "handlers": ["file"],
            "propagate": False
        }
    }
}

dictConfig(LOGGING)

Call dictConfig once, early, for example at the top of your main module. Pyronaut routes loggers created before the call, such as module-level logging.getLogger(name) loggers, to Logback as well. Pyronaut honors disable_existing_loggers only when you set it explicitly to True; it does not apply Python’s default of disabling pre-existing loggers because that would silence exactly those module-level loggers.

Levels use Python’s names (DEBUG, INFO, WARNING, ERROR, CRITICAL) or numeric values, and Pyronaut maps them to the corresponding Logback levels. NOTSET inherits the parent level; an unknown level name raises ValueError, as it does in Python.

Handler translation

Pyronaut translates Python handler classes to Logback appenders:

Python handler Logback appender Notes

logging.StreamHandler

ConsoleAppender

Writes to standard output. (Python’s StreamHandler defaults to standard error.)

logging.FileHandler

FileAppender

Plain file logging. Provide filename.

logging.handlers.RotatingFileHandler

RollingFileAppender

Size-based rotation. maxBytes becomes the size trigger and backupCount the number of rotated files (app.log.1 to app.log.N).

A handler’s level becomes a threshold filter on the appender, so a DEBUG root logger with an INFO console handler prints INFO and above on the console, as it would in Python. The encoding and mode options are not translated.

Format translation

Pyronaut translates format strings in %(name)s style to Logback patterns. It preserves width and alignment modifiers, so %(levelname)-5s becomes %-5level:

Python format Logback pattern

%(asctime)s

%d{yyyy-MM-dd HH:mm:ss.SSS}

%(levelname)s

%level

%(name)s

%logger

%(message)s

%msg

%(threadName)s

%thread

%(lineno)d

%line

%(filename)s

%file

%(funcName)s

%method

The adapter appends a newline (%n) automatically. %(process)d renders the JVM process id, and a record attribute with no Logback equivalent becomes an MDC lookup (%X{name}), which renders as empty text unless your code puts that key into the MDC.

Using Logback appenders directly

Configure any Logback appender by giving its fully qualified class name as the handler class. Pyronaut applies keys other than class, level and formatter as properties of the appender:

LOGGING = {
    "version": 1,
    "handlers": {
        "syslog": {
            "class": "ch.qos.logback.classic.net.SyslogAppender",
            "syslogHost": "logs.example.com",
            "facility": "USER",
            "suffixPattern": "%logger %msg"
        }
    },
    "root": {
        "level": "ERROR",
        "handlers": ["syslog"]
    }
}

Property mapping rules:

  • A scalar value "name": "value" calls the appender’s setName(value) method. Pyronaut converts only String, int, long, boolean and similar simple parameters; it skips a property whose setter needs another type and prints a warning on standard error.

  • A list value "name": ["a", "b"] calls addName(…​) once per element.

  • Nested objects (for example a custom layout or encoder) are not supported. Configure such appenders in a logback.xml on the classpath instead.

Commonly used appenders include ch.qos.logback.core.ConsoleAppender, ch.qos.logback.core.FileAppender, ch.qos.logback.core.rolling.RollingFileAppender, ch.qos.logback.classic.net.SyslogAppender and ch.qos.logback.classic.net.SMTPAppender. See the Logback appenders reference for their properties.

Writing log messages

Once configured, use the standard logging API:

import logging

logger = logging.getLogger(__name__)
logger.info("Started processing order %s", order_id)
logger.warning("Slow response from %s", service)

The adapter formats messages with Python’s % arguments and then passes them to Logback, so %s placeholders and lazy formatting work as usual.

Capturing log messages in tests

Use capture_logs to capture Python and framework Logback messages without importing Java logging APIs:

import logging
from logback import capture_logs

logger = logging.getLogger(__name__)
with capture_logs(logger, level="TRACE") as records:
    logger.warning("Processing request")

assert records[0].getMessage() == "Processing request"
assert records[0].levelno == logging.WARNING

The argument can also be a logger name; omit it to capture the root logger. The optional level accepts the same names and numbers as dictConfig. It temporarily changes the Java logger level and restores the previous level, including inherited levels, even when the body raises an exception. Python’s own logger level still controls Python calls. Existing appenders and propagation remain unchanged.

The returned list is populated with Python logging.LogRecord values only when the scope exits. Java event threads never call Python to capture a message. Records preserve the logger name, formatted message, timestamp and level; TRACE uses levelno=5 and levelname="TRACE". Emitter-thread and caller information are not available.

Complete requests and await or join asynchronous producers before leaving the scope. Do not reconfigure logging while capture is active or overlap level-changing scopes on the same logger across threads. Capturing requires the Java Logback backend; it raises RuntimeError when that backend is unavailable.

Combining with logback.xml

Micronaut applications can also ship a logback.xml in the config directory. The shared Logback context applies loggers and appenders declared there to Python loggers too because the adapter delivers Python records to that context. Use logback.xml for appenders that need nested configuration and dictConfig for settings you want to keep in Python.

12 Testing

Pyronaut supports JUnit 5 tests, pytest tests, or both through the JUnit Platform. Use pyronaut test when tests need the Micronaut classpath, processed sources, test resources, or Micronaut test integration.

If you usually use pytest, keep using it: write ordinary test_*.py modules with fixtures, parametrization and marks, and use the MicronautTest fixture described in Using MicronautTest when a test needs a running application. The JUnit 5 Python module style described below trades pytest’s fixture model for direct dependency injection into the test module; it is the better fit for direct-source tests and for tests that share an application context across many test functions.

Selecting a test engine

Configure the engine under [tool.pyronaut.test]:

[tool.pyronaut.test]
engine = "both" # junit|pytest|both

The default is both, preserving the current behavior. junit runs only JUnit Jupiter tests, pytest runs only pytest tests, and both runs both engines in one JUnit Platform launch.

When you write JUnit tests as Python modules, you can use module-level MicronautTest() and JUnit lifecycle annotations such as BeforeAll and BeforeEach. Pytest tests use pytest fixtures, scopes, parametrization, marks, and plugins. JUnit owns a module-level MicronautTest() module and excludes it from pytest discovery when both engines are enabled.

Add the pytest integration to the test scope:

[tool.pyronaut.dependencies]
test = [
  "io.micronaut.pyronaut:micronaut-pyronaut-pytest",
  "io.micronaut.test:micronaut-test-junit5"
]

Run all tests:

pyronaut test

VS Code’s Python pytest support invokes pytest directly and is not suitable for Micronaut-backed Pyronaut tests. Use the Pyronaut VS Code Test Explorer extension when running these tests from VS Code. See VS Code Test Explorer Extension.

pyronaut test performs install and process preflight, runs configuration validation for the test scenario, starts configured project test resources, and delegates discovery to the configured engines. For direct sources, Test Resources starts only when runtime dependencies and inline runtime @AppConfig declarations identify a missing property supported by an inferred provider. Use --disable-test-resources to disable either form of automatic orchestration.

JUnit 5 Python modules

The JUnit engine supports Python modules as JUnit 5 tests. Invoke MicronautTest() at module level. Top-level functions whose names start with test become test methods, while helper and lifecycle functions are also defined at module level. Injected values are available through their module-level attributes.

from typing import Annotated

from jakarta.inject import Inject
from micronaut.context import ApplicationContext
from micronaut.test.extensions.junit5.annotation import MicronautTest
from org.junit.jupiter.api import BeforeEach

MicronautTest()

context: Annotated[ApplicationContext, Inject]

@BeforeEach
def verify_context():
    assert context.isRunning()

def test_context():
    assert context.isRunning()

JUnit module tests can run in direct-source mode. They do not use pytest fixtures or require a Python virtual environment.

Direct JUnit 5 tests

For a small application, you can test Java or Python sources without a project manifest. By default, Pyronaut recursively discovers *Test.java files for Java and *Test.py or test_.py modules for Python from the current working directory:

pyronaut test Foo.java
pyronaut test Foo.py

You can also supply test sources explicitly after --, which is useful for custom test layouts:

pyronaut test Foo.java -- FooTest.java
pyronaut test Foo.py -- FooTest.py
pyronaut test -t Foo.java -- *Test.java

An explicit -- without test sources remains invalid.

Pyronaut compiles direct tests and executes them in memory through the JUnit Platform. Python direct tests use the JUnit engine and can use module-level MicronautTest(); Pyronaut does not invoke pytest because pytest requires test files on disk. Direct Java runs disable Python runtime infrastructure automatically; Python remains enabled by default for Python tests.

Use --continuous or -t to rerun direct tests when application or test sources change. The console prints execution progress and a final test summary.

Direct tests write JUnit XML and HTML reports to pyronaut/reports/tests and print a terminal link to the HTML report. Pyronaut includes container startup failures that prevent tests from starting in the report. Pass a directory after --report to choose another location:

pyronaut test --report Foo.java -- FooTest.java
pyronaut test --report build/test-reports Foo.java -- FooTest.java

Project test discovery

Pyronaut discovers Python tests from the configured python-test source directory. The default directory is tests.

[tool.pyronaut.sources]
python-test = "tests"

Use --tests for selector-style filtering:

pyronaut test --tests tests/test_controller.py::test_index

Reports

Pyronaut writes test reports under:

__pyronaut__/reports/tests/

Important files include:

  • index.html

  • junit.xml

  • .pyronaut-last-nodeid.txt

  • events.ndjson

With engine = "both", the JUnit XML and HTML reports contain results from both engines. The node-id and event files remain pytest-specific.

Console output

pyronaut test keeps the terminal for progress: each test collapses into a pass, fail, or skip line as it finishes, failures print their assertion message beneath, and a summary with a link to the HTML report follows. Pyronaut captures everything that the application and test frameworks write to the console during a test (Micronaut logging, GraalPy diagnostics, and print calls) and attributes the output to that test in the reports: the <system-out> and <system-err> elements of junit.xml, the collapsible sections of index.html, and test_output events in events.ndjson. Output produced outside any test, such as the pytest session banner and application bootstrap logging, is kept in console.log next to the other reports.

To stream that output to the console instead, pass --verbose (which also enables trace logging) or set:

[tool.pyronaut.test]
verbose = true

Streaming disables the live progress display; Pyronaut reports tests as plain lines.

Context tests

Use MicronautTest with the pytest fixture integration when a pytest needs a Micronaut ApplicationContext, injected beans, an EmbeddedServer, or configuration properties. Use pyronaut.requests or the requests shim for HTTP tests against the embedded server.

12.1 Using MicronautTest

MicronautTest is the Python-side configuration object used by Pyronaut’s pytest fixture support. It starts a Micronaut application context for a pytest and exposes it through a Python wrapper.

import pytest

from pyronaut.test import MicronautTest, micronaut_test_fixture


@pytest.fixture
def my_context(request):
    fixture = micronaut_test_fixture(
        request,
        MicronautTest(
            environments=["test"],
            properties={"custom.property": "test_value"},
        ),
    )
    yield fixture
    fixture.stop()

MicronautTest() mirrors the options of the Java @MicronautTest annotation. The environments, packages, start_application, properties and sql options are fully supported by the pytest integration.

The pytest fixture integration does not currently drive Micronaut Test’s per-test transaction and context-rebuild lifecycle. The integration accepts transactional, rollback and rebuild_context for compatibility, but ignores them. It also does not run Sql scripts declared with Sql.Phase.AFTER_ALL. Use explicit clean-up in a fixture, or write the test as a JUnit 5 Python module (see Testing), when transactional rollback is required.

Common options

MicronautTest(
    environments=["test"],
    packages=[],
    transactional=False,
    rollback=True,
    rebuild_context=False,
    start_application=True,
    resolve_parameters=True,
    properties={}
)

environments defaults to ["test"]. The fixture passes additional properties into the Micronaut context during bootstrap.

Bean lookup

The fixture returns an application context wrapper. You can look up beans by Java class name, Java type, or Python class when Pyronaut can resolve the Python type to its generated bean name.

import java


def test_environment(my_context):
    env = my_context["io.micronaut.context.env.Environment"]
    assert "test" in env.getActiveNames()


def test_environment_by_java_type(my_context):
    Environment = java.type("io.micronaut.context.env.Environment")
    env = my_context[Environment]
    assert env is not None

You can also delegate directly to the underlying Micronaut context:

def test_context_running(my_context):
    assert my_context.isRunning()

Embedded server

When start_application=True, an EmbeddedServer is available from the context:

def test_server_port(my_context):
    server = my_context["io.micronaut.runtime.server.EmbeddedServer"]
    assert server.getPort() > 0

For HTTP tests, bind requests to the context so relative URLs target the embedded server:

import requests


@pytest.fixture
def client(my_context):
    return requests.with_context(my_context)


def test_health(client):
    response = client.get("/health")
    assert response.status_code == 200

SQL scripts

Use Sql with MicronautTest to execute SQL scripts during the pytest lifecycle. Micronaut resolves the scripts with its ResourceLoader, so classpath resources such as classpath:sql/seed-data.sql work the same way they do with Micronaut Test on the JVM.

import pytest

from pyronaut.test import MicronautTest, Sql, micronaut_test_fixture


@pytest.fixture
def my_context(request):
    fixture = micronaut_test_fixture(
        request,
        MicronautTest(
            start_application=False,
            sql=Sql(
                scripts="classpath:sql/seed-data.sql",
                phase=Sql.Phase.BEFORE_EACH,
            ),
        ),
    )
    yield fixture
    fixture.stop()

Pass a list when you need multiple scripts or phases:

MicronautTest(
    sql=[
        Sql("classpath:sql/init-db.sql", phase=Sql.Phase.BEFORE_EACH),
        Sql("classpath:sql/seed-data.sql", phase=Sql.Phase.BEFORE_EACH),
    ],
)

Sql defaults to the default datasource and javax.sql.DataSource. Use data_source_name or resource_type when the test needs another SQL resource. The pytest integration executes Sql.Phase.BEFORE_ALL, BEFORE_EACH and AFTER_EACH; see the warning above regarding AFTER_ALL.

12.2 Test Resources and Docker

Pyronaut can orchestrate Micronaut Test Resources for pyronaut dev and pyronaut test. This is useful for tests and local runs that need services such as databases without hard-coding connection settings. pyronaut run does not infer, start, or consume Test Resources.

Enable test resources in pyproject.toml:

[tool.pyronaut.test-resources]
enabled = true

When enabled in a project, pyronaut install resolves a test-resources-server classpath and pyronaut dev or pyronaut test starts a server when needed. The CLI propagates test resources client settings to delegated JVM processes.

For direct-source execution without a pyproject.toml, Pyronaut resolves the server and client only when runtime dependencies and inline runtime @AppConfig declarations identify a missing property supported by an inferred provider. This applies to direct dev and test only.

Lifecycle

Default behavior:

  • pyronaut dev and pyronaut test start an owned server on demand.

  • Owned servers stop when the owning development or test session exits.

  • If an external project-local server is already running, the CLI attaches to it instead of claiming ownership.

  • Shared servers stay running across command invocations.

Pyronaut writes project-local metadata under:

.micronaut/test-resources/test-resources.properties
__pyronaut__/test-resources-session.json

Pyronaut writes logs to .micronaut/test-resources/logs by default unless you configure logs-dir.

The server pulls and starts containers in its own process, so pyronaut dev and pyronaut test tail that log while they wait and report the image pulls, container starts and failures alongside their own progress output. Configuring logs-dir moves the log the launchers follow along with the log itself.

Configuration

[tool.pyronaut.test-resources]
enabled = true
explicit-port = 18080
infer-classpath = true
client-timeout = 60
shared-server = false
logs-dir = ".micronaut/test-resources/logs"
startup-optimization = "none" # none|auto|leyden|cds
additional-modules = ["jdbc-mysql"]

startup-optimization controls JVM start-up optimisation for the server process. auto and cds use class-data sharing when the JDK supports it; Pyronaut accepts leyden but currently falls back to cds with a warning. logs-dir applies to the server process; the launcher’s own log output is always written under .micronaut/test-resources/logs in the project.

infer-classpath lets Pyronaut infer test resources modules from application dependencies. Use additional-modules when Pyronaut cannot infer a module or when you want to select modules explicitly. An entry can be a short Test Resources module name such as jdbc-mysql, a group:artifact coordinate, or a group:artifact:version coordinate:

  • Short names and versionless io.micronaut.testresources coordinates use the Test Resources version.

  • Versionless coordinates in any other group use the version managed by the Micronaut platform BOM ([tool.pyronaut.platform]) or a configured BOM, for example "io.micronaut.langchain4j:micronaut-langchain4j-ollama-testresource". If no BOM manages the module, add an explicit version.

  • An explicit version is always used as written.

Standalone server commands

Use the explicit server command when you want a reusable server:

pyronaut test-resources-server start
pyronaut test-resources-server status
pyronaut test-resources-server stop

Set PYRONAUT_TEST_RESOURCES_DISABLED=true to disable automatic orchestration for a command invocation. For direct-source execution, --disable-test-resources is also authoritative.

12.2.1 Docker Requirements

Micronaut Test Resources uses Testcontainers, so make Docker or a compatible container runtime available before pyronaut dev or pyronaut test provisions containers.

Verify the runtime first:

docker ps
docker info

If these commands cannot connect to a daemon, Test Resources fails before it can start the application dependency.

macOS

On macOS, start Docker Desktop or another Docker-compatible runtime before running Pyronaut commands. If you use an alternative runtime that exposes a non-default socket, ensure the shell running Pyronaut has the correct Docker environment variables.

For example, when a runtime requires a custom host:

export DOCKER_HOST=unix:///path/to/docker.sock
docker ps
pyronaut test

Make sure the runtime has enough memory and disk space for the images used by your test resources modules. The first run may pull images and take longer than later runs.

Linux

On Linux, ensure the Docker service or rootless Docker daemon is running:

docker ps

If you install Docker in rootful mode, give the user running Pyronaut permission to access the Docker socket. Common setups add the user to the docker group and require a new login session before the permission is active.

For rootless Docker, ensure DOCKER_HOST points at the rootless socket when it is not the CLI default.

CI

In CI, run Pyronaut tests on an executor that supports Docker-in-Docker, a sibling Docker daemon, or a container runtime service compatible with Testcontainers. Cache image layers when possible, but do not cache .micronaut/test-resources state across unrelated projects unless you intentionally use shared-server mode.

13 Pyronaut Requests

Pyronaut Requests provides a subset of the Python requests API and delegates HTTP work to the Micronaut HTTP client. Code that uses the supported API can keep import requests, and the client can also target an embedded server in tests.

If standard Requests is installed in the virtual environment, import requests selects that package without replacing its transports, Session, or exceptions. The requests.with_context extension remains available for Micronaut-backed test clients. Use from pyronaut import requests to select the Micronaut-backed API explicitly, regardless of installed packages.

Add it to the scope where you need it. For application code declare it under runtime; for tests only, under test:

[tool.pyronaut.dependencies]
runtime = [
  "io.micronaut.pyronaut:micronaut-pyronaut-requests"
]

Direct-source files can declare it inline with Dependency(group="io.micronaut.pyronaut", module="micronaut-pyronaut-requests").

Quick start

from pyronaut import requests

response = requests.get("https://httpbin.org/get", params={"q": "pyronaut"})
print(response.status_code, response.json())

import pyronaut.requests as requests also selects the Micronaut-backed API explicitly.

Supported API

  • Functions: request, get, post, put, patch, delete, head, options, and Session (usable as a context manager)

  • Request options: params, data, json, files, headers, cookies, auth (basic auth tuple), timeout, allow_redirects, verify

  • Response: status_code, reason, ok, url, headers (case-insensitive, iterable), content, text, json(), raise_for_status()

  • Exceptions under requests.exceptions: RequestException, ConnectionError, Timeout, HTTPError

Not supported: a per-request proxies argument, streaming responses (stream=True), and SSL contexts beyond verify=False. For proxies, use standard proxy environment variables or set Session.proxies.

When a request uses timeout, verify or allow_redirects values that differ from the defaults, Pyronaut Requests creates a short-lived Micronaut client with those settings and closes it after the request.

Typed JSON

response.json() returns Python dict and list values. Pass a class to deserialize with Micronaut Serialization, using the same JsonMapper configuration as the application:

from dataclasses import dataclass

from micronaut.serde.annotation import Serdeable


@Serdeable
@dataclass
class Message:
    message: str


response = client.get("/hello/John")
message = response.json(Message)
assert message.message.startswith("Hello")

Use with MicronautTest

requests.with_context(context) binds a client to a running Micronaut application context. Relative URLs resolve against the EmbeddedServer in that context and JSON uses the context’s JsonMapper:

import pytest
import requests

from pyronaut.test import MicronautTest, micronaut_test_fixture


@pytest.fixture
def my_context(request):
    fixture = micronaut_test_fixture(request, MicronautTest())
    yield fixture
    fixture.stop()


@pytest.fixture
def client(my_context):
    return requests.with_context(my_context)


def test_hello_world(client):
    response = client.get("/hello/John")
    assert response.status_code == 200
    assert response.json()["message"]

See Using Requests for Testing for more test patterns.

Client lifecycle

The library registers Micronaut HTTP clients in a registry. Its shutdown listener closes them when an application context stops, and an atexit hook closes any clients that remain at interpreter exit. Use Session as a context manager (with requests.Session() as session:) to close a session’s client deterministically.

The shutdown listener closes every registered client when any application context stops. In a test suite that starts several contexts in one JVM, create clients with with_context per fixture rather than sharing module-level sessions across contexts.

def test_absolute_url(my_context):
    server = my_context["io.micronaut.runtime.server.EmbeddedServer"]
    base_url = f"http://localhost:{server.getPort()}"

    response = requests.get(f"{base_url}/")
    assert response.status_code == 200

JSON responses

Untyped response.json() returns Python-native dictionaries and lists. Pass a target type to deserialize with Micronaut Serialization:

class Message:
    def __init__(self, message: str):
        self.message = message


def test_typed_json(client):
    response = client.get("/hello/John")
    message = response.json(Message)
    assert message.message.startswith("Hello")

The library’s shutdown listener closes its clients when a Micronaut context stops; see Pyronaut Requests for the lifecycle details.

14 Pyronaut CLI Reference

Pyronaut CLI v2 is a process-oriented toolchain. The pyronaut command is a Python orchestrator that delegates work to focused executables:

  • pyronaut-install

  • pyronaut-processor

  • pyronaut-dev

  • pyronaut-run

  • pyronaut-test

  • pyronaut-jar-build (used by pyronaut build --jar)

  • pyronaut-native-build (used by pyronaut build --native)

  • pyronaut-validate-config (used by pyronaut validate-config)

  • pyronaut-test-resources-server (used by pyronaut test-resources-server)

This separation keeps dependency resolution, processing, run/test execution, and native-image orchestration deterministic and independently testable.

Platform support

Phase 1 supports macOS and Linux for the Pyronaut runtime commands. The pyronaut create command additionally supports the published Micronaut Launch SDK for Windows x64.

Command syntax

pyronaut [--version] [--allow-draft-release] [--tui [--smoke|--non-interactive]] <setup|update|doctor|clean|install|process|dev|run|test|build|create|validate-config|test-resources-server> [args...]

Quick-start workflow

pyronaut install --project-dir /path/to/app
pyronaut process --project-dir /path/to/app
pyronaut dev --project-dir /path/to/app
pyronaut test --project-dir /path/to/app

Installed SDK wheels require a successful global pyronaut setup before this workflow. Source-checkout launchers remain usable for repository development.

Project layout

Pyronaut reads project layout settings from [tool.pyronaut.sources] in pyproject.toml. Directory values are relative to the project root.

Defaults:

  • python = "src"

  • python-test = "tests"

  • java = "src-java"

  • java-test = "test-java"

  • resources = "config"

  • test-resources = "tests-config"

  • additional-resources = []

  • additional-test-resources = []

Example:

[tool.pyronaut.sources]
python = "app"
python-test = "test/python"
java = "src/main/java"
java-test = "src/test/java"
resources = "app-config"
test-resources = "tests-config"
additional-resources = ["views", "assets"]
additional-test-resources = ["tests-fixtures"]

additional-resources is a list of extra application resource directories. Pyronaut includes these directories for dev, run, and test scopes, watches them for auto-restart in dev, includes them in lifecycle validation defaults, and stages them into JVM wheels and Docker images.

additional-test-resources is a list of extra test-only resource directories. Pyronaut includes these directories for test scope, watches them for auto-restart in dev and test, and includes them in test lifecycle validation defaults.

The commands pyronaut process, pyronaut dev, pyronaut run, and pyronaut test use these settings, as do lifecycle validation, auto-restart file watching, and build staging for wheels and Docker images.

Command reference

pyronaut setup

Provisions the complete SDK before any project command runs:

pyronaut setup [--local-repository <dir>] [--offline] [--refresh] [--progress <auto|on|off>]

Setup provisions the packaged/default GraalVM JDK first, so you do not need JAVA_HOME or a preinstalled Java runtime. It then locates the exact GraalPy interpreter the SDK was built with (shown by pyronaut --version as GraalPy Interpreter, for example graalpy3.13-25.4.4). Setup reuses a matching GraalPy when the CLI itself runs on one, when ~/.pyronaut/sdks/<version> already contains one, or when pyenv already has that version installed. Otherwise it runs pyenv install <version> when pyenv is available, and falls back to downloading the checksum-verified GraalPy release from GitHub into ~/.pyronaut/sdks/<version>. Delegated commands receive that interpreter through PYRONAUT_PYTHON_EXECUTABLE and PATH; a project .venv takes precedence. It then caches pyronaut-dev, pyronaut-run, and pyronaut-run-python, seeds wheel-bundled Pyronaut artifacts into the selected Maven repository, and resolves the wheel’s portable dependency descriptors. Pyronaut writes validated state atomically below ~/.pyronaut/setup.

The default remote repository is Maven Central. Snapshot SDK versions also use https://central.sonatype.com/repository/maven-snapshots/. Configure a replacement list in ~/.pyronaut/settings.toml:

[maven]
repositories = ["mavenCentral", "https://repo.example.com/snapshots/"]

--refresh re-resolves and rewrites setup state while reusing healthy downloaded JDK, GraalPy, and native images. --offline performs no JDK, GraalPy, native-image, or Maven downloads and therefore succeeds only when every required component is already cached. When setup is missing, corrupt, or stale, execution commands exit with code 8 and print Pyronaut setup is missing or stale. Run pyronaut setup.

pyronaut update

Replaces the installed Pyronaut wheel with a newer release from GitHub and provisions it:

pyronaut update [<version>] [--check] [--keep-old] [--local-repository <dir>] [--progress <auto|on|off>]

Without a version, update selects the newest release that carries a Pyronaut wheel. A stable installation only moves to stable releases. When the installed version is a pre-release (a milestone, release candidate, or snapshot, or a release that GitHub marks as a pre-release), update may also select a newer pre-release. Pass a version such as 1.0.0 or v1.0.0 to install that release instead, including an older one.

Update then:

  1. downloads the release’s wheel and installs it with pip into the Python environment that runs pyronaut;

  2. runs the new version’s pyronaut setup, which downloads the matching pyronaut-dev, pyronaut-run, and pyronaut-run-python launchers and prepares the Maven repository recorded by the previous setup;

  3. removes the launchers, tool runtimes, setup state, and Pyronaut Maven artifacts of every version older than the installed one.

Update never removes versions newer than the one it installs, nor a launcher version pinned by [native-images].version. If setup fails, the new wheel stays installed and older versions are kept; fix the reported problem and run pyronaut setup.

--check reports an available update without installing it, and --keep-old skips the removal of older versions. Update reads releases through the GitHub API; set GH_TOKEN or GITHUB_TOKEN when the API requires authentication.

pyronaut doctor

Checks the local environment without changing it and prints one pass/warn/fail row per check. A non-passing row includes a suggested fix when Pyronaut can identify one:

pyronaut doctor [--project-dir <dir>] [--json] [--offline] [--progress <auto|on|off>]

Run it first when pyronaut setup or a project command fails. Unlike the execution commands it never requires valid setup state, so it can diagnose a missing or stale setup.

The checks, in order:

  • Python: the interpreter running the CLI is 3.10 or newer.

  • Pyronaut SDK: the installed wheel version and whether the cached setup state below ~/.pyronaut/setup is valid for it (suggests pyronaut setup, or pyronaut setup --refresh when stale state exists).

  • GraalVM JDK: the discovery used by pyronaut setup --offline (JAVA_HOME, ~/.pyronaut/sdks, SDKMAN, jenv, Gradle JDKs) finds a GraalVM JDK 25+. The check reports a warning when it silently ignores JAVA_HOME because it does not point to a compatible GraalVM.

  • GraalPy: inside a project, the check verifies that .venv uses GraalPy; otherwise it checks the GraalPy recorded by pyronaut setup, or a GraalPy selected by PYENV_VERSION, by the global ~/.pyenv/version file, or found on PATH. A GraalPy other than the version bundled with the SDK is a warning.

  • Interpreter: the check verifies that the pieces agree. PYRONAUT_PYTHON_EXECUTABLE must point at an existing GraalPy, an activated VIRTUAL_ENV must be the project .venv, and the .venv must use the currently selected GraalPy (the check reports a .venv that remained after pyenv global moved to another version, or whose base interpreter someone removed).

  • Native launchers: Pyronaut caches pyronaut-dev, pyronaut-run, and pyronaut-run-python below ~/.pyronaut/bin for the configured version and platform.

Inside a project, Pyronaut adds the following checks:

  • pyproject.toml: the file parses and its [tool.pyronaut] settings are valid.

  • Classpath manifests: the manifests written by pyronaut install exist.

  • Generated state: the check verifies that the manifests are current. Classpath entries that no longer exist (the Maven repository changed) fail the check; a pyproject.toml edited after the last pyronaut install is a warning, because the preflight of dev, run and test only checks that the manifests exist. The check reports sources newer than the processed classes for information because dev, run, and test process changed sources automatically.

  • Threading: the application configuration in config/application.toml (or application.properties) is read the way the runtime reads it. An executor with virtual = true fails the check because GraalPy cannot run Python code on virtual threads, and invalid micronaut.python.pool values fail it. The row reports the effective context pool size, executor overrides, and the deployment mode from [tool.pyronaut.packaging] and [tool.pyronaut.toolchain]. Configuration kept in application.yml is not inspected and produces a warning.

  • Python packages: a smoke test of every package declared in [project].dependencies. A probe runs inside the project .venv (that is, on the GraalPy that the application uses), resolves each distribution, derives its importable modules, and imports them concurrently from as many threads as the configured context pool would use (micronaut.python.pool.size, or twice the CPU count by default, one thread when the pool is disabled). Missing packages fail the check with the exact pip install command; import errors fail it with the first error; the check warns about packages that ship native extensions, using wording for the configured deployment mode (native extensions are experimental on GraalPy and in native images).

  • GraalPy compatibility: each declared package is looked up in the package test results that GraalPy publishes per release at https://graalpy.org/python-developers/compatibility/. Packages that fail to install on the project’s GraalPy release, or pass fewer than 90% of their tests there, produce a warning; the check lists unknown packages as untested. The check reads the release from the .venv interpreter, falling back to the GraalPy bundled with the SDK. Pyronaut caches the CSV below ~/.pyronaut/graalpy-compatibility for a week; --offline uses only the cache and never downloads.

  • pytest: pytest is importable from the project .venv.

The remaining checks run everywhere:

  • Proxy: the proxy in effect (environment variables, ~/.pyronaut/settings.toml, or ~/.m2/settings.xml) is a well-formed http(s)://host:port URL. Conflicting HTTPS_PROXY/https_proxy values or an incomplete [proxy] table are warnings. Credentials are never printed.

  • Docker: the daemon answers docker version. Pyronaut needs Docker only for test resources and pyronaut build --docker, so a missing CLI or unreachable daemon is a warning.

Project checks run for the current directory when it contains a pyproject.toml, and always for an explicit --project-dir.

Pyronaut writes the human-readable rows to stderr using the same live progress display as pyronaut setup; it writes the summary line to stdout. --json instead writes a single JSON document to stdout for tooling:

{
  "pyronaut": "0.0.3",
  "platform": "macos-aarch64",
  "project": "/path/to/app",
  "status": "fail",
  "summary": {"pass": 8, "warn": 1, "fail": 1},
  "checks": [
    {
      "id": "install",
      "title": "Classpath manifests",
      "status": "fail",
      "detail": "3 of 3 missing in /path/to/app/__pyronaut__: resolved-build-dependencies, resolved-runtime-dependencies, resolved-test-dependencies",
      "fix": "Run pyronaut install",
      "data": {"directory": "/path/to/app/__pyronaut__"}
    }
  ]
}

Each check carries a stable id (python, pyronaut, graalvm, graalpy, interpreter, launchers, pyproject, install, state, threading, packages, compat, pytest, proxy, docker) and check-specific data, for example the selected javaHome, the per-package probe results with their import errors, or the compatibility verdict per package.

Exit codes follow the conventions listed under Exit code conventions below: 0 when no check fails (warnings do not fail the command), 8 when at least one check fails, and 2 for an unknown option.

pyronaut create

Creates a Python application by delegating to the Micronaut Launch native CLI:

pyronaut create [NAME] [options]

Pyronaut supplies --lang python, --build pyronaut, and --test pytest automatically. Supported options are:

  • --features <feature[,feature…​]> (repeatable)

  • --inplace

  • --list-features

  • --verbose

  • --stacktrace

--lang, --build, --test, and --jdk are intentionally not exposed. Use pyronaut create --list-features for the Python-compatible feature catalog; the command removes known reflection-dependent and JVM-only features before it shows the catalog, while Micronaut Starter performs final validation.

The command does not require pyronaut setup. It first looks for an exact matching Micronaut candidate in SDKMAN_DIR/candidates/micronaut/<version> (default ~/.sdkman), then in ~/.pyronaut/sdks/micronaut/<version>. If neither contains a matching executable, the command downloads the platform-specific archive from Micronaut Starter releases and installs it in the latter location.

Downloads use the same proxy settings, retry behavior, and progress indicator as the rest of the CLI. The first download prints Project Creation Tooling is being installed. Python creation requires Micronaut Platform 5.2.0 or newer. Published native archives are available for macOS x64/arm64, Linux x64, and Windows x64. Stage a locally built snapshot at the exact versioned SDK path before using it.

pyronaut install

Resolves dependencies into the configured local Maven repository and writes scoped manifests under pyronaut/.

Before resolving Java dependencies, pyronaut install prepares the project Python environment when the project declares Python dependencies in [project].dependencies, PEP 735 [dependency-groups], or a requirements.txt file, or has a Python test directory:

  • It creates .venv in the project directory with the GraalPy interpreter recorded by pyronaut setup, unless .venv already exists.

  • It runs pip install inside .venv for every declared requirement and requirements.txt. When the project has Python tests but does not declare pytest, Pyronaut adds pytest because pyronaut test imports it from .venv.

  • It records the installed declarations in .venv/.pyronaut-requirements.json and skips pip until they change. --refresh reinstalls; --offline skips pip.

An existing .venv that GraalPy did not create fails the command, because the embedded runtime cannot use its packages. Remove it and run pyronaut install again.

By default, Pyronaut installs dependency artifacts into Maven local (~/.m2/repository, or the path configured by the maven.repo.local system property).

Common options:

  • --project-dir <dir>: project root (default .)

  • --local-repository <dir> (alias --local-repo): local Maven repository directory for resolved dependency artifacts; relative paths are resolved against the project root

  • --scope <build|runtime|development-runtime|test|test-resources-server|all>: restrict resolution scope

  • --dependencies: render dependency tree output

  • --progress <auto|on|off>: progress display mode

  • --color <auto|always|never>: dependency output color mode

  • --refresh: force re-resolution and manifest rewrite without clearing the selected local repository

  • --no-cache: bypass Pyronaut manifest cache reads before rewriting manifests

  • --offline: resolve using offline repository mode

When several scopes are selected, their Maven resolutions run in parallel. On an interactive terminal, pyronaut install renders one live row per scope (Collecting … while the dependency graph is read, then Resolving … resolved/total artifacts), a byte-level bar for every in-flight download, and a row for the schema bundling and editor-stub generation that follow. Finished work collapses into permanent [elapsed] ✓ … lines; see Progress output. Redirected and CI output remains deterministic and uses plain summary lines without cursor-control sequences.

Proxy configuration:

pyronaut setup and pyronaut install use the configured proxy for Maven dependency resolution; setup also applies it to GraalVM, GraalPy, and native-launcher downloads. This includes dependencies resolved from the global [maven].repositories list and project tool.pyronaut.repositories. Pyronaut discovers proxy configuration in this order:

  1. Environment variables: HTTPS_PROXY, https_proxy, HTTP_PROXY, http_proxy

  2. Pyronaut user settings: ~/.pyronaut/settings.toml

  3. Maven user settings: ~/.m2/settings.xml

Environment proxy URLs may include credentials and may omit the scheme; Pyronaut uses http when the scheme is absent. NO_PROXY or no_proxy configures hosts that should bypass the proxy. Comma-separated and pipe-separated bypass lists are both accepted.

export HTTPS_PROXY=https://user:password@proxy.example.com:8443
export NO_PROXY=localhost,127.0.0.1,*.internal.example.com
pyronaut install --project-dir /path/to/app

For a persistent Pyronaut-specific proxy configuration, create ~/.pyronaut/settings.toml:

[proxy]
url = "https://user:password@proxy.example.com:8443"
nonProxyHosts = "localhost|127.0.0.1|*.internal.example.com"

The same file can also split the proxy into individual fields:

[proxy]
protocol = "https"
host = "proxy.example.com"
port = 8443
username = "user"
password = "password"
noProxyHosts = "localhost,127.0.0.1,*.internal.example.com"

If neither environment variables nor ~/.pyronaut/settings.toml define a proxy, pyronaut install reads the first active Maven proxy from ~/.m2/settings.xml. If no proxy is marked active, Pyronaut uses the first proxy entry.

<settings>
  <proxies>
    <proxy>
      <active>true</active>
      <protocol>https</protocol>
      <host>proxy.example.com</host>
      <port>8443</port>
      <username>user</username>
      <password>password</password>
      <nonProxyHosts>localhost|127.0.0.1|*.internal.example.com</nonProxyHosts>
    </proxy>
  </proxies>
</settings>

Generated manifests:

  • pyronaut/resolved-build-dependencies

  • pyronaut/resolved-runtime-dependencies

  • pyronaut/resolved-test-dependencies

  • pyronaut/resolved-test-resources-server-dependencies

Manifest entries point at artifacts in the selected local repository. Build-wheel and Docker packaging copy those artifacts into the packaged application’s pyronaut/m2-repository directory and rewrite the packaged manifest to use project-relative paths.

Managed runtime defaults:

  • When the Micronaut platform manages dependency versions, pyronaut install adds io.micronaut.toml:micronaut-toml to the runtime classpath by default, so application.toml in the configured resources directory works without an explicit dependency declaration.

  • pyronaut install also adds io.micronaut:micronaut-context-python to runtime by default.

  • pyronaut install also adds io.micronaut:micronaut-inject-python and io.micronaut:micronaut-context-python to build by default.

  • pyronaut install also adds io.micronaut.openapi:micronaut-openapi to build and its annotations to runtime, enabling OpenAPI processing without a project-specific processor declaration.

  • pyronaut install also adds org.junit.platform:junit-platform-launcher and org.junit.jupiter:junit-jupiter-engine to test by default.

  • Commands that need a GraalVM JDK resolve one through the shared toolchain flow described in GraalVM toolchains.

Editor support:

  • pyronaut install also materializes a project-local JSON schema at pyronaut/schemas/pyronaut-pyproject.schema.json.

  • pyronaut install prepends a Taplo schema directive to pyproject.toml pointing at that schema.

  • If application.toml exists in the configured resources directory, pyronaut install also builds pyronaut/schemas/micronaut-application.schema.json from the Micronaut configuration schemas present on the resolved runtime classpath and prepends a schema directive to that file.

  • Pyronaut merges runtime configuration schemas by their x-micronaut.prefix path, so it combines overlapping contributors such as micronaut.server and micronaut.server.netty into one rooted schema tree.

Annotation processor options:

  • During installation, Pyronaut discovers TypeElementVisitor.getSupportedOptions() from the resolved processor classpath and caches the sorted option names under pyronaut/annotation-processor-options.properties.

  • Pyronaut flattens matching values from the Micronaut application environment (including application.toml, application.yml, and application.properties) to dotted keys and passes them to processing as -A compiler arguments. It ignores unrelated application configuration.

  • Pyronaut supplies the supported micronaut.openapi.views.spec option with swagger-ui.enabled=true,redoc.enabled=true by default, unless the application overrides it. This causes Pyronaut to generate Swagger UI and ReDoc HTML assets under META-INF/swagger/views.

  • pyronaut dev and direct-source pyronaut run <source> supply default static-resource routes for the generated YAML, Swagger UI, and ReDoc under /swagger/, /swagger-ui/, and /redoc/**. Explicit --property values or application configuration take precedence; project-mode pyronaut run does not add these routes automatically.

  • The test processing pass always passes micronaut.openapi.enabled=false, so Pyronaut generates OpenAPI files only for main sources.

  • pyronaut install also generates Python editor stubs under pyronaut/ide-stubs from the resolved runtime and test classpaths.

  • Python editor stub generation is configurable under [tool.pyronaut.ide-stubs] with enabled, ide, packages, exclude-patterns, and destination-dir.

  • ide defaults to vscode and currently supports vscode and pycharm.

  • exclude-patterns accepts wildcard matches against fully qualified Java type names and defaults to ["*ModuleInfo"] to skip generated module metadata classes.

  • Pyronaut records the resolved editor input set in pyronaut/resolved-editor-artifacts.json, including binary JAR and source JAR paths when available.

  • When you select ide = "vscode" without user-managed Pyright configuration, pyronaut install writes .vscode/settings.json with python.analysis.extraPaths pointing at the configured stub directory so Pylance can resolve Java-backed Python imports such as micronaut.http.annotation and jakarta.inject.

  • If pyrightconfig.json or [tool.pyright] already exists, pyronaut install leaves that configuration user-managed and records the skipped settings update in the editor stub report.

  • When ide = "pycharm", pyronaut install writes a generated .idea/pyronaut-editor-stubs.iml module and adds it to .idea/modules.xml so the stub directory is visible as a source root without rewriting the main project module.

  • Python editor stub generation is best effort. If Pyronaut cannot render a particular Java type cleanly, it skips that API surface and continues install processing.

  • Pyronaut writes detailed stub-generation warnings to pyronaut/reports/editor-stubs/stub-generation-report.txt instead of streaming them line-by-line to the console.

  • Existing user-managed #:schema …​ directives at the top of pyproject.toml are left untouched.

  • Existing user-managed #:schema …​ directives at the top of application.toml in the configured resources directory are left untouched.

  • Pyronaut removes older generated .taplo.toml files from previous installs to avoid conflicting schema associations. It leaves user-managed .taplo.toml files untouched.

pyronaut process

Processes source trees and generates metadata/classes via pyronaut-processor.

Common options:

  • --project-dir <dir>

  • --verbose: full diagnostics on failures

  • --incremental: enable incremental Python and Java compilation for this invocation

  • --no-incremental: disable incremental compilation for this invocation

  • --daemon: use the persistent compiler daemon for this invocation

  • --no-daemon: process in the current command process for this invocation

  • --no-cache: clear processor outputs and incremental state, then perform a full compilation without reusing either cache

  • merged source+test pass → pyronaut/test-classes

pyronaut clean

Removes generated project output.

pyronaut clean [--project-dir <dir>] [-f|--full]

By default pyronaut clean removes only what pyronaut process produces: classes, test-classes, test-sources, the incremental compiler state under incremental, and the processor input digests. Dependency manifests, the project-local Maven repository, schemas, IDE stubs, and reports are kept, so the next run, test, or process reprocesses the sources without reinstalling.

-f or --full removes the entire pyronaut directory (all generated state and caches) and the project .venv. Run pyronaut install again afterwards to recreate them.

For Maven and Gradle projects the command cleans target/pyronaut or build/pyronaut instead of pyronaut. The command refuses to run in a directory without a pyproject.toml, pom.xml, or Gradle build file.

pyronaut dev

pyronaut run

Common options:

  • Runs pyronaut-validate-config --scenario run before preflight by default.

Direct-source tests:

Direct tests automatically discover recursive *Test.java sources for Java and Python test modules named *Test.py or test_.py, based on the application language, so the common case does not need a separator:

pyronaut test Foo.java
pyronaut test Foo.py

The equivalent explicit syntax remains available for custom test layouts:

pyronaut test Foo.java -- FooTest.java
pyronaut test Foo.py -- FooTest.py
pyronaut test src/*.java -- test/*.java

The implicit search starts at the current working directory. An explicit -- with no test source is invalid; use the shorthand form when you want the default recursive test discovery.

Pyronaut compiles direct tests in memory and executes them through JUnit 5. Python direct tests use the Python compiler’s JUnit 5 integration; they do not invoke pytest or require a Python virtual environment. Java-only direct tests disable Python runtime beans unless you supply micronaut.python.enabled explicitly.

Use -t or --continuous to rerun direct tests after source changes:

pyronaut test -t Foo.java -- FooTest.java

Direct-source runs show each stage on the console: Processing main.py, test_main.py, the dependency declarations found in the sources (Found 1 dependency declaration … with each coordinate beneath it), one row per resolved scope while Maven fetches declared dependencies, the final processing pass and, for run/dev, Starting application until the context is up. Direct test output then includes per-test progress and a final execution summary. Direct mode writes JUnit XML and HTML reports to pyronaut/reports/tests and prints a terminal link to the HTML report. The report includes container startup failures that prevent tests from starting. Pass a directory after --report to choose another location. Project-based pyronaut test always writes to pyronaut/reports/tests (or target/pyronaut / build/pyronaut for Maven and Gradle projects).

pyronaut test --report Foo.java -- FooTest.java
pyronaut test --report build/test-reports Foo.java -- FooTest.java

Report artifacts:

  • pyronaut/reports/tests/index.html

  • pyronaut/reports/tests/junit.xml

  • pyronaut/reports/tests/.pyronaut-last-nodeid.txt

  • pyronaut/reports/tests/events.ndjson

pyronaut build

Builds a runnable FAT JAR, Python wheel, or Docker image.

Packaging selection:

  • --jar selects fat-jar

  • --mode jvm|native

  • --jvm (shortcut for JVM mode)

  • --native (shortcut for native mode)

  • --docker changes an explicit JVM/native selection to its Docker equivalent

  • --native-base[=<default|path|image|url>] selects the matching Crema equivalent and implies native mode

  • tool.pyronaut.packaging.format when no packaging-shaping flag is present

The configured values are fat-jar, wheel-jvm, wheel-native, wheel-crema, docker-jvm, docker-native, and docker-crema; the default is fat-jar for Java applications (Maven and Gradle projects, projects with Java sources, and direct .java sources) and wheel-jvm otherwise. Explicit flags take precedence. The spelling jar is not accepted in configuration. Pyronaut no longer accepts tool.pyronaut.build.mode: migrate JVM and native values to wheel-jvm and wheel-native (or the matching Docker/Crema format). tool.pyronaut.toolchain.type continues to select how CLI tools run, but no longer changes build output.

Common options:

  • --project-dir <dir>

  • --jar: build one runnable FAT JAR

  • --docker: build a container image instead of a wheel or native executable on the host

  • --static: static native container build; only valid with --native --docker

  • --native-base or --native-base=default: package against the configured Java or Python Crema runtime for the target platform

  • --native-base=<path>: build a custom Crema runtime at that path, package against it, and record it as tool.pyronaut.build.native-base (with format = "wheel-crema") in pyproject.toml

  • --docker --native-base=<image>: build and tag a custom Crema base image, build the application image on it, and record it as tool.pyronaut.build.docker.base-image (with format = "docker-crema") in pyproject.toml

  • --native-base=<HTTP(S)-URL>: package against an existing native launcher without building or recording a base

  • --pgo=<profile>[,<profile>…​]: compile a custom native base with profile-guided optimization using local or HTTP(S) .iprof profiles; repeatable, requires Oracle GraalVM, and only valid with --native-base=<path> or --docker --native-base=<image> (see Profile-guided optimization)

  • --name <name> / --version <version>: package metadata for direct Java or Python sources

  • --verbose: run native-image --verbose and print the exclusion summary (native mode)

  • --no-validate: explicitly bypasses lifecycle config validation

On a terminal every stage of a build is shown as a live row that collapses into a stamped summary line: configuration validation and the install/process preflight, Packaging FAT JAR · n/m dependencies, Downloading reachability metadata, Building native image · [3/8] Performing analysis (native-image’s own output flows above the row), Building wheel (pip’s output is shown only when it fails) and Building Docker image <tag> (Docker keeps the terminal while it builds). The final The ✓ … build complete line names the artifact, and the CLI follows it with an Install with: or Run it with: hint. Without a terminal the CLI prints the same information as plain lines. See Progress output.

JVM mode:

  • Runs pyronaut-validate-config --scenario production by default.

  • Builds a wheel using pip wheel.

  • Outputs artifacts to dist/.

FAT JAR (pyronaut build --jar):

  • Rejects --main-class and JVM/native, Docker, static, and native-base flags.

  • Packages application classes and resources before ordered runtime and production-launcher dependencies.

  • Produces dist/<project-name>-<version>.jar, runnable with java -jar.

  • Uses an indexed class loader without extracting dependency entries.

  • Preserves multi-release and package-manifest behavior, enumerates duplicate resources and services, and removes invalidated dependency signature/index metadata.

  • Requires the same compatible GraalVM JDK as a JVM wheel; a Python application includes the GraalPy runtime and consequently produces a larger artifact.

Native mode always uses io.micronaut.pyronaut.run.PyronautRunMain; --main-class is not supported.

wheel-native and docker-native are closed-world formats and reject a configured reusable base. wheel-crema and docker-crema use a configured custom base when present, otherwise the bundled language-specific default. Bare --native-base always selects the bundled default, even when a custom base is configured; name a path or image to build a custom base.

The SDK wheel contains JVM launchers only. Native project commands download pyronaut-dev on demand, and native production runs download pyronaut-run for Java projects or pyronaut-run-python for Python projects. Direct-source run, test, and dev commands use pyronaut-dev because it includes the compiler. Pyronaut versions downloaded images under ~/.pyronaut/bin and reuses them on later invocations.

JVM Docker mode (pyronaut build --docker):

  • Runs pyronaut-validate-config --scenario production before install/process preflight by default.

  • Runs install/process preflight.

  • Stages a compact build context under a temporary app/ root containing the configured resources directory, any additional-resources directories, pyproject.toml, processed classes, the project-local Maven cache, and the delegated pyronaut-run distribution.

  • Generates a default Dockerfile when Dockerfile is not present.

  • Builds an image tagged <image-name>:<project-version>.

  • Uses tool.pyronaut.build.docker.jvm-base-image when configured, otherwise defaults to container-registry.oracle.com/graalvm/jdk:25i4.

Native mode:

  • Runs pyronaut-validate-config --scenario production before install/process preflight by default.

  • Runs install/process preflight.

  • Delegates to pyronaut-native-build.

  • Produces pyronaut/native/application by default.

  • For Python-capable images, keeps the copied GraalPy resources directory and adjacent native libraries beside the executable in wheel and Docker distributions.

Native Docker mode (pyronaut build --native --docker):

  • Runs pyronaut-validate-config --scenario production before install/process preflight by default.

  • Runs install/process preflight.

  • Stages a container build context with processed classes, runtime dependency metadata, the project-local Maven cache, and the delegated pyronaut-native-build distribution.

  • Builds the native executable inside the configured builder image so container builds remain Linux-targeted even when started from macOS.

  • Uses a generated multistage Dockerfile when DockerfileNative is not present.

  • Builds an image tagged <image-name>:<project-version>-native.

  • Uses tool.pyronaut.build.docker.native-builder-image and tool.pyronaut.build.docker.native-base-image by default.

  • When --static is present, the generated Dockerfile adds --static --libc=musl and uses tool.pyronaut.build.docker.static-native-builder-image plus tool.pyronaut.build.docker.static-native-base-image.

Reusable Crema base images

pyronaut build --native-base=<path> creates a production native launcher that uses runtime class loading (-H:+RuntimeClassLoading) to run already processed applications. It does not include the compiler, annotation processors, test frameworks, or other development tooling. Java applications use the pyronaut-run launcher; Python applications use pyronaut-run-python, which adds the GraalPy/Truffle and Python logging runtime.

The repository’s own runtime images use this exact same builder: run ./gradlew :micronaut-pyronaut-run:buildCremaNativeImage or ./gradlew :micronaut-pyronaut-run-python:buildCremaNativeImage. The standard nativeCompile task delegates to the corresponding shared-builder task.

The native-base builder includes the application’s runtime dependencies, so custom dependencies declared in pyproject.toml are available to subsequent application builds. Native-base builds export an SBOM; inspect it to verify the included dependencies.

Use --native-base (equivalent to --native-base=default) when application dependencies do not need to be included in a custom base. Host builds resolve the bundle for the current operating system and architecture; Docker builds resolve Linux for the current architecture. Pyronaut caches the language-specific pyronaut-run image for Java applications or pyronaut-run-python for Python applications. Resolution uses the [native-images] repository, version, release, authentication, and proxy settings in ~/.pyronaut/settings.toml; Pyronaut downloads missing bundles with progress reporting. The equivalent pyproject.toml setting is native-base = "default".

To build a custom base, pass its output path. The first command builds the base, exports its SBOM, packages the application, and records the base in pyproject.toml; the second reuses it without another native-image build:

pyronaut build --native-base=build/pyronaut-base/pyronaut-run
pyronaut build
[tool.pyronaut.packaging]
format = "wheel-crema"

[tool.pyronaut.build]
native-base = "build/pyronaut-base/pyronaut-run"

Add --pgo=<profile> to compile the custom base with profile-guided optimization; see Profile-guided optimization.

Pyronaut updates only these two settings and preserves the rest of pyproject.toml. If the file defines them in a layout it cannot update safely (for example with dotted keys under [tool.pyronaut]), it leaves the file unchanged and prints the settings to add.

Without native-base, Pyronaut builds an application-specific native executable. With it, the later native build packages the configured reusable launcher and the processed application classes separately.

Direct-source packaging

Package standalone Java or Python source files or directories directly:

pyronaut build App.java --native --name example-app --version 1.0.0
pyronaut build App.py --docker --native-base

Sources compile into a disk-backed project under pyronaut/direct-source-build. Without --name and --version, Pyronaut uses the source stem and 0.1.0. --setup pyproject.toml supplies normal Pyronaut configuration. Inline Pyronaut resolves @Dependency declarations before packaging and includes them in a custom native base’s SBOM. Direct-source builds do not record a custom base, because their staged pyproject.toml is regenerated for every build; configure it in the --setup file instead.

For Docker, pyronaut build --docker --native-base packages the application on the bundled Linux runtime. pyronaut build --docker --native-base=<image> first creates and tags the custom base image <image>, then creates the final application image on top of it, and records format = "docker-crema" and build.docker.base-image = "<image>" in pyproject.toml so that later builds reuse it. To share a base between projects or CI builds, configure its OCI image reference:

[tool.pyronaut.packaging]
format = "docker-crema"

[tool.pyronaut.build.docker]
base-image = "registry.example.com/acme/pyronaut-runtime:1"

With build.docker.base-image, native Docker builds copy only application configuration, processed classes, and schemas into a new layer over that runtime image. The base image contains /opt/pyronaut/bin/pyronaut-run (or pyronaut-run-python), with any copied language resources under the adjacent /opt/pyronaut/bin/resources directory; the application layer uses it with --project-dir /app.

Production packaging matrix

You can exercise the installed production wheel against direct sources and isolated copies of Gradle, Maven, and Python projects with the opt-in matrix:

PYRONAUT_PACKAGING_E2E=true \
  PYRONAUT_PACKAGING_E2E_PYTHON=/path/to/graalpy \
  PYTHONPATH=pyronaut/src/test/python \
  python -m unittest packaging_matrix_e2e_test

The 45-case matrix runs FAT JAR, JVM, native, default-base, custom-base, and Docker packaging sequentially. It uses isolated copies under ~/dev/pyronaut-testing by default. Set PYRONAUT_PACKAGING_E2E_WORKSPACE to change that location and PYRONAUT_PACKAGING_E2E_CLI to select the installed pyronaut executable. The matrix writes results, command logs, and follow-up-issues.md to build/packaging-e2e.

Custom Dockerfiles with a reusable base

Generated application Dockerfiles expose the default HTTP port, 8080/tcp. For a different port, use a custom Dockerfile with the matching EXPOSE instruction. Custom Dockerfiles are used unchanged.

Custom Dockerfiles receive PYRONAUT_BASE_IMAGE as a build argument. A runtime-only application Dockerfile can therefore keep the reusable launcher and application code in distinct layers:

ARG PYRONAUT_BASE_IMAGE
FROM ${PYRONAUT_BASE_IMAGE}
WORKDIR /app
EXPOSE 8080
COPY app/config /app/config
COPY app/__pyronaut__/classes /app/__pyronaut__/classes
COPY app/__pyronaut__/schemas /app/__pyronaut__/schemas
ENTRYPOINT ["/opt/pyronaut/bin/pyronaut-run", "--project-dir", "/app"]

Set tool.pyronaut.build.docker.dockerfile-native to this Dockerfile and tool.pyronaut.build.docker.base-image to the already-built runtime image.

Custom Dockerfiles:

  • Dockerfile customizes JVM Docker builds.

  • DockerfileNative customizes native Docker builds.

  • tool.pyronaut.build.docker.dockerfile and tool.pyronaut.build.docker.dockerfile-native can point at alternate paths relative to the project directory.

  • Custom Dockerfiles still receive build arguments such as PYRONAUT_PROJECT_NAME, PYRONAUT_PROJECT_VERSION, PYRONAUT_BUILD_MODE, PYRONAUT_NATIVE_STATIC, PYRONAUT_JVM_BASE_IMAGE, PYRONAUT_NATIVE_BUILDER_IMAGE, and PYRONAUT_NATIVE_BASE_IMAGE.

  • The Docker build context root is temporary, with the application materialized under app/, so custom Dockerfiles should use paths such as COPY app/ /app/.

Example pyproject.toml Docker settings:

[tool.pyronaut.build.docker]
image-name = "acme/demo"
jvm-base-image = "container-registry.oracle.com/graalvm/jdk:25i4"
native-builder-image = "container-registry.oracle.com/graalvm/native-image:25i4"
native-base-image = "gcr.io/distroless/base"
static-native-builder-image = "container-registry.oracle.com/graalvm/native-image:25i4-muslib-ol8"
static-native-base-image = "scratch"
dockerfile = "docker/Dockerfile.jvm"
dockerfile-native = "docker/Dockerfile.native"

pyronaut test-resources-server

Manages standalone Micronaut test resources server lifecycle in phase 1.

Actions:

  • start (default when omitted)

  • status

  • stop

Common options:

  • --project-dir <dir>

Deterministic lifecycle metadata:

  • project-local settings: .micronaut/test-resources/test-resources.properties

  • shared mode settings: ~/.micronaut/test-resources[-<namespace>]/test-resources.properties

  • startup optimization cache path: pyronaut/test-resources-cds

Example pyproject.toml test resources settings:

[tool.pyronaut.test-resources]
enabled = true
explicit-port = 18080
infer-classpath = true
client-timeout = 60
shared-server = false
logs-dir = ".micronaut/test-resources/logs"
startup-optimization = "none" # none|auto|leyden|cds
leyden-jvm-args = ["--enable-preview"]

Canonical pyproject.toml keys are kebab-case. Legacy camelCase aliases are still accepted for compatibility, but the generated schema prefers the kebab-case names.

logs-dir controls where standalone test resources server logs go. Pyronaut resolves a relative value against the project directory. When omitted, the default is .micronaut/test-resources/logs.

Lifecycle behavior:

  • pyronaut dev and pyronaut test automatically orchestrate test resources when enabled.

  • Pyronaut starts owned servers on demand and stops them when the owning development/test session exits.

  • Shared servers (shared-server = true) are intentionally left running across command invocations.

  • When project-local settings already exist, dev and test attach to externally started servers without claiming or stopping them.

  • pyronaut test-resources-server start remains the way to keep a reusable server running until you explicitly stop it.

Integration behavior:

  • dev/test propagate micronaut.test.resources.* client settings to delegated JVMs via dedicated environment variables.

  • validate-config, install, process, and JVM build do not start or own test-resources orchestration.

  • validate-config removes stale inherited test-resources client settings for non-run/test scenarios to avoid pointing at dead servers.

Fallback semantics:

  • none: default; no startup optimization flags.

  • auto: opt-in CDS by default; if Leyden args are supplied and unsupported, prints one fallback warning and continues.

  • leyden: best effort; prints one deterministic fallback warning and continues with CDS/plain startup.

  • cds: best effort CDS, fallback to plain startup when unavailable.

GraalVM toolchains

Pyronaut CLI resolves a GraalVM JDK for commands that need Java delegation, including install, process, run, test, validate-config, build, and --tui.

Optional pyproject.toml settings:

[tool.pyronaut.toolchain]
type = "native" # jvm|native
distribution = "dev" # ce|ee|dev
version = "25.1.0-dev+10.1"
java-version = 25
release-tag = "jdk-25.1.0-dev-20260429_0111"

Supported keys:

  • type: CLI execution toolchain. The default is jvm, which launches the existing command-specific Java delegates. native routes supported lifecycle commands through the pyronaut-dev native uber CLI.

  • distribution: requested GraalVM distribution. Supported values are ce, ee, and dev.

  • version: exact GraalVM version string to match or download.

  • java-version: minimum Java major version. Pyronaut CLI currently requires GraalVM JDK 25 or newer.

  • release-tag: the distribution = "dev" setting requires this value unless you provide download-url directly. The value must match the GitHub release tag from graalvm-ce-dev-builds, or an Oracle EA tag such as jdk-25e1-25.0.3-ea.32 from oracle-graalvm-ea-builds.

  • download-url: optional explicit archive URL override.

Discovery order:

  1. JAVA_HOME when it already points at a matching GraalVM.

  2. ~/.pyronaut/sdks

  3. legacy ~/.pyronaut/jdks

  4. SDKMAN candidates under ~/.sdkman/candidates/java

  5. jEnv versions under ~/.jenv/versions

  6. Gradle-provisioned toolchains under ~/.gradle/jdks

  7. download and install into ~/.pyronaut/sdks

Distribution sources:

  • ce: downloads from https://github.com/graalvm/graalvm-ce-builds/releases.

  • ee: downloads from https://www.graalvm.org/downloads/.

  • dev: resolves assets from https://github.com/graalvm/graalvm-ce-dev-builds/releases using release-tag; Oracle EA tags such as jdk-25e1-25.0.3-ea.32 resolve from https://github.com/graalvm/oracle-graalvm-ea-builds/releases.

Behavior notes:

  • tool.pyronaut.toolchain.type controls how the pyronaut command executes CLI tooling. Build output defaults are configured separately with tool.pyronaut.packaging.format.

  • Command-specific tool.pyronaut.processor.mode and tool.pyronaut.test.mode settings override the global toolchain type for those commands.

  • If no explicit toolchain is configured, Pyronaut CLI accepts any compatible GraalVM JDK 25+ already available on the machine.

  • If you configure an explicit toolchain, Pyronaut reuses an installed JDK only when the distribution, version, and Java major version match the requested spec.

  • Pyronaut caches downloaded JDKs under ~/.pyronaut/sdks for reuse across projects.

  • The generated pyproject.toml schema supports the canonical kebab-case keys and also accepts the compatibility aliases javaVersion, releaseTag, and downloadUrl.

macOS note:

  • Gatekeeper may quarantine development builds that you download from GitHub.

  • When Pyronaut detects a quarantined GraalVM, it prints the command you should run:

    sudo xattr -r -d com.apple.quarantine /path/to/graalvm

Progress output

Every Pyronaut command renders its work the same way. On an interactive terminal (stderr is a TTY and TERM is not dumb) running work is shown as spinner rows at the bottom of the output with the elapsed time on the right; a finished row collapses into a permanent [elapsed] ✓ message (took) line, failures into ✗ lines and warnings into ! lines. The [elapsed] stamp counts from the start of the pyronaut command for every tool it delegates to, so one invocation reads as a single timeline. Output written by libraries, the application or a child process while rows are visible lands above the rows rather than tearing them.

While a delegated launcher starts, the CLI shows a Starting … row (for example Starting test runner) until the launcher reports that it is running. This covers the pause before a large native launcher executes its first instruction: on macOS the operating system verifies a freshly downloaded launcher on its first run, which can take several seconds. The row disappears as soon as the tool takes over.

Without a terminal (CI, pipes, pyronaut … 2>log) Pyronaut prints the same steps as deterministic plain lines and the CLI emits no cursor-control sequences. NO_COLOR disables colours, --color never does the same for the commands that accept it, and --progress off silences the live rows of setup, install and doctor. The CLI uses Unicode glyphs on a UTF-8 terminal; -Dpyronaut.progress.unicode=false forces the ASCII set for the Java tools.

Preflight behavior summary

  • run, test: orchestrator runs install+process preflight.

  • build --native: orchestrator runs install+process preflight, then delegates native build.

  • build --docker: orchestrator runs install+process preflight, then delegates Docker image creation with the staged JVM runtime.

  • build --native --docker: orchestrator runs install+process preflight, then delegates Docker image creation with in-container native compilation.

  • install, process, build (JVM): no additional orchestrator preflight stage.

Environment variables

  • PYRONAUT_TRACE_DELEGATION=true: prints delegated command lines.

  • PYRONAUT_TEST_RESOURCES_DISABLED=true: disables automatic test-resources orchestration for dev and test.

  • PYRONAUT_PYTHON_EXECUTABLE=<python>: overrides the GraalPy interpreter that pyronaut setup recorded for delegated commands, and the Python executable used for wheel builds.

  • PYRONAUT_NATIVE_BUILD_EXECUTABLE=<path>: overrides native build delegate executable.

  • PYRONAUT_INSTALL_EXECUTABLE, PYRONAUT_PROCESSOR_EXECUTABLE, PYRONAUT_RUN_EXECUTABLE, PYRONAUT_TEST_EXECUTABLE, PYRONAUT_VALIDATE_CONFIG_EXECUTABLE, PYRONAUT_TEST_RESOURCES_SERVER_EXECUTABLE, PYRONAUT_TUI_EXECUTABLE: override specific delegated executables.

  • PYRONAUT_PROGRESS_EPOCH_MS and PYRONAUT_LAUNCH_HANDSHAKE are set by the CLI for the tools it delegates to (the shared timeline epoch and the launch-indicator pipes described under Progress output); they are not meant to be set by hand.

Exit code conventions

The orchestrator uses stable high-level categories:

  • 0: success

  • 2: usage/argument error

  • 8: precondition failure (missing executable/artifacts/prerequisites)

  • 9: unsupported platform

  • 10: internal execution error

Delegated tools may return command-specific non-zero codes for domain failures (for example, test failures), and Pyronaut propagates those codes back to the caller.
