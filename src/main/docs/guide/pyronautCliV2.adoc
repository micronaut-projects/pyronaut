= Pyronaut CLI v2

Pyronaut CLI v2 is a process-oriented toolchain. The `pyronaut` command is a Python orchestrator that delegates work to focused executables:

- `pyronaut-install`
- `pyronaut-processor`
- `pyronaut-dev`
- `pyronaut-run`
- `pyronaut-test`
- `pyronaut-create` (used by `pyronaut create`)
- `pyronaut-native-build` (used by `pyronaut build --native`)
- `pyronaut-validate-config` (used by `pyronaut validate-config`)
- `pyronaut-test-resources-server` (used by `pyronaut test-resources-server`)

This separation keeps dependency resolution, processing, run/test execution, and native-image orchestration deterministic and independently testable.

== Platform support

Phase 1 supports macOS and Linux.

== Command syntax

[source,bash]
----
pyronaut [--version] [--tui [--smoke|--non-interactive]] <install|process|dev|run|test|build|create|validate-config|test-resources-server> [args...]
----

== Quickstart workflow

[source,bash]
----
pyronaut install --project-dir /path/to/app
pyronaut process --project-dir /path/to/app
pyronaut dev --project-dir /path/to/app
pyronaut test --project-dir /path/to/app
pyronaut create demo
----

== Project layout

Pyronaut reads project layout settings from `[tool.pyronaut.sources]` in `pyproject.toml`. Directory values are relative to the project root.

Defaults:

- `python = "src"`
- `python-test = "tests"`
- `java = "src-java"`
- `java-test = "test-java"`
- `resources = "config"`
- `test-resources = "tests-config"`
- `additional-resources = []`
- `additional-test-resources = []`

Example:

[source,toml]
----
[tool.pyronaut.sources]
python = "app"
python-test = "test/python"
java = "src/main/java"
java-test = "src/test/java"
resources = "app-config"
test-resources = "tests-config"
additional-resources = ["views", "assets"]
additional-test-resources = ["tests-fixtures"]
----

`additional-resources` is a list of extra application resource directories. These directories are included for `dev`, `run`, and `test` scopes, watched by auto-restart in `dev`, included in lifecycle validation defaults, and staged into JVM wheels and Docker images.

`additional-test-resources` is a list of extra test-only resource directories. These directories are included for `test` scope, watched by auto-restart in `dev` and `test`, and included in test lifecycle validation defaults.

These settings are used by `pyronaut process`, `pyronaut dev`, `pyronaut run`, `pyronaut test`, lifecycle validation, auto-restart file watching, and build staging for wheels and Docker images.

== Command reference

=== `pyronaut create`

Creates a new Pyronaut application from the ProjectGen generator.

[source,bash]
----
pyronaut create [NAME] [options]
----

Common options:

- `--features <f1,f2>`: comma-separated Pyronaut-compatible feature names. The option may be repeated.
- `--list-features`: print the selectable Pyronaut feature catalog and exit.
- `--output <dir>`: parent output directory. Without `--inplace`, the project is written to `<dir>/<name>`.
- `--inplace`: write generated files directly into the selected output directory.
- `--package <module>`: Python package/module name. Defaults to a normalized form of `NAME`.
- `--version <version>`: generated `[project].version` value. Defaults to `0.1.0`.
- `--micronaut-version <version>`: generated `tool.pyronaut.platform.version` value.
- `--repository <repo>`: override generated Maven repositories. Values may be repository aliases such as `mavenCentral` or `mavenLocal`, URLs, or local paths. The option accepts comma-separated values and may be repeated.
- `-h`, `--help`: print command help.

Feature selection:

- Run `pyronaut create --list-features` to see the supported feature names.
- Pass features as a comma-separated list, for example `--features data-jdbc,mysql,json-schema,test-resources`.
- Pyronaut defaults already include the Netty HTTP server, Micronaut Serialization with Jackson, Logback integration, and pytest support.
- Unsupported JVM-language, build-tool, CI/IaC, generated-source, JVM app-type, and Java reflection-dependent starter features are hidden from `--list-features` and fail early if explicitly requested. Reflection-dependent examples include `jackson-databind`, `data-jpa`, `hibernate-jpa`, and `hibernate-validator`.

Examples:

[source,bash]
----
pyronaut create demo
pyronaut create demo --features data-jdbc,mysql
pyronaut create demo --features data-jdbc,mysql,json-schema,test-resources
pyronaut create demo --package example.service --version 1.0.0
pyronaut create demo --output /tmp/apps
pyronaut create --inplace --output /tmp/demo
pyronaut create demo --micronaut-version 5.0.0-SNAPSHOT --repository mavenLocal,mavenCentral
----

=== `pyronaut install`

Resolves dependencies into the configured local Maven repository and writes scoped manifests under `__pyronaut__/`.
By default, dependency artifacts are installed into Maven local (`~/.m2/repository`, or the path configured by the `maven.repo.local` system property).

Common options:

- `--project-dir <dir>`: project root (default `.`)
- `--local-repository <dir>` (alias `--local-repo`): local Maven repository directory for resolved dependency artifacts; relative paths are resolved against the project root
- `--scope <build|runtime|test|test-resources-server|all>`: restrict resolution scope
- `--dependencies`: render dependency tree output
- `--progress <auto|on|off>`: progress display mode
- `--color <auto|always|never>`: dependency output color mode
- `--refresh`: force re-resolution and manifest rewrite without clearing the selected local repository
- `--no-cache`: bypass Pyronaut manifest cache reads before rewriting manifests
- `--offline`: resolve using offline repository mode

Proxy configuration:

`pyronaut install` uses the configured proxy for Maven dependency resolution, including dependencies resolved from `tool.pyronaut.repositories`.
Proxy configuration is discovered in this order:

. Environment variables: `HTTPS_PROXY`, `https_proxy`, `HTTP_PROXY`, `http_proxy`
. Pyronaut user settings: `~/.pyronaut/settings.toml`
. Maven user settings: `~/.m2/settings.xml`

Environment proxy URLs may include credentials and may omit the scheme, in which case `http` is used.
`NO_PROXY` or `no_proxy` configures hosts that should bypass the proxy.
Comma-separated and pipe-separated bypass lists are both accepted.

[source,bash]
----
export HTTPS_PROXY=https://user:password@proxy.example.com:8443
export NO_PROXY=localhost,127.0.0.1,*.internal.example.com
pyronaut install --project-dir /path/to/app
----

For a persistent Pyronaut-specific proxy configuration, create `~/.pyronaut/settings.toml`:

[source,toml]
----
[proxy]
url = "https://user:password@proxy.example.com:8443"
nonProxyHosts = "localhost|127.0.0.1|*.internal.example.com"
----

The same file can also split the proxy into individual fields:

[source,toml]
----
[proxy]
protocol = "https"
host = "proxy.example.com"
port = 8443
username = "user"
password = "password"
noProxyHosts = "localhost,127.0.0.1,*.internal.example.com"
----

If neither environment variables nor `~/.pyronaut/settings.toml` define a proxy, `pyronaut install` reads the first active Maven proxy from `~/.m2/settings.xml`.
If no proxy is marked active, the first proxy entry is used.

[source,xml]
----
<settings>
  <proxies>
    <proxy>
      <active>true</active>
      <protocol>https</protocol>
      <host>proxy.example.com</host>
      <port>8443</port>
      <username>user</username>
      <password>password</password>
      <nonProxyHosts>localhost|127.0.0.1|*.internal.example.com</nonProxyHosts>
    </proxy>
  </proxies>
</settings>
----

Generated manifests:

- `__pyronaut__/resolved-build-dependencies`
- `__pyronaut__/resolved-runtime-dependencies`
- `__pyronaut__/resolved-test-dependencies`
- `__pyronaut__/resolved-test-resources-server-dependencies`

Manifest entries point at artifacts in the selected local repository.
Build-wheel and Docker packaging copy those artifacts into the packaged application's `__pyronaut__/m2-repository` directory and rewrite the packaged manifest to use project-relative paths.

Managed runtime defaults:

- When dependency versions are managed from the Micronaut platform, `pyronaut install` adds `io.micronaut.toml:micronaut-toml` to the runtime classpath by default, so `application.toml` in the configured resources directory works without an explicit dependency declaration.
- `pyronaut install` also adds `io.micronaut:micronaut-context-python` to `runtime` by default.
- `pyronaut install` also adds `io.micronaut:micronaut-inject-python` and `io.micronaut:micronaut-context-python` to `build` by default.
- `pyronaut install` also adds `io.micronaut.openapi:micronaut-openapi` to `build` and its annotations to `runtime`, enabling OpenAPI processing without a project-specific processor declaration.
- `pyronaut install` also adds `org.junit.platform:junit-platform-launcher` and `org.junit.jupiter:junit-jupiter-engine` to `test` by default.
- Commands that need a GraalVM JDK resolve one through the shared toolchain flow described in <<graalvm-toolchains>>.

Editor support:

- `pyronaut install` also materializes a project-local JSON schema at `__pyronaut__/schemas/pyronaut-pyproject.schema.json`.
- `pyronaut install` prepends a Taplo schema directive to `pyproject.toml` pointing at that schema.
- If `application.toml` exists in the configured resources directory, `pyronaut install` also builds `__pyronaut__/schemas/micronaut-application.schema.json` from the Micronaut configuration schemas present on the resolved runtime classpath and prepends a schema directive to that file.
- Runtime configuration schemas are merged by their `x-micronaut.prefix` path, so overlapping contributors such as `micronaut.server` and `micronaut.server.netty` are combined into one rooted schema tree.

Annotation processor options:

- During installation, Pyronaut discovers `TypeElementVisitor.getSupportedOptions()` from the resolved processor classpath and caches the sorted option names under `__pyronaut__/annotation-processor-options.properties`.
- Matching values from the Micronaut application environment (including `application.toml`, `application.yml`, and `application.properties`) are flattened to dotted keys and passed to processing as `-A` compiler arguments. Unrelated application configuration is ignored.
- Pyronaut supplies the supported `micronaut.openapi.views.spec` option with `swagger-ui.enabled=true,redoc.enabled=true` by default, unless the application overrides it. This causes Swagger UI and ReDoc HTML assets to be generated under `META-INF/swagger/views`.
- `pyronaut dev` and direct-source `pyronaut run <source>` supply default static-resource routes for the generated YAML, Swagger UI, and ReDoc under `/swagger/**`, `/swagger-ui/**`, and `/redoc/**`. Explicit `--property` values or application configuration take precedence; project-mode `pyronaut run` does not add these routes automatically.
- The test processing pass always passes `micronaut.openapi.enabled=false`, so OpenAPI files are generated only for main sources.
- `pyronaut install` also generates Python editor stubs under `__pyronaut__/ide-stubs` from the resolved `runtime` and `test` classpaths.
- Python editor stub generation is configurable under `[tool.pyronaut.ide-stubs]` with `enabled`, `ide`, `packages`, `exclude-patterns`, and `destination-dir`.
- `ide` defaults to `vscode` and currently supports `vscode` and `pycharm`.
- `exclude-patterns` accepts wildcard matches against fully qualified Java type names and defaults to `["*ModuleInfo"]` to skip generated module metadata classes.
- The resolved editor input set is recorded in `__pyronaut__/resolved-editor-artifacts.json`, including binary JAR and source JAR paths when available.
- When `ide = "vscode"` is used without user-managed Pyright configuration, `pyronaut install` writes `.vscode/settings.json` with `python.analysis.extraPaths` pointing at the configured stub directory so Pylance can resolve Java-backed Python imports such as `micronaut.http.annotation` and `jakarta.inject`.
- If `pyrightconfig.json` or `[tool.pyright]` already exists, `pyronaut install` leaves that configuration user-managed and records the skipped settings update in the editor stub report.
- When `ide = "pycharm"`, `pyronaut install` writes a generated `.idea/pyronaut-editor-stubs.iml` module and adds it to `.idea/modules.xml` so the stub directory is visible as a source root without rewriting the main project module.
- Python editor stub generation is best effort. If a particular Java type cannot be rendered cleanly, Pyronaut skips that API surface and continues install processing.
- Detailed stub-generation warnings are written to `__pyronaut__/reports/editor-stubs/stub-generation-report.txt` instead of being streamed line-by-line to the console.
- Existing user-managed `#:schema ...` directives at the top of `pyproject.toml` are left untouched.
- Existing user-managed `#:schema ...` directives at the top of `application.toml` in the configured resources directory are left untouched.
- Older generated `.taplo.toml` files from previous Pyronaut installs are removed to avoid conflicting schema associations. User-managed `.taplo.toml` files are left untouched.

=== `pyronaut process`

Processes source trees and generates metadata/classes via `pyronaut-processor`.

Common options:

- `--project-dir <dir>`
- `--verbose`: full diagnostics on failures
- `--incremental`: enable incremental Python and Java compilation for this invocation
- `--no-incremental`: disable incremental compilation for this invocation
- `--daemon`: use the persistent compiler daemon for this invocation
- `--no-daemon`: process in the current command process for this invocation
- `--no-cache`: clear processor outputs and incremental state, then perform a full compilation without reusing either cache

The CLI `--incremental` and `--no-incremental` options override `tool.pyronaut.processor.incremental`.
Likewise, `--daemon` and `--no-daemon` override `tool.pyronaut.processor.daemon`.
Incremental compilation is disabled when neither the CLI nor project configuration enables it.
See <<incrementalProcessing,Incremental Processing>> for cache locations, invalidation behavior, and source-writing guidance.

Default processing outputs:

- configured `python` + configured `java` -> `__pyronaut__/classes`
- merged source+test pass -> `__pyronaut__/test-classes`

=== `pyronaut dev`

Runs the processed application via `pyronaut-dev` in development mode.

Common options:

- `--project-dir <dir>`
- `--debug-vm`: enables JDWP JVM debug flags (port 5005)
- `--no-validate`: explicitly bypasses lifecycle config validation
- `--control-panel`: enables the development Control Panel, overriding project configuration
- `--disable-test-resources`: disables configured project orchestration and conditional direct-source Test Resources inference

Behavior:

- When no source is specified, detects `main.py` in the current directory for standalone direct-source development. A `pyproject.toml`, Maven build, or Gradle build keeps project mode.
- Runs `pyronaut-validate-config --scenario dev` before preflight by default.
- Automatically performs install/process preflight before launching.
- Starts an owned test-resources server when test resources are enabled and no reusable external server settings are present.
- Attaches to an already running external test-resources server when `.micronaut/test-resources/test-resources.properties` exists and no owned session is active.
- Propagates active test-resources client settings to the delegated JVM via `JAVA_TOOL_OPTIONS`.
- Uses the development runtime classpath manifest plus processed classes.
- Includes the configured resources directory, any `additional-resources` directories, the configured test resources directory, and any `additional-test-resources` directories on the classpath when present.

=== `pyronaut run`

Runs the processed application via the production runtime image in runtime-only
mode: `pyronaut-run` for Java projects and `pyronaut-run-python` when the
resolved runtime includes Micronaut Python support. This is intentionally
separate from `pyronaut dev`, which always uses the development image.

Common options:

- `--project-dir <dir>`
- `--debug-vm`: enables JDWP JVM debug flags (port 5005)
- `--no-validate`: explicitly bypasses lifecycle config validation

Behavior:

- Runs `pyronaut-validate-config --scenario run` before preflight by default.
- Automatically performs install/process preflight before launching.
- Does not start test resources by default.
- Propagates active test-resources client settings to the delegated JVM via `JAVA_TOOL_OPTIONS` when an external project-local server is configured.
- Direct source execution is production-only and never infers, starts, or consumes Test Resources.
- Uses the runtime classpath manifest plus processed classes.
- For native toolchains, excludes runtime artifacts already bundled in the
  selected production image by Maven `group:artifact`, so the image's copy
  takes precedence over a project dependency with the same module identity.
- Includes the configured resources directory and any `additional-resources` directories on the classpath when present.

=== `pyronaut test`

Runs project tests via `pyronaut-test` and the pytest-backed JUnit engine, or runs direct Java/Python JUnit 5 sources in-memory.

Common options:

- `--project-dir <dir>`
- `--debug-vm`: enables JDWP JVM debug flags (port 5005)
- `--tests <selector>`: repeatable Gradle-like test selector filter
- `--no-validate`: explicitly bypasses lifecycle config validation
- `--disable-test-resources`: disables configured project orchestration and conditional direct-source Test Resources inference

Behavior:

- Runs `pyronaut-validate-config --scenario test` before preflight by default.
- Automatically performs install/process preflight.
- Starts an owned test-resources server when test resources are enabled and no reusable external server settings are present.
- Attaches to an already running external test-resources server when `.micronaut/test-resources/test-resources.properties` exists and no owned session is active.
- Propagates active test-resources client settings to the delegated JVM via `JAVA_TOOL_OPTIONS`.
- Uses test classpath manifest and processed test classes when available.
- Uses the configured Python test directory for pytest discovery unless `--tests-dir` overrides it.
- Includes the configured resources directory, any `additional-resources` directories, the configured test resources directory, and any `additional-test-resources` directories on the classpath when present.
- Writes reports under `__pyronaut__/reports/tests`.

Direct source tests:

Direct mode separates application sources from test sources with `--`:

[source,bash]
----
pyronaut test Foo.java -- FooTest.java
pyronaut test Foo.py -- FooTest.py
pyronaut test src/*.java -- test/*.java
----

Direct tests are compiled in-memory and executed through JUnit 5. Python direct tests use the Python compiler's JUnit 5 integration; they do not invoke pytest or require a Python virtual environment. Java-only direct tests disable Python runtime beans unless `micronaut.python.enabled` is supplied explicitly.

Use `-t` or `--continuous` to rerun direct tests after source changes:

[source,bash]
----
pyronaut test -t Foo.java -- FooTest.java
----

Direct test output includes per-test progress and a final execution summary on the console. Direct mode writes JUnit XML and HTML reports to
`__pyronaut__/reports/tests` and prints a terminal link to the HTML report. The
report includes container startup failures that prevent tests from starting.
Pass a directory after `--report` to choose another location. The option is also
accepted by project-based `pyronaut test` and controls its report directory.

[source,bash]
----
pyronaut test --report Foo.java -- FooTest.java
pyronaut test --report build/test-reports Foo.java -- FooTest.java
----

Report artifacts:

- `__pyronaut__/reports/tests/index.html`
- `__pyronaut__/reports/tests/junit.xml`
- `__pyronaut__/reports/tests/.pyronaut-last-nodeid.txt`
- `__pyronaut__/reports/tests/events.ndjson`

=== `pyronaut build`

Builds a JVM wheel, a native executable, or a Docker image for either mode.

Build mode selection:

- `--mode jvm|native`
- `--jvm` (shortcut for JVM mode)
- `--native` (shortcut for native mode)
- `tool.pyronaut.build.mode` in `pyproject.toml`
- `tool.pyronaut.toolchain.type` when no build mode is explicitly configured

The precedence is command-line mode, then `tool.pyronaut.build.mode`, then
`tool.pyronaut.toolchain.type`, then JVM mode. For example, setting
`tool.pyronaut.toolchain.type = "native"` makes `pyronaut build` create a
native build by default, while `pyronaut build --jvm` still explicitly creates
a JVM wheel.

Common options:

- `--project-dir <dir>`
- `--docker`: build a container image instead of a wheel/native binary on the host
- `--static`: static native container build; only valid with `--native --docker`
- `--base-image`: build a reusable Crema production runtime image
- `--base-image=default`: package against the bundled Java or Python Crema runtime
- `--base-image-output <path>`: choose the local output for `--base-image`
- `--name <name>` / `--version <version>`: package metadata for direct Java or Python sources
- `--verbose` (native mode, forwarded to `native-image`)
- `--no-validate`: explicitly bypasses lifecycle config validation

JVM mode:

- Runs `pyronaut-validate-config --scenario production` by default.
- Builds a wheel using `pip wheel`.
- Outputs artifacts to `dist/`.

Native mode always uses `io.micronaut.pyronaut.run.PyronautRunMain`; `--main-class` is not supported.

JVM Docker mode (`pyronaut build --docker`):

- Runs `pyronaut-validate-config --scenario production` before install/process preflight by default.
- Runs install/process preflight.
- Stages a compact build context under a temporary `app/` root containing the configured resources directory, any `additional-resources` directories, `pyproject.toml`, processed classes, the project-local Maven cache, and the delegated `pyronaut-run` distribution.
- Generates a default Dockerfile when `Dockerfile` is not present.
- Builds an image tagged `<image-name>:<project-version>`.
- Uses `tool.pyronaut.build.docker.jvm-base-image` when configured, otherwise defaults to `container-registry.oracle.com/graalvm/jdk:25`.

Native mode:

- Runs `pyronaut-validate-config --scenario production` before install/process preflight by default.
- Runs install/process preflight.
- Delegates to `pyronaut-native-build`.
- Produces `__pyronaut__/native/application` by default.

Native Docker mode (`pyronaut build --native --docker`):

- Runs `pyronaut-validate-config --scenario production` before install/process preflight by default.
- Runs install/process preflight.
- Stages a container build context with processed classes, runtime dependency metadata, the project-local Maven cache, and the delegated `pyronaut-native-build` distribution.
- Builds the native executable inside the configured builder image so container builds remain Linux-targeted even when started from macOS.
- Uses a generated multistage Dockerfile when `DockerfileNative` is not present.
- Builds an image tagged `<image-name>:<project-version>-native`.
- Uses `tool.pyronaut.build.docker.native-builder-image` and `tool.pyronaut.build.docker.native-base-image` by default.
- When `--static` is present, the generated Dockerfile adds `--static --libc=musl` and uses `tool.pyronaut.build.docker.static-native-builder-image` plus `tool.pyronaut.build.docker.static-native-base-image`.

==== Reusable Crema base images

`pyronaut build --base-image` creates a production native launcher that uses
runtime class loading (`-H:+RuntimeClassLoading`) to run already processed
applications. It does not include the compiler, annotation processors, test
frameworks, or other development tooling. Java applications use the
`pyronaut-run` launcher; Python applications use `pyronaut-run-python`, which
adds the GraalPy/Truffle and Python logging runtime.

The repository's own runtime images use this exact same builder: run
`./gradlew :micronaut-pyronaut-run:buildCremaNativeImage` or
`./gradlew :micronaut-pyronaut-run-python:buildCremaNativeImage`. The standard
`nativeCompile` task delegates to the corresponding shared-builder task.

The base builder includes the application's runtime dependencies, so custom
dependencies declared in `pyproject.toml` are available to subsequent
application builds. Base-image builds enable the native-image build report and
SBOM export; inspect the generated report to verify included dependencies.

Use `--base-image=default` when application dependencies do not need to be
included in a custom base. It selects the bundled `pyronaut-run` image for Java
applications and `pyronaut-run-python` for Python applications. The equivalent
`pyproject.toml` setting is `base-image = "default"`. Bare `--base-image`
continues to create a custom base and export its report and SBOM.

[source,toml]
----
[tool.pyronaut.build]
base-image = "build/pyronaut-base/pyronaut-run"
----

[source,bash]
----
pyronaut build --base-image
pyronaut build
----

Without `base-image`, Pyronaut builds an application-specific native binary.
With it, the later native build packages the configured reusable launcher and
the processed application classes separately.

==== Direct-source packaging

Package standalone Java or Python source files or directories directly:

[source,bash]
----
pyronaut build App.java --native --name example-app --version 1.0.0
pyronaut build App.py --docker --base-image=default
----

Sources compile into a disk-backed project under `__pyronaut__/direct-source-build`.
Without `--name` and `--version`, the source stem and `0.1.0` are used.
`--setup pyproject.toml` supplies normal Pyronaut configuration. Inline
`@Dependency` declarations are resolved before packaging and are included in
a custom base image's SBOM.

For Docker, `pyronaut build --native --docker --base-image` first creates and
tags `<image-name>:<project-version>-native-base` and then creates the final
application image. Future Docker builds reuse that base when no explicit
Docker base is configured. To share a base between projects or CI builds,
configure its OCI image reference:

[source,toml]
----
[tool.pyronaut.build.docker]
base-image = "registry.example.com/acme/pyronaut-runtime:1"
----

With `build.docker.base-image`, native Docker builds copy only application
configuration, processed classes, and schemas into a new layer over that
runtime image. The base image contains `/opt/pyronaut/bin/pyronaut-run` (or
`pyronaut-run-python`); the application layer uses it with
`--project-dir /app`.

==== Custom Dockerfiles with a reusable base

Custom Dockerfiles receive `PYRONAUT_BASE_IMAGE` as a build argument. A
runtime-only application Dockerfile can therefore keep the reusable launcher
and application code in distinct layers:

[source,dockerfile]
----
ARG PYRONAUT_BASE_IMAGE
FROM ${PYRONAUT_BASE_IMAGE}
WORKDIR /app
COPY app/config /app/config
COPY app/__pyronaut__/classes /app/__pyronaut__/classes
COPY app/__pyronaut__/schemas /app/__pyronaut__/schemas
ENTRYPOINT ["/opt/pyronaut/bin/pyronaut-run", "--project-dir", "/app"]
----

Set `tool.pyronaut.build.docker.dockerfile-native` to this Dockerfile and
`tool.pyronaut.build.docker.base-image` to the already-built runtime image.

Custom Dockerfiles:

- `Dockerfile` customizes JVM Docker builds.
- `DockerfileNative` customizes native Docker builds.
- `tool.pyronaut.build.docker.dockerfile` and `tool.pyronaut.build.docker.dockerfile-native` can point at alternate paths relative to the project directory.
- Custom Dockerfiles still receive build arguments such as `PYRONAUT_PROJECT_NAME`, `PYRONAUT_PROJECT_VERSION`, `PYRONAUT_BUILD_MODE`, `PYRONAUT_NATIVE_STATIC`, `PYRONAUT_JVM_BASE_IMAGE`, `PYRONAUT_NATIVE_BUILDER_IMAGE`, and `PYRONAUT_NATIVE_BASE_IMAGE`.
- The Docker build context root is temporary, with the application materialized under `app/`, so custom Dockerfiles should use paths such as `COPY app/ /app/`.

Example `pyproject.toml` Docker settings:

[source,toml]
----
[tool.pyronaut.build.docker]
image-name = "acme/demo"
jvm-base-image = "container-registry.oracle.com/graalvm/jdk:25"
native-builder-image = "container-registry.oracle.com/graalvm/native-image:25"
native-base-image = "gcr.io/distroless/base"
static-native-builder-image = "container-registry.oracle.com/graalvm/native-image:25-muslib"

=== `pyronaut validate-config`

Validates Micronaut configuration and writes deterministic reports.

Common options:

- `--project-dir <dir>`
- `--scenario <dev|run|test|production>` (default `production`)
- `--env <name>`: repeatable environment entry
- `--environments <a,b,...>`: comma-separated environments
- `--validate-dependency-injection`
- `--no-validate-dependency-injection`: explicitly disable dependency-injection validation
- `--dependency-injection-validation-strategy <reachable|application-beans|all-beans>`
- `--format <json|html|both>`
- `--out <dir>`
- `--classpath <path[,;path...]>`: repeatable classpath override
- `--resources-dirs <path[,;path...]>`: repeatable resource directory override
- `--project-base-dir <dir>`
- `--deduce-environments` / `--no-deduce-environments`
- `--fail-on-not-present` / `--no-fail-on-not-present`
- `--no-cache`: disable config validation cache
- `--suppress <pattern>`: repeatable suppression entry
- `--suppressions <a,b,...>`: suppression list
- `--suppress-inject-errors <id[,id...]>`: suppress DI error identifiers

Report artifacts (default):

- `__pyronaut__/reports/config-validation/<scenario>/configuration-errors.json`
- `__pyronaut__/reports/config-validation/<scenario>/configuration-errors.html`
- `__pyronaut__/.config-validation-cache.properties` (input/resource/classpath fingerprint cache)

Behavior:

- `dev`, `run`, `test`, and native `build` delegate to `validate-config` with scenario-specific defaults (`dev`, `run`, `test`, or `production`).
- Standalone `pyronaut validate-config` defaults to `production` unless `--scenario` is provided.
- Non-run/test commands strip stale `micronaut.test.resources.*` entries from inherited `JAVA_TOOL_OPTIONS` before validation.
- When configuration errors are present, the CLI prints a copy-pasteable `[tool.pyronaut.validation] suppressions = [...]` snippet below the rendered error table.

Example `pyproject.toml` validation settings:

[source,toml]
----
[tool.pyronaut.validation]
enabled = true
fail-on-not-present = true
validate-dependency-injection = false
dependency-injection-validation-strategy = "reachable"
format = "both"

[tool.pyronaut.validation.production]
environments = []
----

=== `pyronaut test-resources-server`

Manages standalone Micronaut test resources server lifecycle in phase 1.

Actions:

- `start` (default when omitted)
- `status`
- `stop`

Common options:

- `--project-dir <dir>`

Deterministic lifecycle metadata:

- project-local settings: `.micronaut/test-resources/test-resources.properties`
- shared mode settings: `~/.micronaut/test-resources[-<namespace>]/test-resources.properties`
- startup optimization cache path: `__pyronaut__/test-resources-cds`

Example `pyproject.toml` test resources settings:

[source,toml]
----
[tool.pyronaut.test-resources]
enabled = true
explicit-port = 18080
infer-classpath = true
client-timeout = 60
shared-server = false
logs-dir = ".micronaut/test-resources/logs"
startup-optimization = "none" # none|auto|leyden|cds
leyden-jvm-args = ["--enable-preview"]
----

Canonical `pyproject.toml` keys are kebab-case. Legacy camelCase aliases are still accepted for compatibility, but the generated schema prefers the kebab-case names.

`logs-dir` controls where standalone test resources server logs are written.
If the value is relative, it is resolved against the project directory.
When omitted, the default is `.micronaut/test-resources/logs`.

Lifecycle behavior:

- `pyronaut dev` and `pyronaut test` automatically orchestrate test resources when enabled.
- Owned servers are started on demand and stopped when the owning development/test session exits.
- Shared servers (`shared-server = true`) are intentionally left running across command invocations.
- Externally started servers are attached to when project-local settings already exist, but are not claimed or stopped by `dev`/`test`.
- `pyronaut test-resources-server start` remains the way to keep a reusable server running until you explicitly stop it.

Integration behavior:

- `dev`/`test` propagate `micronaut.test.resources.*` client settings to delegated JVMs via dedicated environment variables.
- `validate-config`, `install`, `process`, and JVM `build` do not start or own test-resources orchestration.
- `validate-config` removes stale inherited test-resources client settings for non-run/test scenarios to avoid pointing at dead servers.

Fallback semantics:

- `none`: default; no startup optimization flags.
- `auto`: opt-in CDS by default; if Leyden args are supplied and unsupported, prints one fallback warning and continues.
- `leyden`: best effort; prints one deterministic fallback warning and continues with CDS/plain startup.
- `cds`: best effort CDS, fallback to plain startup when unavailable.

=== GraalVM toolchains

Pyronaut CLI resolves a GraalVM JDK for commands that need Java delegation, including `install`, `process`, `run`, `test`, `validate-config`, `build`, and `--tui`.

Optional `pyproject.toml` settings:

[source,toml]
----
[tool.pyronaut.toolchain]
type = "native" # jvm|native
distribution = "dev" # ce|ee|dev
version = "25.1.0-dev+10.1"
java-version = 25
release-tag = "jdk-25.1.0-dev-20260429_0111"
----

Supported keys:

- `type`: CLI execution toolchain. The default is `jvm`, which launches the existing command-specific Java delegates. `native` routes supported lifecycle commands through the `pyronaut-dev` native uber CLI.
- `distribution`: requested GraalVM distribution. Supported values are `ce`, `ee`, and `dev`.
- `version`: exact GraalVM version string to match or download.
- `java-version`: minimum Java major version. Pyronaut CLI currently requires GraalVM JDK 25 or newer.
- `release-tag`: required for `distribution = "dev"` unless `download-url` is provided directly. This must match the GitHub release tag from `graalvm-ce-dev-builds`, or an Oracle EA tag such as `jdk-25e1-25.0.3-ea.32` from `oracle-graalvm-ea-builds`.
- `download-url`: optional explicit archive URL override.

Discovery order:

. `JAVA_HOME` when it already points at a matching GraalVM.
. `~/.pyronaut/sdks`
. legacy `~/.pyronaut/jdks`
. SDKMAN candidates under `~/.sdkman/candidates/java`
. jEnv versions under `~/.jenv/versions`
. Gradle-provisioned toolchains under `~/.gradle/jdks`
. download and install into `~/.pyronaut/sdks`

Distribution sources:

- `ce`: downloads from `https://github.com/graalvm/graalvm-ce-builds/releases`.
- `ee`: downloads from `https://www.graalvm.org/downloads/`.
- `dev`: resolves assets from `https://github.com/graalvm/graalvm-ce-dev-builds/releases` using `release-tag`; Oracle EA tags such as `jdk-25e1-25.0.3-ea.32` resolve from `https://github.com/graalvm/oracle-graalvm-ea-builds/releases`.

Behavior notes:

- `tool.pyronaut.toolchain.type` controls how the `pyronaut` command executes CLI tooling and is also the default build mode when `tool.pyronaut.build.mode` and command-line build mode are absent.
- Command-specific `tool.pyronaut.processor.mode` and `tool.pyronaut.test.mode` settings override the global toolchain type for those commands.
- If no explicit toolchain is configured, Pyronaut CLI accepts any compatible GraalVM JDK 25+ already available on the machine.
- If an explicit toolchain is configured, Pyronaut only reuses an installed JDK when the distribution, version, and Java major version match the requested spec.
- Downloaded JDKs are cached under `~/.pyronaut/sdks` for reuse across projects.
- The generated `pyproject.toml` schema supports the canonical kebab-case keys and also accepts the compatibility aliases `javaVersion`, `releaseTag`, and `downloadUrl`.

macOS note:

- Development builds downloaded from GitHub may be quarantined by Gatekeeper.
- When Pyronaut detects a quarantined GraalVM, it prints the command you should run:
+
[source,bash]
----
sudo xattr -r -d com.apple.quarantine /path/to/graalvm
----

=== Native-image argument passthrough

`pyronaut build --native` forwards native-image arguments that are not consumed by `pyronaut build` itself.
Native builds always use `io.micronaut.pyronaut.run.PyronautRunMain` as their entry point; the application main class is not configurable.

Examples:

[source,bash]
----
pyronaut build --native --project-dir /path/to/app \
  --trace-object-instantiation=ch.qos.logback.classic.Logger

pyronaut build --native --project-dir /path/to/app -- \
  --trace-object-instantiation=ch.qos.logback.classic.Logger \
  --initialize-at-run-time io.netty.util.ResourceLeakDetector
----

`--` is supported to explicitly separate orchestrator arguments from native-image passthrough arguments.

=== Reachability metadata repository (native mode)

Native builds integrate GraalVM reachability metadata repository selection.

Optional `pyproject.toml` settings:

[source,toml]
----
[tool.pyronaut.build]
mode = "native"

[tool.pyronaut.build.metadata]
enabled = true
version = "0.11.5"
repository-url = "https://repo1.maven.org/maven2/org/graalvm/buildtools/graalvm-reachability-metadata/0.11.5/graalvm-reachability-metadata-0.11.5-repository.zip"
excluded-modules = ["ch.qos.logback:logback-classic"]
----

Notes:

- By default, metadata is enabled.
- Versioned repository zips are resolved from Maven Central when only `version` is set.
- Repository-based selection is applied to runtime artifacts and feeds `-H:ConfigurationFileDirectories=...`.

=== `pyronaut --tui`

Launches the delegated TUI workflow (`pyronaut-tui`).

Common options:

- `--project-dir <dir>`
- `--test`: start in test mode (default run mode)
- `--report-dir <dir>`
- `--smoke`: smoke mode
- `--non-interactive`: non-interactive mode
- `--trace-delegation`: prints delegated command lines

In smoke/non-interactive paths, the TUI delegates through the same orchestrator flow (`install`, `process`, `run`/`test`).

== Preflight behavior summary

- `run`, `test`: orchestrator runs install+process preflight.
- `build --native`: orchestrator runs install+process preflight, then delegates native build.
- `build --docker`: orchestrator runs install+process preflight, then delegates Docker image creation with the staged JVM runtime.
- `build --native --docker`: orchestrator runs install+process preflight, then delegates Docker image creation with in-container native compilation.
- `install`, `process`, `build` (JVM): no additional orchestrator preflight stage.

== Environment variables

- `PYRONAUT_TRACE_DELEGATION=true`: prints delegated command lines.
- `PYRONAUT_TEST_RESOURCES_DISABLED=true`: disables automatic test-resources orchestration for `dev` and `test`.
- `PYRONAUT_PYTHON_EXECUTABLE=<python>`: overrides Python executable used for wheel builds.
- `PYRONAUT_NATIVE_BUILD_EXECUTABLE=<path>`: overrides native build delegate executable.
- `PYRONAUT_INSTALL_EXECUTABLE`, `PYRONAUT_PROCESSOR_EXECUTABLE`, `PYRONAUT_RUN_EXECUTABLE`, `PYRONAUT_TEST_EXECUTABLE`, `PYRONAUT_VALIDATE_CONFIG_EXECUTABLE`, `PYRONAUT_TEST_RESOURCES_SERVER_EXECUTABLE`, `PYRONAUT_TUI_EXECUTABLE`: override specific delegated executables.

== Exit code conventions

The orchestrator uses stable high-level categories:

- `0`: success
- `2`: usage/argument error
- `8`: precondition failure (missing executable/artifacts/prerequisites)
- `9`: unsupported platform
- `10`: internal execution error

Delegated tools may return command-specific non-zero codes for domain failures (for example, test failures), and those are propagated back to the caller.

== Direct Source Execution

Run a Java source file directly in a generated Micronaut application context:

[source,bash]
----
pyronaut run Foo.java
----

Java-only direct execution disables Micronaut Python infrastructure for that run by setting
`micronaut.python.enabled=false`. Python applications remain enabled by default. The property can
also be configured explicitly as an application property or system property.
