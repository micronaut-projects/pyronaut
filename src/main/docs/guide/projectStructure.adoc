== Project layout

Pyronaut reads project layout from `[tool.pyronaut.sources]` in `pyproject.toml`.
All configured paths are relative to the project root.

For SDK provisioning and GraalVM discovery, see <<installation,Installing Pyronaut>>.
For toolchain settings, see <<pyproject,Configuring pyproject.toml>>. Native-image
sources and proxy behavior are covered in <<proxyConfig,Proxy Configuration>>;
advanced CLI toolchain behavior is in <<pyronautCliV2,Pyronaut CLI Reference>>.

The default layout is:

[source,text]
----
.
|-- pyproject.toml
|-- src/
|   `-- application Python sources
|-- src-java/
|   `-- optional Java application sources
|-- config/
|   `-- application.toml and other application resources
|-- tests/
|   `-- Python test sources (pytest or JUnit modules)
|-- test-java/
|   `-- optional Java test sources
|-- tests-config/
|   `-- test-only resources
`-- __pyronaut__/
    `-- generated Pyronaut state
----

The default source settings are:

[source,toml]
----
[tool.pyronaut.sources]
python = "src"
python-test = "tests"
java = "src-java"
java-test = "test-java"
resources = "config"
test-resources = "tests-config"
additional-resources = []
additional-test-resources = []
----

`pyronaut process` compiles the configured Python and Java source trees into `__pyronaut__/classes`.
For tests, Pyronaut also creates `__pyronaut__/test-classes` from the application and test source sets.

[[packageInitializers]]
== Python packages and `__init__.py`

Organize application code into packages by creating directories under the Python source directory.
You do not need an `__init__.py` file: Pyronaut generates the `__init__.py` of every package it processes.
The generated initializer exports each top-level class defined in the modules of the package, so both of these imports work:

[source,python]
----
from bookshelf.book import Book
from bookshelf import Book
----

Pyronaut generates the initializer because packages can be shared between source roots and libraries.
For example, an application and a library on its classpath can both add modules to the same package.
The generated initializer merges every contribution, so one source root does not hide another.

An `__init__.py` that is empty or contains only a docstring and comments is accepted.
Pyronaut ignores the file and uses the generated initializer instead, so a package docstring is not kept at runtime.

`pyronaut process` rejects an `__init__.py` that contains any other code, such as imports, functions, constants, or start-up logic.
Move that code out of the initializer:

* Classes need no re-export. The generated initializer already exports them from the package.
* Move functions and constants into a module of the package, then import them from that module, for example `from bookshelf.util import slugify`.
* Move package start-up work into a bean, for example a `@Context` bean or a `StartupEvent` listener, so that Micronaut runs it during application startup (see <<dependencyInjection,Dependency Injection>>).

== Resource directories

Pyronaut adds the `resources` directory to the runtime classpath for `run`, `test`, and build operations.
It adds the `test-resources` directory only for tests.

Use `additional-resources` for application resource directories that Pyronaut should make available in run, test, JVM wheel, and Docker packaging flows.
Use `additional-test-resources` for test-only resource directories.

[source,toml]
----
[tool.pyronaut.sources]
resources = "config"
additional-resources = ["views", "assets"]
test-resources = "tests-config"
additional-test-resources = ["tests-fixtures"]
----

== Generated state

The `__pyronaut__` directory contains generated state such as dependency manifests, processed classes, test reports, validation reports, schemas, and IDE stubs.
Incremental processing stores compiler state separately for the main and test passes under `__pyronaut__/incremental/main` and `__pyronaut__/incremental/test`.
The compiler daemon stores its authenticated local endpoint metadata and detached diagnostics under `__pyronaut__/daemon`.
It is safe to delete this directory when you want a clean local Pyronaut state; the CLI recreates it as needed.
`pyronaut clean` removes only the `pyronaut process` output, and `pyronaut clean --full` removes the whole directory together with `.venv` (see <<pyronautCliV2,Pyronaut CLI Reference>>).

For Maven and Gradle projects (see <<mavenGradle,Using Maven and Gradle Projects>>) Pyronaut writes the same generated state under the build's output directory instead: `target/pyronaut` for Maven and `build/pyronaut` for Gradle.
