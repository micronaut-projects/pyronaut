= Test Resources and Docker

Pyronaut can orchestrate Micronaut Test Resources for `pyronaut dev` and `pyronaut test`.
This is useful for tests and local runs that need services such as databases without hard-coding connection settings.
`pyronaut run` does not infer, start, or consume Test Resources.

Enable test resources in `pyproject.toml`:

[source,toml]
----
[tool.pyronaut.test-resources]
enabled = true
----

When enabled in a project, `pyronaut install` resolves a test-resources-server classpath and `pyronaut dev` or `pyronaut test` starts a server when needed.
The CLI propagates test resources client settings to delegated JVM processes.

For direct-source execution without a `pyproject.toml`, Pyronaut resolves the server and client only when runtime dependencies and inline runtime `@AppConfig` declarations identify a missing property supported by an inferred provider. This applies to direct `dev` and `test` only.

== Lifecycle

Default behavior:

- `pyronaut dev` and `pyronaut test` start an owned server on demand.
- Owned servers stop when the owning development or test session exits.
- If an external project-local server is already running, the CLI attaches to it instead of claiming ownership.
- Shared servers stay running across command invocations.

Pyronaut writes project-local metadata under:

[source,text]
----
.micronaut/test-resources/test-resources.properties
__pyronaut__/test-resources-session.json
----

Pyronaut writes logs to `.micronaut/test-resources/logs` by default unless you configure `logs-dir`.

The server pulls and starts containers in its own process, so `pyronaut dev` and `pyronaut test` tail that log while they
wait and report the image pulls, container starts and failures alongside their own progress output.
Configuring `logs-dir` moves the log the launchers follow along with the log itself.

== Configuration

[source,toml]
----
[tool.pyronaut.test-resources]
enabled = true
explicit-port = 18080
infer-classpath = true
client-timeout = 60
shared-server = false
logs-dir = ".micronaut/test-resources/logs"
startup-optimization = "none" # none|auto|leyden|cds
additional-modules = ["jdbc-mysql"]
----

`startup-optimization` controls JVM start-up optimisation for the server process. `auto` and `cds` use class-data sharing when the JDK supports it; Pyronaut accepts `leyden` but currently falls back to `cds` with a warning.
`logs-dir` applies to the server process; the launcher's own log output is always written under `.micronaut/test-resources/logs` in the project.

`infer-classpath` lets Pyronaut infer test resources modules from application dependencies.
Use `additional-modules` when Pyronaut cannot infer a module or when you want to select modules explicitly.
An entry can be a short Test Resources module name such as `jdbc-mysql`, a `group:artifact` coordinate, or a `group:artifact:version` coordinate:

* Short names and versionless `io.micronaut.testresources` coordinates use the Test Resources version.
* Versionless coordinates in any other group use the version managed by the Micronaut platform BOM (`[tool.pyronaut.platform]`) or a configured BOM, for example `"io.micronaut.langchain4j:micronaut-langchain4j-ollama-testresource"`. If no BOM manages the module, add an explicit version.
* An explicit version is always used as written.

== Standalone server commands

Use the explicit server command when you want a reusable server:

[source,bash]
----
pyronaut test-resources-server start
pyronaut test-resources-server status
pyronaut test-resources-server stop
----

Set `PYRONAUT_TEST_RESOURCES_DISABLED=true` to disable automatic orchestration for a command invocation.
For direct-source execution, `--disable-test-resources` is also authoritative.
