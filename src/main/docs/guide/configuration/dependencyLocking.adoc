`pyronaut lock` writes `pyronaut.lock`, a list of every Maven artifact that `pyronaut setup`, `pyronaut install`, and `pyronaut build` resolve for the project, each with the repository it came from and its SHA-256 checksum.
Commit the file next to `pyproject.toml` (and `uv.lock`, which covers the Python packages): dependency changes then show up as reviewable diffs, every later resolution is checked against the recorded checksums, and sandboxed builds (Nix, Bazel, Guix, air-gapped CI) can fetch each artifact individually by URL and checksum instead of letting Pyronaut download arbitrary artifacts.

[source,bash]
----
pyronaut lock
----

Run it again whenever you change `[tool.pyronaut.dependencies]`, the repositories, the Micronaut versions, or update the SDK.
`pyronaut lock --check` fails with exit code `8` when `pyronaut.lock` is missing or differs from what the current configuration resolves, which suits a CI step.

== What the lock covers

`pyronaut lock` resolves exactly what the other commands resolve and records each artifact Maven Resolver hands to Pyronaut:

- the SDK launcher classpaths that `pyronaut setup` resolves (the `pyronaut-dev`, `pyronaut-run`, and `pyronaut-run-python` compiler classpaths and the JVM tool runtime), when the installed SDK needs `pyronaut setup`;
- every `pyronaut install` scope: `build`, `runtime`, `development-runtime`, `test`, and `test-resources-server` (when Test Resources is enabled);
- the POM of every artifact, and every parent POM and BOM, because Maven needs them to compute the dependency graph.

`pyronaut build` resolves its Maven dependencies through `pyronaut install`, so the same entries cover it.
Source and Javadoc JARs, which `pyronaut install` only fetches for editor support, are not locked.

The lock does not cover what Pyronaut downloads outside Maven: the GraalVM JDK, the GraalPy interpreter, and the native launchers that `pyronaut setup` provisions are already verified against published checksums, and Python packages belong in `uv.lock`.
Maven and Gradle projects resolve their dependencies with their own build tool; use its dependency locking and checksum verification instead.

== File format

`pyronaut.lock` is TOML, sorted by path so that diffs stay small:

[source,toml]
----
# This file is generated by `pyronaut lock`. Do not edit it by hand.
version = 1

[[artifact]]
coordinates = "io.micronaut:micronaut-core:jar:4.10.7"
path = "io/micronaut/micronaut-core/4.10.7/micronaut-core-4.10.7.jar"
repository = "https://repo1.maven.org/maven2/"
url = "https://repo1.maven.org/maven2/io/micronaut/micronaut-core/4.10.7/micronaut-core-4.10.7.jar"
sha256 = "..."
----

- `coordinates`: `group:artifact:extension[:classifier]:version`.
- `path`: the location in the standard Maven repository layout.
- `repository`: the repository the artifact was resolved from, or one of two markers for an artifact that has no remote origin:
** `bundled`: an `io.micronaut.pyronaut` module that Pyronaut seeds into the local repository from the SDK wheel. These modules ship with the SDK and are not necessarily published to any Maven repository.
** `local`: any other artifact found in the local repository without a record of where it came from, for example one copied there by hand.
- `url`: `repository` followed by `path`. Entries marked `bundled` or `local` have no `url`.
- `sha256`: the checksum of the artifact.

Artifacts resolved from `mavenLocal` or a file repository keep their `file:` URL; such a lock is only portable when those repositories are available to the build too.

== Checksum verification

When `pyronaut.lock` exists, every Maven artifact that Pyronaut resolves and the lock lists must match its recorded checksum, whether the artifact was downloaded or already cached in the local repository.
A mismatch fails the command and names the artifact, both checksums, and the file:

----
Dependency lock verification failed (/work/app/pyronaut.lock):
  - com.example:lib:jar:1.2 does not match pyronaut.lock: expected sha256 3f1a... but /home/me/.m2/repository/com/example/lib/1.2/lib-1.2.jar has 9b02...
----

Artifacts the lock does not list are accepted, so a lock that is out of date after a dependency change does not break `pyronaut install`; run `pyronaut lock` to update it.

== Locked resolution

`pyronaut install --locked` (or `PYRONAUT_LOCKED=true` for any command, including `pyronaut build`, `pyronaut dev`, and `pyronaut test`, which install dependencies on demand) also fails on every artifact the lock does not list.
`pyronaut setup --locked`, run in the project directory, does the same for the SDK launcher classpaths and resolves them again even when setup is already complete.
Locked resolution requires `pyronaut.lock`; without it the command fails and asks you to run `pyronaut lock`.

To resolve only the locked artifacts, without any repository access, point Pyronaut at a directory that contains them in Maven repository layout, at each entry's `path`:

[source,bash]
----
PYRONAUT_LOCK_REPOSITORY=/path/to/locked-artifacts pyronaut install --offline
----

`--lock-repository <dir>` is the equivalent `pyronaut install` option. A lock repository implies `--locked`: it replaces every configured repository (including `mavenCentral`, `mavenLocal`, and the Sonatype snapshot repository), works when the command runs `--offline`, and the checksum of every artifact taken from it is verified against the lock.
An artifact missing from the lock repository fails resolution and names the missing coordinates.

A sandboxed build fetches every `url` with its `sha256`, places each file at its `path`, and passes the resulting directory as the lock repository.
Entries without a `url` are skipped: locked resolution takes them from the local repository instead (`pyronaut setup` and `pyronaut install` seed the `bundled` ones there from the installed SDK) and still verifies their checksums against the lock.
Running `pyronaut lock` against a clean local repository records a download URL for every artifact that is not bundled.
With Nix, for example:

[source,nix]
----
let
  lock = builtins.fromTOML (builtins.readFile ./pyronaut.lock);
  lockRepository = pkgs.linkFarm "pyronaut-maven-repository" (map (artifact: {
    name = artifact.path;
    path = pkgs.fetchurl { inherit (artifact) url sha256; };
  }) (builtins.filter (artifact: artifact ? url) lock.artifact));
in
# ... then, in the build: PYRONAUT_LOCK_REPOSITORY=${lockRepository} pyronaut install --offline
----

The lock file location defaults to `pyronaut.lock` in the project directory; set `PYRONAUT_LOCK_FILE` (or `--lock-file <file>` on `pyronaut install`) to use another file.

Locking has these limitations:

- SNAPSHOT dependencies are recorded with the timestamped version they resolved to, but a lock repository cannot serve them because it holds no `maven-metadata.xml`. Lock only released versions for reproducible builds.
- Version ranges need repository metadata as well, and fail in a lock repository.
- Direct-source projects (`pyronaut install App.java`) and Maven or Gradle projects cannot be locked.
