= Configuration Validation

`pyronaut validate-config` validates Micronaut configuration against the resolved application classpath.
It is useful after changing `application.toml`, dependencies, environments, or source layout.

Run validation explicitly with:

[source,bash]
----
pyronaut validate-config --scenario dev
pyronaut validate-config --scenario production
----

Supported scenarios are:

- `dev`
- `run`
- `test`
- `production`

The standalone command defaults to `production`.
`pyronaut dev`, `pyronaut run`, `pyronaut test`, and native build flows call validation with their own scenario defaults unless you pass `--no-validate`.

== What is validated

Validation loads configuration the same way the application does.
It reads `application.toml` (and `application.properties`, `application.yml` or `application.json`) plus environment-specific variants such as `application-dev.toml` from:

- the resources directories (`config` by default, set with `resources` and `additional-resources` in `[tool.pyronaut.sources]`)
- `src/main/resources`
- for the `test` scenario, the test resources directories as well (Maven and Gradle projects also include them for `dev`)

Each property is checked against the configuration schemas of the application classpath.
Validation reports:

- values of the wrong type, for example `port = "eighty-eighty"` under `[micronaut.server]`
- values that are not in an enum, for example `schema-generate = 'CREATE_DRPO'` under `[datasources.default]`
- unknown keys, for example `prot = 8080` under `[micronaut.server]`, with a suggestion when a similar key exists

Each error names the file and line it came from.
Unknown keys are errors while `fail-on-not-present` is `true`, which is the default.

Validation runs for `pyproject.toml` projects and for Maven and Gradle projects.
Direct-source launches such as `pyronaut dev main.py` do not run configuration validation.

== Reports

By default, Pyronaut writes reports under:

[source,text]
----
__pyronaut__/reports/config-validation/<scenario>/
----

The default report files are:

- `configuration-errors.json`
- `configuration-errors.html`

Pyronaut also writes `__pyronaut__/.config-validation-cache.properties` to avoid repeating unchanged validations.

For Maven and Gradle projects Pyronaut writes the reports and cache under `target/pyronaut` or `build/pyronaut` instead of `__pyronaut__`.

== Project configuration

[source,toml]
----
[tool.pyronaut.validation]
enabled = true
fail-on-not-present = true
deduce-environments = false
validate-dependency-injection = false
dependency-injection-validation-strategy = "reachable"
format = "both"
suppressions = []

[tool.pyronaut.validation.test]
environments = ["test"]

[tool.pyronaut.validation.production]
environments = []
----

Scenario-specific settings can override environments, classpath entries, resources directories, and output directories.

== Dependency injection validation

Pyronaut disables dependency injection validation by default.
Enable it when you want validation to include bean graph checks:

[source,bash]
----
pyronaut validate-config --validate-dependency-injection
----

or in `pyproject.toml`:

[source,toml]
----
[tool.pyronaut.validation]
validate-dependency-injection = true
dependency-injection-validation-strategy = "reachable"
----

Available strategies are `reachable`, `application-beans`, and `all-beans`.

== Suppressions

When validation finds suppressible errors, the CLI prints a TOML snippet that you can copy into `pyproject.toml`:

[source,toml]
----
[tool.pyronaut.validation]
suppressions = [
  "datasources.default.url"
]
----

Keep suppressions narrow and revisit them when adding the missing configuration or dependency.
