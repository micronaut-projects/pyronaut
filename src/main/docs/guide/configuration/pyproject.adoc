= Configuring pyproject.toml

`pyproject.toml` is the source of truth for Pyronaut's project configuration and runtime project model.
It includes standard Python project metadata plus the `[tool.pyronaut]` tables consumed by the CLI.

== Minimal structure

[source,toml]
----
[project]
name = "hello-pyronaut"
version = "0.1.0"
dynamic = ["scripts"]

[build-system]
requires = ["setuptools", "wheel", "tomli"]
build-backend = "setuptools.build_meta"

[tool.pyronaut]
repositories = ["mavenCentral"]

[tool.pyronaut.dependencies]
runtime = []
build = []
test = []
----

== Managed versions

Pyronaut can resolve versionless Micronaut coordinates from configured BOM versions:

[source,toml]
----
[tool.pyronaut.core]
version = "5.2.3"

[tool.pyronaut.platform]
version = "5.1.0"
----

If these tables are omitted, Pyronaut uses the managed versions bundled with the current Pyronaut distribution, which `pyronaut --version` prints. Python support requires Micronaut Core 5.2 or later.

== Source layout

Use `[tool.pyronaut.sources]` to move source and resource directories away from the defaults:

[source,toml]
----
[tool.pyronaut.sources]
python = "app"
python-test = "test/python"
java = "src/main/java"
java-test = "src/test/java"
resources = "app-config"
test-resources = "tests-config"
additional-resources = ["views", "assets"]
additional-test-resources = ["tests-fixtures"]
----

== Packaging, processor, and test modes

Choose what `pyronaut build` produces when no packaging-shaping command-line
option is present:

[source,toml]
----
[tool.pyronaut.packaging]
format = "wheel-jvm"

[tool.pyronaut.processor]
mode = "jvm" # jvm|native
incremental = false
python-incremental-mode = "conservative" # conservative|optimistic
daemon = false

[tool.pyronaut.test]
mode = "jvm" # jvm|native
engine = "both" # junit|pytest|both
verbose = false # stream application and test framework output to the console
----

`format` accepts exactly `fat-jar`, `wheel-jvm`, `wheel-native`,
`wheel-crema`, `docker-jvm`, `docker-native`, or `docker-crema`. It defaults to
`fat-jar` when the project has Java sources and to `wheel-jvm` otherwise. Command-line flags such as `--jar`, `--jvm`, `--native`, and
`--docker` override the configured format for that invocation.

The former `tool.pyronaut.build.mode` setting is no longer accepted. Migrate
`mode = "jvm"` to `format = "wheel-jvm"`, and `mode = "native"` to either
`format = "wheel-native"` for a closed-world build or `format = "wheel-crema"`
for a reusable native runtime.

The test engine defaults to `both`. Use `junit` for JUnit Jupiter tests, `pytest` for pytest tests, or `both` to execute both types.

`verbose` defaults to `false`: console output written while a test runs is
captured into the test reports rather than shown. Set it to `true`, or pass
`--verbose` to `pyronaut test`, to stream it to the terminal instead.

Native image settings and Docker image settings also live under `[tool.pyronaut.build]`.
For a Crema format, set `native-base = "default"` to use the configured
language-specific production runtime for the target platform, or set a
filesystem path or HTTP(S) URL to reuse a custom base. Docker builds select
Linux; host builds select the current operating system.
`pyronaut build --native-base=<path>` builds a custom base and writes
`build.native-base` together with `packaging.format = "wheel-crema"`;
`pyronaut build --docker --native-base=<image>` writes
`build.docker.base-image` together with `packaging.format = "docker-crema"`.
Bare `--native-base` selects the default runtime and does not change
`pyproject.toml`.
A closed-world
`wheel-native` or `docker-native` format rejects a configured reusable base.
See the CLI reference for the full build option surface.
See <<incrementalProcessing,Incremental processing>> before enabling incremental processing, the compiler daemon, or the optimistic Python dependency policy.

== Control panel

The development/TUI Control Panel is opt-in, and Pyronaut disables it by default. Enable it for `pyronaut dev` and `pyronaut --tui` with:

[source,toml]
----
[tool.pyronaut.control-panel]
enabled = true
path = "/control-panel"
production-enabled = false
----

The command-line option `--control-panel` enables it for that invocation and overrides this setting. `pyronaut dev --control-panel` also works for direct-source execution.
When you enable development Control Panel support, Pyronaut also adds Micronaut Management and the Control Panel management integration to the development runtime so health and diagnostic panels are available.
Pyronaut also adds the optional Control Panel modules that match the application's dependencies. It adds a module only when the application uses the library that the panel inspects:

[cols="1,1"]
|===
|Application dependency |Control Panel module

|`io.micronaut.sql:micronaut-jdbc`
|`micronaut-control-panel-datasource`

|`org.hibernate.orm:hibernate-core`
|`micronaut-control-panel-hibernate`

|`io.micronaut.kafka:micronaut-kafka`
|`micronaut-control-panel-kafka`

|`io.micronaut.objectstorage:micronaut-object-storage-core`
|`micronaut-control-panel-object-storage`

|A Micronaut Cache implementation, such as `micronaut-cache-caffeine`
|`micronaut-control-panel-cache`
|===

The Caffeine cache that Pyronaut adds to the development runtime by default does not enable the cache panel. Direct-source execution selects the same modules from the dependencies that the sources declare.

Pyronaut writes the implicitly enabled development Control Panel dependencies only to the `development-runtime` dependency manifest, so `pyronaut build` does not package them.
Applications can declare their own development-only runtime dependencies with `development-runtime = [...]` under `[tool.pyronaut.dependencies]`.

Set `production-enabled = true` only when the application has Micronaut Security on the runtime classpath and you want the Control Panel in production runtime artifacts.
Production Control Panel inclusion keeps the Micronaut Control Panel security defaults; the anonymous access used by `pyronaut --tui` is not applied to production builds.

== Toolchain

Commands that delegate to Java use a GraalVM JDK.
You can let Pyronaut discover a compatible installed JDK, or pin a toolchain:

[source,toml]
----
[tool.pyronaut.toolchain]
type = "jvm" # jvm|native
distribution = "ee"
java-version = 25
version = "25i4"
----

Development builds can use `distribution = "dev"` with a `release-tag` or explicit `download-url`.
Use `type = "native"` to route supported CLI lifecycle commands through the native `pyronaut-dev` uber CLI.
It selects how CLI tooling executes; it does not select the output of
`pyronaut build`. Use `[tool.pyronaut.packaging]` for the build default.

=== AOT cache

With the JVM toolchain on JDK 25 or later, Pyronaut can start its JVMs from a Leyden AOT cache (JEP 483).
It is disabled by default:

[source,toml]
----
[tool.pyronaut.toolchain]
type = "jvm"
aot-cache = true
----

The first launch of each JVM, whether the application or test JVM of `pyronaut dev`, `run` and `test`, or a tool such as the processor, configuration validator, installer or Test Resources client, is a training run.
It starts more slowly and prints `AOTConfiguration recorded` as it exits.
The cache is then created in the background under `~/.pyronaut/caches/aot`, and later launches start from it.
A cache is replaced when the JDK, the JVM options or a class path JAR changes, so a dependency change means one more training run.
Each cache takes up to a few hundred megabytes; delete `~/.pyronaut/caches/aot` to reclaim the space.

== Python environment

`pyronaut install` creates `.venv` with GraalPy and installs the project's Python dependencies into it, with `uv sync` for uv projects and `pip` otherwise (see <<python-uv-projects,uv projects>>).
Set `manage-dependencies = false` when another tool manages `.venv`; Pyronaut then only checks that GraalPy created it:

[source,toml]
----
[tool.pyronaut.python]
manage-dependencies = false
----

`pyronaut install --no-python-deps` does the same for a single run.
