= Installing Pyronaut

Install the Pyronaut CLI, then run `pyronaut setup` to provision the SDK that runs Pyronaut applications.

== Install the Pyronaut CLI

The CLI requires Python 3.10 or later.

Install Pyronaut from PyPI:

[source,bash,subs="attributes"]
----
python3 -m pip install --upgrade 'pyronaut=={projectVersion}'
pyronaut --version
----

The same wheel is also attached to its https://github.com/{githubSlug}/releases[GitHub release]. To install it
directly from the release instead of PyPI, point `pip` at the release assets:

[source,bash,subs="attributes"]
----
python3 -m pip install --upgrade --no-index \
  --find-links https://github.com/{githubSlug}/releases/expanded_assets/v{projectVersion} \
  'pyronaut=={projectVersion}'
pyronaut --version
----

The Python installation used by `pip` only installs the CLI. Pyronaut applications run with the embedded GraalPy
runtime supplied by the Pyronaut SDK, and `pyronaut setup` provisions the matching GraalPy interpreter for project
virtual environments. `pyronaut --version` shows the required version on the `GraalPy Interpreter` line.
If your application or tests use Python packages, see <<prerequisites,Getting Started Step 1>> for the project
environment setup.

== Provision the Pyronaut SDK

Provision the SDK after installing or upgrading the Pyronaut CLI:

[source,bash]
----
pyronaut setup
----

Setup locates or provisions a compatible GraalVM JDK and the exact GraalPy interpreter the SDK was built with, downloads
the native Pyronaut launchers, resolves the SDK dependencies, and stores validated machine-local state under
`~/.pyronaut`. You do not need to install GraalVM or GraalPy manually for the default setup.

Setup reuses a matching GraalPy that is already installed with pyenv or under `~/.pyronaut/sdks`. When none is
installed, setup runs `pyenv install` if pyenv is available, and otherwise downloads GraalPy into
`~/.pyronaut/sdks`.

Pyronaut records setup state in `setup.json` under the Pyronaut home directory:

[source,text]
----
~/.pyronaut/setup/<sdk-version>/<os>-<architecture>/setup.json
----

The placeholders `<sdk-version>`, `<os>`, and `<architecture>` identify the SDK version and the platform where setup runs.

The setup command is idempotent. Run `pyronaut setup --refresh` when you need to re-resolve setup dependencies or rewrite setup state. Use `pyronaut setup --offline` only when the required JDK, native launchers, and Maven artifacts are already cached.
If Pyronaut cannot find a recorded artifact, or if the SDK, platform, repository, or native bundle configuration changes, execution commands exit with code `8` and instruct you to run `pyronaut setup` again.
Help and version commands remain available before setup.

To upgrade an installed CLI to the latest release and provision it in one step, run:

[source,bash]
----
pyronaut update
----

The command also removes the launchers and cached artifacts of older versions. See <<pyronautCliV2,Pyronaut CLI Reference>> for its options.

If `pyronaut setup` or any later command fails, run `pyronaut doctor` first:

[source,bash]
----
pyronaut doctor
----

It checks the Python version, the installed wheel and its setup state, the GraalVM JDK, GraalPy and interpreter mismatches, the native launchers, proxy settings, and Docker. Inside a project it also checks `pyproject.toml`, stale `pyronaut install` state, the threading configuration, that every declared Python package imports on the project's GraalPy under the configured context pool, GraalPy's published compatibility results for those packages, and `pytest`.
Failing rows include a suggested command or action when Pyronaut can identify one, and `pyronaut doctor --json` produces the same report for tooling.
See <<pyronautCliV2,Pyronaut CLI Reference>> for the full list of checks.

By default, setup resolves SDK dependencies from Maven Central. When the installed SDK is a snapshot build, setup also checks Sonatype Central's snapshots repository for pre-release artifacts.
Override the setup repositories globally in `~/.pyronaut/settings.toml`; an explicit list replaces these defaults:

[source,toml]
----
[maven]
repositories = [
  "mavenCentral",
  "https://central.sonatype.com/repository/maven-snapshots/"
]
----

Setup installs native executables into `~/.pyronaut/bin`:

[source,text]
----
~/.pyronaut/bin/<version>/<os>-<architecture>/
----

== Relocate Pyronaut state

Global Pyronaut state (setup records, the SDK tool runtime, native launchers, JDKs, caches and `settings.toml`)
follows the XDG base directory layout described below on Linux, and whenever an `XDG_*_HOME` variable is set.
Otherwise it lives in `~/.pyronaut`, where `~` is `$HOME`. Set `PYRONAUT_HOME` to keep all of it in one directory
of your choice instead:

[source,bash]
----
export PYRONAUT_HOME=/opt/pyronaut-state
pyronaut setup
----

The CLI passes the resolved directories to every Java tool and launcher it starts (as `PYRONAUT_CONFIG_DIR`,
`PYRONAUT_CACHE_DIR` and `PYRONAUT_DATA_DIR`), so they use the same locations even when the JVM's `user.home` (taken
from the operating system's user database) differs from `$HOME`, for example in a build sandbox. The local Maven
repository defaults to `$HOME/.m2/repository` on both sides; use `--local-repository` to change it.

=== Use the XDG base directory layout

Pyronaut follows the https://specifications.freedesktop.org/basedir-spec/latest/[XDG Base Directory Specification]
for new installations on Linux, and on any platform when `XDG_CONFIG_HOME`, `XDG_CACHE_HOME` or `XDG_DATA_HOME` is set.
State is then split by kind:

[cols="1,2,3"]
|===
|Kind |Directory |Contents

|Configuration
|`$XDG_CONFIG_HOME/pyronaut` (default `~/.config/pyronaut`)
|`settings.toml`

|Cache
|`$XDG_CACHE_HOME/pyronaut` (default `~/.cache/pyronaut`)
|AOT caches (`caches/aot`), IDE stubs (`ide-stubs`), GraalPy compatibility data and `pyronaut update` downloads

|Data
|`$XDG_DATA_HOME/pyronaut` (default `~/.local/share/pyronaut`)
|JDKs and SDKs (`sdks`), native launchers (`bin`), setup records (`setup`) and the SDK tool runtime (`tools`)
|===

An existing `~/.pyronaut` installation keeps working where it is. To move it to the XDG layout, run:

[source,bash]
----
pyronaut setup --xdg
----

Setup copies `~/.pyronaut/settings.toml` to the XDG configuration directory when that directory has none, provisions
the SDK into the data directory, and prints a note that `~/.pyronaut` is no longer used and can be removed.

`pyronaut setup` creates `$XDG_CONFIG_HOME/pyronaut` whenever the XDG layout is in use. Its existence keeps the layout
enabled, so later commands (and the Java tools they start) use it even if a `~/.pyronaut` directory appears.
`pyronaut doctor` reports the active layout and its paths in the *Pyronaut state* row.

Set `PYRONAUT_XDG=true` or `PYRONAUT_XDG=false` to choose the layout explicitly; `false` keeps `~/.pyronaut` even on
Linux. `PYRONAUT_HOME` always takes precedence and keeps everything in one directory.

To switch back to `~/.pyronaut`, export `PYRONAUT_XDG=false` (or, outside Linux and without `XDG_*_HOME` variables,
remove `$XDG_CONFIG_HOME/pyronaut`), move `settings.toml` back into `~/.pyronaut` and run `pyronaut setup` again. The
XDG cache and data directories can then be removed.

== Project installation

After you create a project with `pyronaut create` or add a `pyproject.toml` as described in <<project,Create a Pyronaut Project>>, run:

[source,bash]
----
pyronaut install
----

`pyronaut install` creates the project `.venv` with GraalPy and installs the Python dependencies declared in
`pyproject.toml` or `requirements.txt` into it. It then resolves Java dependencies for the configured build, runtime,
development-runtime, test, and test-resources-server scopes.

By default, Pyronaut installs dependency artifacts into Maven local:

[source,text]
----
~/.m2/repository
----

If you start the JVM with `-Dmaven.repo.local=/path/to/repo`, Pyronaut uses that value as the default local repository instead.
Override the selected repository for an invocation:

[source,bash]
----
pyronaut install --local-repository .pyronaut-m2
----

Pyronaut resolves relative paths passed to `--local-repository` against the project directory.
Pyronaut still writes project state and classpath manifests under `__pyronaut__`; the option changes only where Pyronaut stores resolved Maven artifacts.

== Generated project state

`pyronaut install` writes files that later commands consume:

- scoped dependency manifests under `__pyronaut__/resolved-*-dependencies`
- `pyproject.toml` schema support under `__pyronaut__/schemas`
- optional `application.toml` schema support
- Python IDE stubs under `__pyronaut__/ide-stubs`

Pyronaut generates the `__pyronaut__` directory as state.
Treat it as generated state, not application source.

== Platform notes

The CLI currently targets macOS and Linux.
Docker is only required when using Micronaut Test Resources or Docker package formats.
