= Installing Pyronaut

Pyronaut can be installed into your existing Python installation via `pip`.


[source,bash]
----
pip install pyronaut
pyronaut --version
pyronaut setup
----

Note the version of Python used to run applications is dictated by `pyronaut` which bundles GraalPy and DOES NOT use your local Python installation but instead an isolated embedded version of GraalPy.

`pyronaut setup` is required once after installing or upgrading the SDK wheel.
It locates or provisions the packaged GraalVM JDK, downloads all three native launchers, resolves the SDK and native compiler dependencies into Maven local, and publishes validated machine-local state under:

[source,text]
----
~/.pyronaut/setup/<sdk-version>/<os>-<architecture>/setup.json
----

The setup command is idempotent. Use `pyronaut setup --refresh` to re-resolve dependencies and rewrite setup state, or `pyronaut setup --offline` to use only an already cached JDK, native launchers, and Maven artifacts.
If a recorded artifact is removed or the SDK, platform, repository, or native bundle configuration changes, execution commands exit with code `8` and instruct you to run `pyronaut setup` again.
Help and version commands remain available before setup.

If `pyronaut setup` or any later command fails, run `pyronaut doctor` first:

[source,bash]
----
pyronaut doctor
----

It checks the Python version, the installed wheel and its setup state, the GraalVM JDK, GraalPy and interpreter mismatches, the native launchers, proxy settings, and Docker. Inside a project it also checks `pyproject.toml`, stale `pyronaut install` state, the threading configuration, that every declared Python package imports on the project's GraalPy under the configured context pool, GraalPy's published compatibility results for those packages, and `pytest`.
Every failing row comes with the command that fixes it, and `pyronaut doctor --json` produces the same report for tooling.
See <<pyronautCliV2,Pyronaut CLI Reference>> for the full list of checks.

By default setup resolves SDK dependencies from Maven Central. Snapshot SDK versions also use the Sonatype Central snapshots repository.
Override the setup repositories globally in `~/.pyronaut/settings.toml`; an explicit list replaces these defaults:

[source,toml]
----
[maven]
repositories = [
  "mavenCentral",
  "https://central.sonatype.com/repository/maven-snapshots/"
]
----

Setup installs native executables into `~/.pyronaut/bin`:

[source,text]
----
~/.pyronaut/bin/<version>/<os>-<architecture>/
----

TIP: see
<<proxyConfig,Proxy Configuration>> for proxy setup.

== Project Installation

After a project has a `pyproject.toml`, run:

[source,bash]
----
pyronaut install
----

`pyronaut install` resolves Java dependencies for the configured build, runtime, development-runtime, test, and test-resources-server scopes.

Dependency artifacts are installed into Maven local by default:

[source,text]
----
~/.m2/repository
----

If the JVM was started with `-Dmaven.repo.local=/path/to/repo`, that value is used as the default local repository instead.
The selected repository can be overridden per invocation:

[source,bash]
----
pyronaut install --local-repository .pyronaut-m2
----

Relative paths passed to `--local-repository` are resolved against the project directory.
Pyronaut still writes project state and classpath manifests under `__pyronaut__`; the option only changes where resolved Maven artifacts are stored.

== Generated Project State

`pyronaut install` writes files that later commands consume:

- scoped dependency manifests under `__pyronaut__/resolved-*-dependencies`
- `pyproject.toml` schema support under `__pyronaut__/schemas`
- optional `application.toml` schema support
- Python IDE stubs under `__pyronaut__/ide-stubs`

The `__pyronaut__` directory is generated state.
It should not be treated as application source.

== Platform Notes

The CLI currently targets macOS and Linux.
Docker is only required when using Micronaut Test Resources or Docker-based build modes.
