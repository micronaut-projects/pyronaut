Pyronaut is a framework for building Python applications on https://www.graalvm.org/python/[GraalPy] and https://micronaut.io[Micronaut]. It gives Python code access to Micronaut's HTTP server, dependency injection, configuration, validation, serialization, observability, and testing capabilities. Pyronaut processes Python and Java source before the application starts, preparing routes, beans, serializers, and validation metadata.

Python developers can use type hints and decorators to build applications for development, direct execution, or deployment as JVM applications, native executables, or containers. You write ordinary Python while Pyronaut connects it to the Micronaut application model.

Java developers can add Python code to a Micronaut application. Both languages share the application context, application configuration, and test lifecycle while retaining their own package and library dependencies.

== A minimal application

Create `app.py`:

[source,python]
----
from micronaut.http.annotation import Get


@Get("/")
def index() -> dict[str, str]:
    return {"Hello": "World"}
----

Run:

[source,bash]
----
pyronaut dev app.py
----

Pyronaut processes the source, starts a server on port 8080, and reloads it when the file changes. The route returns JSON, Pyronaut generates an OpenAPI description, and it serves Swagger UI at `/swagger-ui/index.html`. This direct-source application does not need `pyproject.toml`, a GraalPy virtual environment, or a separate application server.

== How Pyronaut differs from Flask and FastAPI

* *Decorators map to Micronaut annotations.* `@Get`, `@Singleton`, `@Value`, and the other decorators in this guide correspond to Micronaut annotations. Type hints on parameters and return values tell Micronaut how to bind requests, validate input, and serialize output.
* *Processing happens before startup.* `pyronaut process` reads your decorators and type hints and generates route and bean metadata, serializers, and validation metadata before the application starts. Source and generated-metadata errors can therefore appear during processing instead of on the first request.
* *Java libraries are available from Python.* Declare a Java library in `pyproject.toml`, resolve it with `pyronaut install`, and import its classes from Python.
* *Threads and `asyncio` both work.* Plain `def` routes run on a thread pool, `async def` routes run on the Netty event loop, and Python coroutines can await Java asynchronous results directly.

== Why choose Pyronaut

A typical production Python service combines a web framework, an application server, validation, serialization, testing, observability, packaging, and deployment tooling. Pyronaut connects these concerns through one application model on top of Micronaut, so the same Python types and decorators drive HTTP, validation, serialization, OpenAPI, dependency injection, editor support, and tests.

The following capabilities are available through this application model:

Observability and operations::
Micronaut's management endpoints (health, info, environment, loggers, routes, and thread dumps) are part of the runtime. Add the Micronaut modules for https://micronaut-projects.github.io/micronaut-micrometer/latest/guide/[Micrometer] metrics with registries for Prometheus, Datadog, CloudWatch, and others, https://micronaut-projects.github.io/micronaut-tracing/latest/guide/[OpenTelemetry] distributed tracing, and https://micronaut-projects.github.io/micronaut-kubernetes/latest/guide/[Kubernetes] service discovery, configuration, and health probes through `[tool.pyronaut.dependencies]`. For JVM deployments, Java tooling such as Java Flight Recorder, heap and thread analysis, and JMX also applies to the Python service.

Concurrency with the JVM and Netty::
Netty's event loop and Micronaut's thread pools serve requests. Synchronous Python routes run on a thread pool, while `async def` routes run on the event loop, so you can choose the model that fits the work. GraalPy can run Python in several interpreter contexts inside one process, so Python code can execute in parallel; the trade-offs are memory use and separate module state per context. See <<threading,Threading, Blocking Work and asyncio>>.

Test Resources for local infrastructure::
With `MicronautTest`, `pyronaut test` can run pytest against the application context and an embedded server. When the configured dependencies identify a supported service, https://micronaut-projects.github.io/micronaut-test-resources/latest/guide/[Micronaut Test Resources] can start the service, often in a Docker container through Testcontainers, and supply its connection settings. This can remove the need to hard-code local service URLs and credentials. The same mechanism supports `pyronaut dev`. See <<testResources,Test Resources and Docker>>.

Errors before deployment::
Pyronaut generates route and bean metadata, serializers, and validation metadata during processing, where it can report source and generated-metadata errors. `pyronaut validate-config` checks application configuration per environment; enable dependency injection validation when you also want it to check the bean graph. `pyronaut dev`, `pyronaut run`, `pyronaut test`, and native build flows run configuration validation automatically unless you disable it. See <<validateConfig,Configuration validation>>.

Optimise hot paths in Java::
When a code path needs more speed than Python offers, write it in Java in the same project (under `src-java` by default) and inject it into your Python code like any other bean. Both languages share one dependency injection container, application configuration, and test invocation. See <<usingPackagesJavaLibraries,Using Python Packages and Java Libraries>>.

Java libraries and Micronaut modules::
Declare JDBC drivers, Kafka and RabbitMQ clients, cloud SDKs, PDF and document libraries, and other Java libraries in `pyproject.toml`, then import them from Python. Micronaut modules add https://micronaut-projects.github.io/micronaut-data/latest/guide/[Micronaut Data] repositories, https://micronaut-projects.github.io/micronaut-security/latest/guide/[Micronaut Security] (JWT, OAuth 2.0, and OpenID Connect), Kafka and RabbitMQ listeners, caching, scheduling, and views. Python code can use their Java APIs, including annotation-based APIs that Pyronaut exposes as decorators.

One CLI for the application lifecycle::
`pyronaut create`, `dev`, `test`, `validate-config`, and `build` cover the project lifecycle. The build command supports Python wheels, runnable JARs, container images, GraalVM native executables, and reusable Crema runtime images. See <<packaging,Packaging and Deployment>>.

Multiple deployment targets::
JVM packages require a compatible GraalVM JDK. Native executable targets depend on the available launcher bundle and native toolchain for the target platform. Packages for Python applications include the embedded GraalPy runtime, so the deployment target does not need a separate Python installation.

Editor support::
`pyronaut install` generates stubs that Pylance and PyCharm can use for completion and type checking of Micronaut and Java APIs. It also writes JSON schemas that supported editors can use to validate `pyproject.toml` and `application.toml`.

== Project structure

A typical Pyronaut project directory contains:

* Python application sources under `src`
* Python tests under `tests`
* Micronaut configuration such as `application.toml` under `config`
* Python and Java dependencies declared in `pyproject.toml`
* Generated state under `__pyronaut__`, which is safe to delete

The `pyronaut` command is the single entry point. It creates projects, resolves Java dependencies, processes sources, runs applications during development or for deployment, runs tests, validates configuration, and builds wheels, JARs, native executables, and container images. It also generates editor stubs that VS Code (Pylance) and PyCharm can use for completion of Micronaut and Java APIs.
