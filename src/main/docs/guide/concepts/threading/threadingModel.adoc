Our HTTP server is built on https://netty.io[Netty]. Netty uses a small number of _event loop_ threads, typically two per CPU core, and each thread serves many connections by reacting to I/O events. Blocking one of these threads stalls every connection assigned to it, so the whole design revolves around one question: where does application code run?

== The three kinds of threads

[cols="1,3", options="header"]
|===
|Thread |Purpose

|Netty event loop
|Reads requests, writes responses and runs non-blocking code. There are few of them and they must never block.

|`io` executor
|An unbounded pool of ordinary platform threads for code that may block, such as a database query or a call to a slow service. We create threads on demand and reuse idle ones.

|`blocking` executor
|A second pool for work explicitly marked with `@ExecuteOn(TaskExecutors.BLOCKING)`. Other application code may use virtual threads; Pyronaut configures this pool to use platform threads because GraalPy cannot run Python code on virtual threads.
|===

== Where Python code runs

We decide where to run a route from its signature, the same way FastAPI decides between the event loop and its thread pool:

[cols="2,2", options="header"]
|===
|Function |Runs on

|`def` route or bean method
|The `io` executor. We route every synchronous Python method there automatically, so ordinary Python code cannot block the event loop even if it performs I/O.

|`async def` route or bean method
|The Netty event loop that received the request. The coroutine is bound to a Pyronaut-managed asyncio loop on that thread; `await` suspends it and frees the thread for other connections.

|Method decorated with `@ExecuteOn(TaskExecutors.BLOCKING)`
|The `blocking` executor.

|Method decorated with `@ExecuteOn("my-pool")`
|A custom executor named `my-pool` under `micronaut.executors`.

|Method returning a `Publisher`, `Mono` or `CompletionStage`
|We subscribe on the event loop and write the response when the value arrives. The code that produces the value decides which thread does the work.
|===

In practice, a plain `def` route can call a JDBC repository, read a file, or use the `requests` shim without an extra decorator because it already runs off the event loop. An `async def` route must await non-blocking operations; move blocking work to `run_in_executor` (see <<blockingWork,Running Blocking Code>>).

NOTE: The Python-specific selector exists because Python code usually has no way to signal that it is non-blocking.

== Pyronaut executor defaults

Pyronaut sets low-priority defaults so that both executors use cached platform threads:

[source,toml]
----
[micronaut.executors.io]
type = "cached"
virtual = false

[micronaut.executors.blocking]
type = "cached"
virtual = false
----

Anything you put in `application.toml` overrides these values. For example, to bound the number of concurrent database calls to match a connection pool of 20 connections:

[source,toml]
----
[micronaut.executors.io]
type = "fixed"
n-threads = 20
----

WARNING: Never set `virtual = true` for an executor that runs Python code. GraalPy does not support executing Python on virtual threads and the application will fail at runtime.

See the https://docs.micronaut.io/latest/guide/#threadPools[Configuring Server Thread Pools] section of the Micronaut guide for executor types and options.
