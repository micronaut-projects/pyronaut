= Packaging & Deployment

`pyronaut build` packages the processed application for distribution. The
default is `wheel-jvm`; configure another default with
`tool.pyronaut.packaging.format`. An explicit packaging flag takes precedence
over that setting. `tool.pyronaut.toolchain.type` only controls how Pyronaut's
CLI tooling executes and does not select a build output.

== Choosing a package type

[cols="1,1,2",options="header"]
|===
|Format |Equivalent command |Best fit and trade-off

|`fat-jar`
|`pyronaut build --jar`
|One JVM-hosted artifact runnable with `java -jar`. It includes the selected
Java or Python production runtime and is typically larger than a wheel.

|`wheel-jvm`
|`pyronaut build --jvm`
|The default Python distribution. It has the shortest build time and is a good
choice when a JVM is already available in the deployment environment.

|`docker-jvm`
|`pyronaut build --jvm --docker`
|A portable container form of the JVM wheel. JVM deployment generally offers
the best peak throughput after warm-up, at the cost of JVM startup time and a
larger memory footprint.

|`wheel-native`
|`pyronaut build --native`
|Produces a standalone executable with fast startup and low memory use. Each
application build performs native-image analysis, which is comparatively slow,
and application code must satisfy native-image's closed-world requirements,
including reachability metadata or reflection configuration where needed.

|`docker-native`
|`pyronaut build --native --docker`
|Builds the native executable in a Linux container and packages it in a small
runtime image. Choose this when the target platform is a container platform.

|`wheel-crema`
|`pyronaut build --native-base=default`
|A wheel using a reusable native production runtime. A configured custom base
is preferred; otherwise Pyronaut uses the bundled default.

|`docker-crema`
|`pyronaut build --native-base=default --docker`
|A container with a reusable custom or bundled Crema base and an application
layer.
|===

`pyronaut build --native-base` remains a separate operation that creates a
reusable base; it does not select a final packaging format.

== Runnable FAT JARs

Build one executable JAR with:

[source,bash]
----
pyronaut build --jar
java -jar dist/hello-pyronaut-0.1.0.jar argument1 argument2
----

The artifact is written as `dist/<project-name>-<version>.jar`; unsafe filename
characters are replaced with `-`. Both Java and Python applications require a
compatible GraalVM JDK, as they use the same production runtime selected for a
JVM wheel. Python FAT JARs therefore include GraalPy and are larger than their
Java equivalents. The command supports Pyronaut projects, direct Java or Python
sources, and external Maven or Gradle projects.

The outer JAR contains a small launcher plus an indexed `PYRONAUT-INF` layout.
Application classes and resources precede dependencies, followed by dependency
roots in resolved-classpath order. Duplicate classes use first-root-wins
semantics. Resources, including `META-INF/services` descriptors, remain
enumerable across every root. Multi-release JAR selection and package manifest
metadata such as sealing are preserved. The launcher reads entries directly
from the artifact and does not extract them to disk.

Packaging is reproducible: entry ordering and timestamps are deterministic and
source paths are not recorded. Dependency signature files and stale JAR indexes
are omitted because repackaging invalidates them. Sign the completed FAT JAR if
artifact signing is required.

== Wheels and JVM containers

A JVM build produces a Python wheel in `dist/`:

[source,bash]
----
pyronaut build --jvm
----

Install the wheel into the target Python environment in the normal way. The
wheel carries the processed application and its runtime launch support; the
deployment environment must provide a compatible GraalVM JDK.

Use Docker when the deployment platform expects an OCI image:

[source,bash]
----
pyronaut build --jvm --docker
----

The default Dockerfile stages the processed classes, application resources,
resolved runtime dependencies, and the appropriate production launcher.

== Application native images

Native builds create `__pyronaut__/native/application` by default:

[source,bash]
----
pyronaut build --native
----

Native images offer fast startup and low memory consumption, which is useful
for short-lived workloads and densely deployed services. The trade-off is build
time: every application-native build performs native-image analysis. Native
image analysis also uses a closed-world model, so libraries that use reflection,
dynamic proxies, resources, or other dynamic behavior may need reachability
metadata or explicit native-image configuration. See
xref:pyronautCliV2.adoc#reachability-metadata-repository-native-mode[] for the
metadata repository settings.

Pyronaut derives application packages from processed output and preserves them
in fully closed-world native images, keeping user classes available for runtime
reflection without widening a reusable production base image.

Use a container-native build to compile for Linux inside the configured native
builder image:

[source,bash]
----
pyronaut build --native --docker
----

== Crema production runtimes and base images

Crema is a reusable native production runtime. It contains Pyronaut's runtime
modules but excludes compilers, annotation processors, test libraries, and
other development tooling. `pyronaut-run` is the Java runtime; Python projects
use `pyronaut-run-python`, which additionally contains GraalPy, Truffle, and
the Python Logback integration.

Build a native base once after declaring the dependencies that should be shared:

[source,bash]
----
pyronaut build --native-base
----

Use the downloaded language-specific runtime when no dependency needs to be
included in a custom base. The first invocation resolves the configured
`[native-images]` bundle and stores it under `~/.pyronaut/bin`:

[source,bash]
----
pyronaut build --native-base=default
----

`--native-base` implies native packaging. For `default`, a host build selects
the bundle matching the current operating system and architecture; a Docker
build selects the Linux bundle matching the current architecture. Pyronaut
chooses `pyronaut-run` for Java projects and `pyronaut-run-python` for Python
projects.
The bundle is resolved using `[native-images]` in
`~/.pyronaut/settings.toml`, including its configured repository, version,
proxy, and authentication settings. A valid bundle already cached under
`~/.pyronaut` is reused; otherwise it is downloaded with progress reporting.

The native launcher projects publish the same complete bundle format used by
the CLI downloader. Running `./gradlew :micronaut-pyronaut-dev:assemble`,
`:micronaut-pyronaut-run:assemble`, or
`:micronaut-pyronaut-run-python:assemble` creates a versioned `.tar.gz` under
the module's `build/distributions` directory. Each archive contains the native
executable, generated native classpath manifests, and the native-image
`resources` directory. Python-capable images are built with
`-H:+CopyLanguageResources`, so `resources` is a runtime input and must remain
beside its executable when an archive is extracted, copied into a wheel, or
installed in a container. Adjacent native runtime libraries are part of the
same bundle contract.

[source,toml]
----
[tool.pyronaut.packaging]
format = "wheel-crema"

[tool.pyronaut.build]
native-base = "default"
----

Later native builds reuse the configured native base:

[source,bash]
----
pyronaut build
----

Set a stable output location in `pyproject.toml` when the image is shared by
multiple builds:

[source,toml]
----
[tool.pyronaut.packaging]
format = "wheel-crema"

[tool.pyronaut.build]
native-base = "build/pyronaut-base/pyronaut-run-python"
----

The value may instead be an HTTP(S) URL to a native executable. Pyronaut uses
the configured proxy settings and displays download progress. URL-based native
bases are unavailable with `--offline`. A raw URL continues to represent a
self-contained executable; use a published Pyronaut native bundle when
external language resources must be transported with the launcher.

Crema avoids rebuilding the native runtime for each source change. The native
base is the only expensive native-image build; subsequent application builds
package processed classes and application dependencies for runtime loading.
They retain native startup time without requiring each application to meet the
same closed-world reflection configuration requirements as a fully
application-native image. Inspect the native-base native-image report and SBOM
to confirm that its shared dependencies are included.

For Docker, build and tag the native base layer, then build the application
layer:

[source,bash]
----
pyronaut build --docker --native-base
----

[source,toml]
----
[tool.pyronaut.packaging]
format = "docker-crema"
----

[source,bash]
----
pyronaut build
----

To reuse a base produced in CI or another project, configure its image name:

[source,toml]
----
[tool.pyronaut.packaging]
format = "docker-crema"

[tool.pyronaut.build.docker]
base-image = "registry.example.com/acme/pyronaut-runtime:1"
----

The final image then adds only the application configuration, processed
classes, and schemas on top of the shared production runtime layer. For a
custom layering arrangement, see xref:pyronautCliV2.adoc#custom-dockerfiles-with-a-reusable-base[].

== Direct-source applications

`pyronaut build` packages standalone sources through the same JVM, native,
Docker, and native-base flows as a regular project:

[source,bash]
----
pyronaut build App.java --native --name hello-java --version 1.0.0
pyronaut build App.py --docker --native-base=default
pyronaut build App.java --jar --name hello-java --version 1.0.0
----

Sources compile to disk under `__pyronaut__/direct-source-build`. Use
`--setup pyproject.toml` for project configuration. Inline `@Dependency`
declarations are resolved before packaging and become part of a custom native
base's SBOM.
